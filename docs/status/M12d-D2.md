## 1. Re-deriving the patch's claims

Each claim was checked against the current tree and the oracle, not taken from
the commit messages.

### 1.1 The heuristic's mechanism — **true**

`CPDF_Font::LoadCharPositions` (`cpdf_font.cpp:449-467`) gated by
`ShouldApplyGlyphSpacingHeuristic` (`:240-264`). Both branches are ported in
`glyph_spacing_adjust` (`crates/pdfrum-render/src/text.rs:274`) and the five
gate conditions in `applies_glyph_spacing`
(`crates/pdfrum-font/src/subst/substfont.rs:310`). Read side by side:

| C++ | Rust | |
|---|---|---|
| `font_glyph_width && pdf > font + 1` | `face != 0 && declared > face.saturating_add(1)` | ✓ |
| `origin_.x += (pdf - font) * font_size / 2000.0f` | `origin.x = (declared - face) * font_size / 2000.0` | ✓ |
| `pdf && font && pdf < font` | `declared != 0 && face != 0 && declared < face` | ✓ |
| `adjust_matrix_ = [pdf/font, 0, 0, 1]` | `Affine::scale_non_uniform(declared / face, 1.0)` | ✓ |
| `is_vertical \|\| IsEmbedded() \|\| !HasFontWidths()` | `vertical \|\| embedded \|\| !declared_widths` | ✓ |
| `GetStandardFontIndex(lower).has_value()` | `standard_font_index(&lower).is_some()` | ✓ |
| `subst->IsBuiltInGenericFont()` | `subst.is_builtin_generic` | ✓ |
| `!subst->IsActualFontLoaded(lower)` | `!subst.is_actual_font_loaded(&lower)` | ✓ |

One apparent divergence was chased and is not one. The C++ reads
`current_font->GetSubstFont()`, where `current_font` may be a **per-glyph
fallback** font; ours reads the primary font's `subst()`. Our renderer has no
per-glyph fallback machinery at all, so `current_font` is always the primary
font and the two agree by construction. If fallback fonts are ever added, this
gate is one of the places that must learn about them.

### 1.2 The 0.759 factor — **true**, with the arithmetic corrected

The brief says `/MissingWidth 506` against "Arimo's `A` advance 667" gives
0.759. Measured from `Arimo-Regular.ttf`'s own tables: `unitsPerEm` 2048, `A`
is glyph 36, `advanceWidth` 1366, so 1366 × 1000 / 2048 = **666** per 1000 em,
not 667. The factor is 506 / 666 = **0.758630**, which rounds to the brief's
0.759. The claim is right; the intermediate was one unit off.

Two details of the fixture that the brief states loosely and are worth having
written down, because both are load-bearing:

- The drawn character is `(A)`, code 65, which is **outside** the font's
  `/FirstChar 1 /LastChar 1`. Its width therefore comes from `/MissingWidth
  506`, not from `/Widths [300]`. The 300 never participates.
- The text is set at `/F1 20 Tf`, **20 pt**, not 40. The brief's "at 40 pt the
  oracle's glyph is 20 px where ours is 28 px" is the figure at the pixel
  suite's 2× device scale. Measured now at 1×, the ink box is 21 px wide, and
  21 / 0.7586 = 27.7 ≈ the 28 px the brief names for the uncorrected glyph.

## 2. Step 3 — the serif bit, which was genuinely owed

This is the only part of D2 that was not already in the tree.

### 2.1 The hypothesis

M12b §10 item 8: "our `SystemFontDb::describe` derives the serif bit from
PANOSE while `CFX_FolderFontInfo` sets it only when the face *name* contains
'Serif', so Tinos and Gelasio carry `STYLE_SERIF` for us and not for the
oracle. It did not bite this corpus but it is real in
`FaceInfo::similarity_score`."

### 2.2 The measurement

The oracle has **two** style rules and the question is which one a `--font-dir`
run reaches.

- `CFX_FolderFontInfo::ReportFace` (`cfx_folderfontinfo.cpp:349-358`) sets
  three bits from two strings — ForceBold and Italic from the subfamily,
  Serif from the joined face name containing `"Serif"` — and sets **nothing
  else**. The script and fixed-pitch bits are never set by it at all.
- `CFX_Face::GetFontStyle` (`cfx_face.cpp:1608-1633`) reads PANOSE, `IsBold`,
  `IsItalic` and `IsFixedWidth`. It is inside
  `#if defined(PDF_ENABLE_XFA) || IS_ANDROID || IS_LINUX` and its only caller
  in the tree is `xfa/fgas/font/cfgas_fontmgr.cpp:651`.

`pdfium_test --font-dir` goes through `CFX_FolderFontInfo`. Ours was a port of
the XFA rule sitting in the folder enumerator's place.

Enumerating `third_party/test_fonts` through both rules, the disagreement is
not marginal:

| face | PANOSE rule (ours, before) | `ReportFace` (the oracle) |
|---|---|---|
| `Tinos`, `Tinos Bold`, `Tinos Bold Italic`, `Tinos Italic` | serif | — |
| `Cousine` ×4 | serif + fixed-pitch | — |
| `GardinerMod` ×2 | serif + fixed-pitch | — |
| `Gelasio`, `Gelasio Italic`, `Gelasio Bold Italic` | serif | — |
| **`Gelasio Bold`** | **not serif** | — |
| `Noto Color Emoji` | fixed-pitch | — |
| everything else (16 faces) | — | — |

**No face in the oracle's hermetic directory is serif**, because the Croscore
serif family is spelled `Tinos` and the other one `Gelasio`, and neither
contains the word. Eleven faces carried a bit the oracle gives to none of them,
and three carried a fixed-pitch bit the same way.

The `Gelasio Bold` row is the one that settles it independently of the port
question. Its PANOSE disagrees with its own Regular and Bold Italic siblings',
so the PANOSE rule splits one family three ways. A rule that does that is
scoring on something other than the family, and serif is the **16-point** term
— the largest of the five in `FaceInfo::similarity_score`, tied with weight and
slant.

Bold and italic agreed on this set: every face's `fsSelection` matches its own
subfamily string. They were moved onto the string regardless — the agreement is
a property of these fonts, not of the rule.

### 2.3 The fix, and a second divergence it uncovered

`describe` now calls a small `face_styles(name, style)` that is the three
substring tests and nothing else. `STYLE_SCRIPT` and `STYLE_FIXED_PITCH` are
still defined and still read by `similarity_score` — the terms exist in the
oracle's score too — they are simply never set by the enumerator, in either
implementation now.

Re-running the enumeration probe after the change: **every** face in
`test_fonts` reports serif=false, script=false, fixed=false, and bold/italic
exactly as its subfamily string says. Non-vacuous, and matching the oracle row
for row.

Checking the *names* the two enumerators produce, in the same probe, turned up
a second divergence in the same function that the register does not mention:

```
DIFF  fontdb="Noto Sans CJK JP"  nameID1="Noto Sans CJK JP Regular"
```

`ReportFace` builds its face name from `GetNameFromTT(names, 1)` and
`(names, 2)` — the legacy family and subfamily. `fontdb`'s
`FaceInfo::families` prefers name ID 16, the *typographic* family, where a face
declares one. `NotoSansCJKjp-Regular.otf` declares both: ID 1 is
`"Noto Sans CJK JP Regular"` and ID 16 is `"Noto Sans CJK JP"`. Of the thirty
faces, it is the only one where the two disagree — and the name is not
decorative. `find_family_name_match`, `font_by_name`'s exact compare,
`match_installed`'s normalized compare and the score's 4-point length bonus all
read it, and the last is decided by `family.len() == face.name.len()`, which
eight characters settles on its own. `describe` now reads name ID 1 directly
and has lost its `families` argument with it, so it reads only the face's own
tables — which is what the module header already claimed it did.

**Zero movement, per file, on both.** No regressions, and no gains either.

That is the predicted result and it is worth stating as a result rather than as

Both fixes are paid on the strength of the oracle comparison, not on a
scoreboard number, and neither should be credited with one.

## 5. Tests added

In `crates/pdfrum-font/src/subst/db.rs`, module `face_style_bits`:

- `bold_reads_the_style_not_the_face_name` — including the negative case, a
  family whose *name* says Bold while its subfamily does not.
- `italic_takes_oblique_as_well` — the one place the port reads two words.
- `serif_is_the_face_name_containing_serif` — including the two case-sensitive
  refusals, `"PT SERIF"` and `"PT serif"`, which are ported crudeness rather
  than oversight.
- `no_face_in_the_hermetic_font_set_is_serif` — all **thirty** distinct faces
  of `test_fonts`, asserting serif, script and fixed-pitch are clear on every
  one. The whole directory is listed rather than only the eleven the old rule
  got wrong, so the test reads as a comparison against the oracle's enumeration
  rather than as a list of past failures. This is the test that would have
  caught the original divergence.
- `a_monospaced_face_takes_no_fixed_pitch_bit` — `Cousine` against `Arimo`
  under a `FIXED` pitch request, asserting the two score *equally*. Cousine is
  genuinely monospaced and its `post` table says so; the point is that the
  folder enumerator never asks.

The name-ID change has no unit test. It needs a real font file carrying both
name ID 1 and ID 16, this crate has no test-font-file fixture convention, and
depending on a path inside the oracle checkout from a unit test would make the
suite non-hermetic. The rationale is in the doc comment and the behavior is
covered by the conformance run.
