# M12d D3 — Single-image work

**Updated:** 2026-09-01 · **State:** complete.

PLAN.md §M12d D3 hands this item two documents under one heading and tells it to
rank them by measurement before touching either:

- **`image_en_fqa`** — 552 small images at ~600 ms cold *and* warm, with
  `to_pixmap` totalling **0.1 ms** across the whole document, so the cost is
  per-*image* overhead rather than per-pixel work. M12 §11 names this document
  as the proof that single-image work is where the engine is genuinely behind.
- **`image_bug_718762`** — ~403 ms left in the Adobe CMYK four-dimensional
  interpolated table (M12b-P1.md §8.2), deliberately not taken there.

Written in M12.md's register: hypothesis → A/B → verdict, **non-results
included**, and a claim a later measurement refutes is withdrawn in place.

---

## 0. Environment and measurement discipline

Same machine as M12b: AMD Ryzen 9 7950X (16 cores / 32 threads), Linux
6.8.0-138, release profile with `debug = 1`. Oracle checkout at `6f2272e`,
read-only.

**The machine is not idle.** Load average was 19.7 at the start of this item,
from unrelated jobs holding ~450% CPU that are not agents and did not clear.
M12b.md §7 records four near-false findings this week on exactly this machine.
Every number below that is presented as a result is therefore either

- an **in-process attribution** (the `walk-profile` instrument, or a temporary
  extension of it), which measures a share of one process's own work and is
  immune to what the rest of the machine is doing; or
- a **paired A/B** run by alternating two binaries built from two trees in one
  window, so contention hits both sides equally.

`ratchet update` is **not** run: that debt is M12d M1's and is gated on idle.

## 1. `image_en_fqa`: the digest was wrong about what the document is

PLAN.md D3 and M12b-P1.md §9.1 both carry a claim inherited from an earlier
digest: *"552 small images, every one a 1-bit mask minified 8.33x in both
axes."* Instrumented at the dispatch in `render_image`, on the real file, that
is wrong in three of its four parts, and getting it right is what located the
cost.

What the document actually draws, per render:

| | digest's claim | measured |
|---|---|---|
| image draws | 552 | **301** |
| what they are | 1-bit `/ImageMask` stencils | **2x2 RGB images carrying an `/SMask`** |
| minified 8.33x | of the image | **of the `/SMask`**, which is 48x85 … 1339x86 |
| arm taken | the ordinary image path | **`render_masked_image`** |

Every one of the 301 is a **2x2 base image** with a **non-co-registered
`Alpha` mask**, so `is_coregistered` is false and `render_image` hands the draw
to `render_masked_image` — `DrawMaskedImage`, `cpdf_imagerenderer.cpp:375-424`.
Destination extents run from 6.0x10.2 to 391.5x10.2 device pixels; the masks
run from 48x85 to 1339x86 samples. The 8.33x minification the digest reported
is real and it is the **mask's**, not the image's.

That single fact explains the two readings that made this document look
mysterious:

- **`to_pixmap` totals 0.1 ms** because the thing `to_pixmap` converts here is
  a 2x2 base. It was never the work.
- **`Phase::Image` reads zero calls** in the walk profile against 905
  `draw_image` device calls. `render_masked_image` is **outside** the phase
  wrapper *and* outside the `(ObjRef, PixmapRequest)` render cache M12 §9.1
  built — neither instrument nor cache reaches this arm, which is why 73.5% of
  the render fell into the profile's unattributed "INTERPRETATION" bucket.

### 1.1 The attribution

`render_masked_image` was instrumented stage by stage with a temporary
extension of the `walk-profile` instrument (an eleven-slot thread-local
accumulator around each stage of the function). `profile --op render --sample`,
`exact` backend, 10 iterations, 301 draws per iteration:

| stage | ms/iter | share |
|---|---:|---:|
| `separate_mask` — materialize the `/SMask` as an RGBA `Pixmap` | **32.7** | **32.0%** |
| `prescale` the mask — box-filter it 8.33x down | **42.6** | **41.7%** |
| `draw_image` the mask into its scratch target | 14.8 | 14.5% |
| `draw_image` the base into its scratch target | 7.0 | 6.9% |
| final `draw_image` of the composed buffer | 3.9 | 3.8% |
| `new_target` (mask) | 0.36 | 0.3% |
| `finish` + `alpha_mask` | 0.34 | 0.3% |
| `multiply_alpha_mask` | 0.29 | 0.3% |
| `to_pixmap` of the base | **0.10** | **0.1%** |
| `new_target` (base) | 0.07 | 0.1% |
| **total** | **102.2** | |

The 102.2 ms accounted for here is the whole of the render's 104.4 ms measured
at the same seam, so nothing material is outside the split.

**73.7% of this document is two functions, and both of them are the mask's.**
`separate_mask` and the mask's `prescale` process **29.8 million mask samples
per render** (301 masks, mean 98,920 samples each) at 1.10 ns and 1.43 ns per
sample respectively — rates that are memory-bandwidth-shaped rather than
arithmetic-shaped, on a four-byte-per-pixel buffer.

`to_pixmap` at 0.1 ms is exactly the figure M12b-P1.md §9.1 reported. It was
measuring the base, and the base is 2x2.

### 1.2 Caching is not the lever, and that is measured rather than assumed

The obvious response to "301 draws each redoing the same two pure functions" is
to extend M12 §9.1's cache to this arm. **It would recover almost nothing.**
Hashing every mask's sample buffer over one render finds **276 distinct masks
in 301 draws** — the document draws each mask about 1.09 times. A perfect cache
saves 8%.

This is the sharpest possible statement of M12 §10.3's residue: *M12 made
repeated image work free and left single image work exactly where it was.* The
work here has to get **cheaper**, not be **skipped**.

## 2. What the walk did with those 301 draws, and the two changes it took

`render_masked_image` is `DrawMaskedImage` (`cpdf_imagerenderer.cpp:375-424`):
the base into one device-sized buffer, the mask into a second over the same
rect through the same matrix, and a multiply. PDFium never reconciles the two
grids, and neither do we — that part is right and stays. What was wrong is
everything the mask's own pixels did on the way.

### 2.1 `separate_mask` copied a plane that already existed — 32.0% to 0.0%

`ImageMask::Alpha` **holds a coverage plane**: one byte per sample, already
decoded. `separate_mask` walked it with `alpha_at` and pushed the bytes into a
second buffer, and `alpha_at` differs from reading that buffer only in two
ways — a stencil's inversion, and what it answers past the end.

When neither applies, the plane *is* the buffer. `separate_mask` now borrows it
(`Cow::Borrowed`) and keeps the walk for the two cases that need it, with
`the_borrowed_mask_plane_is_the_walked_one` walking both arms against
`alpha_at` over a stencil, a short buffer and a long one.

It also stopped cloning the mask's whole sample array into a `Pixels::Gray8`
descriptor on every draw. Nothing reads those samples through that descriptor;
`resample_quality` asks it for two dimensions and a component count.

| | before | after |
|---|---:|---:|
| `separate_mask`, ms per render | **32.7** | **0.008** |

### 2.2 The reduction filtered four copies of one channel — 41.7% to 25.4%

Every pixel `separate_mask` built was `[a, a, a, a]`, and `prescale` then
box-filtered all four channels toward a footprint 8.3x smaller in each axis.
Only the alpha is ever read: the buffer's whole purpose is to become an
`alpha_mask()`.

`reduce_gray_to` is `reduce_to` over one channel — the same two tap tables, the
same fixed-point accumulation, the same `>> 16` — and `reduced_mask_pixmap`
expands to four channels **after** the reduction, at the destination size. The
four-channel form is never built at all.

The equality is not an argument, it is two tests. The filter is per-channel and
the four channels are equal, so
`the_gray_reduction_is_the_rgba_reduction_on_a_gray_image` asserts the
single-channel filter against the four-channel one over eight size ratios, and
`the_reduced_mask_pixmap_is_the_prescaled_expanded_one` asserts the whole
composed operation against `prescale` of the expanded pixmap, transform
included.

### 2.3 And the larger half was not in the walk at all

The walk is ~100 ms of `image_en_fqa`. Its **page-graph build is ~550 ms**, and
the `--sample` harness reports the two separately — which is why the cold
number (669 ms) and the warm number (104 ms) had looked like different
documents.

`load_mask_image` (`crates/pdfrum-page/src/image/mod.rs`) walked every mask
sample through `Pixels::color_at`, which reaches an `Rgb` of three `f32`, and
took `to_bytes()[0]` back. **That is exactly the float round trip M12b P1 §7
deleted from `to_pixmap` for -35% on the image class** — and P1's change was in
`pdfrum-render`, so it went straight past this one, which is in `pdfrum-page`
on the build path.

`Pixels::sample_bytes` is the same answer without the floats, proved
exhaustively by P1's own `the_byte_path_is_exactly_the_float_path`. Two arms
then take the index out of the loop as well: `Gray8`, which every `/SMask` in
the corpus is, copies; `Indexed` encodes its palette once through
`byte_palette`. `the_mask_planes_fast_arms_are_the_general_one` pins both
against the general arm, because the conformance corpus carries no indexed
`/SMask` and cannot see that half.

## 3. `image_en_fqa`: the A/B

Paired and alternating in one window, two binaries built from two isolated
worktrees differing only in these files, best of ten rounds of three
iterations each. **The machine carried load 20-60 throughout**, which is why
the build/warm split below — taken inside one process — is reported beside the
wall clock rather than instead of it.

| | before | after | delta |
|---|---:|---:|---:|
| **cold render** (fresh session per iteration) | **679.7 ms** | **158.7 ms** | **-76.7%** |
| of which page-graph build | 541.6 ms | 88.0 ms | **-83.7%** |
| of which warm walk | 104.6 ms | 62.3 ms | **-40.4%** |

The build and warm figures are best-of-six alternating rounds, and the two
sets do not overlap on either: build spans 541-571 before and 88-145 after;
warm spans 104-117 before and 62-70 after.

## 4. `image_bug_718762`: the brief's hypothesis, tested and refuted

D3 asks whether the ~403 ms of Adobe CMYK table work M12b P1 §8.2 left is being
spent on pixels `prescale` is about to discard — in which case "the fix is
ordering, not arithmetic".

**It is not, and the arithmetic says so exactly.** Instrumented on the real
file, the draw is 5000x5000 CMYK8 reduced to **64x64**. The reduction is an
*area average*: every destination pixel's footprint spans `5000/64 = 78.1`
source columns, and enumerating the tap tables confirms the filter reads
**5000 of 5000 source columns** and every source row. No pixel `to_pixmap`
converts is one `prescale` discards; there is nothing to reorder.

The other half of the same question — averaging *before* converting — was
already settled against by M12b P1 §8.3 on oracle evidence, and that verdict
stands: `CStretchEngine::ContinueStretchHorz` (`cstretchengine.cpp:346`)
accumulates from `CPDF_DIB::GetScanline`, which is the **already-converted**
scanline. The oracle converts every source pixel too. It simply has 1/64th as
many of them, because `CreateDCTDecoder` (`cpdf_dib.cpp:531`) hands libjpeg
`scale_denom = 8` and decodes at 625x625. **That remains the structural fix and
it remains upstream's** (`docs/upstream/zune-jpeg-scaled-decode.md`).

### 4.1 What was reachable, and it is the smaller half

`to_pixmap` reached each sample through `Pixels::sample_bytes(x, y, width)`,
which derives the buffer offset with a `checked_mul` and a `checked_add` per
sample. In front of a four-dimensional interpolated table run 25 million times,
that shows; the row walk has the index already.

Measured by clocking `to_pixmap` itself rather than the render around it, so
the reading does not depend on the machine:

| `to_pixmap` on `image_bug_718762` | best of five | range |
|---|---:|---|
| before | 409.9 ms | 409.9 - 520.0 |
| after | **367.3 ms** | 367.3 - 387.4 |

**-10.4%, with the two sets not overlapping.** It is ~42 ms of the 403 ms P1
left, and it is honestly the smaller half of that entry: the structural fix is
worth ~397 ms and is not ours to make.

`the_cmyk_fast_arm_is_sample_bytes` pins the arm against `sample_bytes` over
every sample of four buffer shapes, including one short of its declared size,
which is the one place the two index ladders could disagree.

## 5. What measured to zero, and what was refused

- **Caching the mask pixmap.** The obvious response to 301 draws each redoing
  two pure functions. Hashing every mask's samples over one render finds **276
  distinct masks in 301 draws** — a perfect cache saves 8%. Not built. §1.2.
- **Reordering `to_pixmap` and `prescale` on `image_bug_718762`.** The brief's
  own hypothesis, refuted by enumerating the tap tables: the box filter reads
  all 5000 source columns. §4.
- **`axis_taps`.** Suspected as allocation churn — 403 small `Vec`s per call,
  301 calls a render. Instrumented at **4.6 ms of the 34.9 ms** the reduction
  costs, 13% of it, so the bulk is the filter's own arithmetic and not the
  weight tables. Not pursued.
- **`adobe_cmyk_to_srgb` itself.** The genuine arithmetic left on
  `image_bug_718762`. It lives in `crates/pdfrum-page/src/color/`, which is not
  this item's to own, and M12b-P2 measured colour conversion at **<= 7.2% of the
  engine half** across the corpus — so it is not the general lever either.
  Named, not touched.

### 5.1 A claim withdrawn in place

**PLAN.md D3 and M12b-P1.md §9.1 both describe `image_en_fqa` as "552 small
images, every one a 1-bit mask minified 8.33x in both axes."** Instrumented at
the dispatch, three of those four parts are wrong: there are **301** draws, they
are **2x2 RGB images carrying an `/SMask`**, and the 8.33x minification is the
**mask's**. The count "552" is the file's image *XObject* count, not its draw
count. The digest's one correct part — the 8.33x — was correct about a buffer
nobody had looked at, and finding out which buffer is what located the cost.

M12b-P1.md §9.1's reading of `to_pixmap` at 0.1 ms was **right and its
conclusion was wrong**: it concluded the cost was not per-pixel. It was
per-pixel throughout, on the mask, which `to_pixmap` never sees.

## 6. The regression gate

**The conformance scoreboard is byte-identical after every one of the four
commits** — 1675 files, 1624 pass, 51 fail, tags `page-count 2 / pixel-fail 42
/ tierA-mismatch 9`, with no metric of any file moved. That is stricter than
the regression gate can enforce and is what a set of changes proved identical
by exhaustive test should produce.

`cargo nextest run` on `pdfrum-page` and `pdfrum-render`: **770 tests, 770
passed**, including the five equivalence tests these changes added. Clippy
`-D warnings` and `cargo fmt --check` clean on both crates.

**`ratchet update` was not run.** That is M12d M1's debt and it is gated on an
idle machine; this one carried load 20-60 for the whole item, with two
unrelated jobs at ~450% CPU that are not agents.

| **`image_bug_718762`** | `to_pixmap` **409.9 -> 367.3 ms, -10.4%**; the remaining ~360 ms is the upstream scaled decode's, and the brief's ordering hypothesis is refuted |

M12 §10.3's residue is the heading this item was given: *M12 made repeated image
work free and left single image work exactly where it was.* On `image_en_fqa`
that residue is now paid, and it was paid by making the work cheaper rather
than by skipping it — which is what a document with 276 distinct masks in 301
draws leaves as the only option. On `image_bug_718762` it is not paid, the
reachable part is taken, and the part that is not reachable is named with the
arithmetic that says why.
