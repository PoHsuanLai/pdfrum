## 2. The items

### 2.1 A11 — single-function `/TR` with `OutputCount() > 16`

**Verified at the line.** `cpdf_docrenderdata.cpp:130-143`, quoted from the
pin:

```cpp
  } else {
    for (size_t v = 0; v < CPDF_TransferFunc::kChannelSampleSize; ++v) {
      float input = static_cast<float>(v) / 255.0f;
      if (pFuncs[0]->OutputCount() <= kMaxOutputs) {
        pFuncs[0]->Call(pdfium::span_from_ref(input), output);
      }
      size_t o = FXSYS_roundf(output[0] * 255);
```

The guard covers the `Call` and not the read below it. `OutputCount()` is
loop-invariant, so when it exceeds 16 the guard fails on all 256 iterations and
`output[0]` is never written — the curve is all-black. The **array** branch
twelve lines above meets the identical condition correctly:

```cpp
        if (pFuncs[i]->OutputCount() > kMaxOutputs) {
          samples[i][v] = v;
          continue;
        }
```

`samples[i][v] = v` is the identity. Two branches of one function, same
condition, opposite answers — which settles it as an oversight rather than a
policy.

**Spec:** §8.6.5.9. §7.10.1 requires clipping to `/Range`; nothing sanctions
blacking a channel out because its function is unusable.
**pdf.js:** no equivalent — transfer functions are built per array element with
no output-count cap (`evaluator.js:944-959`), so the case cannot arise. Stated
rather than read as agreement, per §4's discipline.

**Ruling: no action — already correct.** `crates/pdfrum-page/src/transfer.rs:51-66`
already carries the `[oracle-bug]` label with both citations and
`MAX_OUTPUTS: usize = 16` with identity on both paths.

**On the premise.** I was asked to verify rather than accept that this decline
was "clearly wrong". It is wrong as a *decline*, and the audit already says so
— but the work is done: §8's first tranche relabelled it in `e75a834`/`a2464fc`/
`4ff2908`. So the answer is not "overturn and implement" but "already
overturned, already implemented". The same is true of A23 and A24. **Three of
the eleven items were closed before this pass began**, which is worth saying
plainly: the audit's §1 table still carries the "already declined" label on all
three, and that label is now stale in §1 even though §6 and §8 correct it.

### 2.2 A23 — the mesh bbox helper's mutated loop invariants

**Verified.** `cpdf_streamcontentparser.cpp:94-123`: `point_count` and
`color_count` are set once from the shading type (`:94-109`), then inside
`while (!stream.IsEOF())`:

```cpp
    if (!bGouraud && flag) {
      point_count -= 4;
      color_count -= 2;
    }
```

The subtraction mutates the variables that *are* the record shape, so it is
cumulative: after the first flagged patch every later patch under-reads by
four points, after the second by eight, and the counts run to zero and below.
PDFium's own second copy of the loop — `cpdf_rendershading.cpp:900-917` — uses
per-iteration `iStartPoint`/`iStartColor` against an untouched `point_count`,
which is correct.

**Spec:** §8.7.4.5.5-7 give the bbox no licence to omit a declared control
point. **pdf.js:** no counterpart (canvas-backed, needs no bbox helper), so the
oracle's own renderer is the independent reading.

**Ruling: no action — already correct.**
`crates/pdfrum-page/src/shading/mesh.rs:433-449`.

### 2.4 A15 — the zero-length dash substitution

**Verified.** `cfx_agg_devicedriver.cpp:367-373`:

```cpp
    for (float dash_len : dash_array) {
      if (dash_len <= 0.000001f) {
        dash_len = 0.1f;
      }
      dash.add_dash(fabs(dash_len * scale));
```

The test is `<= 0.000001f`, so it catches a genuine **zero** along with
negatives. (PDFium patched AGG to a single-argument `add_dash`, so each entry is
one segment and an odd array cycles — `third_party/agg23/0017-support-odd-size-dash-arrays.patch`.)

**Spec:** §8.4.3.6 — a zero-length dash is a **dot** under a round or
projecting-square cap and **nothing** under a butt cap. A 0.1-unit segment is
neither shape. **pdf.js:** hands the array to the canvas unchanged
(`canvas.js:1126-1131`, `setLineDash(dashArray)`), reaching §8.4.3.6's answer by
delegation, since HTML Canvas has the identical rule.

#### The audit names the wrong fixture, and the right one is remarkable

The audit charges A15 "≥2 rows (`dashed_lines`)". I scanned every `.pdf` and
`.in` under `testing/corpus` and `testing/resources`, decompressing content
streams and parsing every `d` operator (42 files carry a dash array):

- **zero-length entry: exactly 1 file** — `corpus/fx/path/bug_0_length_line.pdf`
- **negative entry: 2 rows** — `resources/pixel/dashed_lines.{in,pdf}`, arrays
  `[6 5 -4 3 2 1]`

`dashed_lines` has **no zero entry at all**. It hits the *negative* branch,
which is a different question (see below). So the audit's fixture citation and
its row count are both wrong: **1 row, and a different file.**

That file is the oracle's own regression fixture for exactly this case, and it
argues the specification against PDFium in its own page text. It draws
`[0 10] 0 d` under `0 J`, `1 J` and `2 J` at a 10-unit line width and labels
them, in visible text on the page: **"Butt Cap; no Output"**, "Round Cap",
"Projecting square Cap". Its comments even record that Adobe and Foxit
disagree about `[10 0]`.

Rendering it with the pinned oracle and counting pixels on each line:

| line | oracle: dark px | oracle: any non-white | §8.4.3.6 says |
|---|---|---|---|
| `0 J` butt `[0 10]` | 0 | **20**, at RGB 229-230 | nothing |
| `1 J` round `[0 10]` | 202 | 202 | a dot |
| `2 J` square `[0 20]` | 102 | 110 | a dot |

So the oracle **does** paint where its own fixture says "no Output" — a
200-pixel band at ~10% opacity, 0.057% of the page. The round and square lines
happen to look right, because a 0.1-long segment under a round cap is
visually almost the circle the spec asks for. The defect is real but small,
and confined to the butt-cap case.

#### Why this is nevertheless a decline: the fix is unreachable

I implemented the narrowest faithful fix — substitute for negatives only, let a
genuine zero reach the rasterizer, and let the cap draw it — with the
`[oracle-bug]` label, both citations, and four tests. Unit tests passed,
including a geometry test asserting `area == 0` under butt and `area > 100`
under round and square. **The pixel measurement refuted it.**

Rendering the fixture before and after, and counting non-white pixels per line
in the band the change touches (y 241-310, and nothing else on the page moved):

| line | oracle | pdfrum before | pdfrum **after the fix** |
|---|---|---|---|
| `0 J` butt `[0 10]` | 20 | 20 | **0** ✓ |
| `1 J` round `[0 10]` | 202 | 202 | **20** ✗ |
| `2 J` square `[0 20]` | 110 | 110 | **10** ✗ |

The butt case became correct. The round and square cases **collapsed to a
single dot each**. Inspecting the pixels shows the oracle drawing ~10 dots
beginning at x=25, and the patched pdfrum drawing one dot at x≈117.

The mechanism, isolated:

```
kurbo dashes [0.0, 10.0] over a 200-unit line, round cap:  subpaths = 2
kurbo dashes [0.1, 10.0] over the same line, round cap:    subpaths = 20
```

`kurbo`'s dasher emits a subpath only where it accumulates non-zero length, so
**18 of 20 zero-length dashes are dropped** before any cap is applied. The two
survivors are the path's own endpoints. My geometry test passed on exactly
those two, which is why it did not catch this: the test measured area, and two
dots have area.

SSIM against the golden moves **0.999905 → 0.981354**, below the 0.99 floor —
but the row loss is not the reason to decline. The reason is that the change
**does not produce the correct behaviour**. It trades a small, wrong artefact
(a faint sliver where nothing belongs) for a large, wrong one (nine of ten dots
missing). SPEC §12 asks for the narrowest faithful fix; this one is not
faithful.

**Ruling: DECLINE — unreachable from our architecture.** This is the decline
category the brief allows, not the forbidden one: the behaviour is genuinely
wrong and I am not defending it, and the cost is not why. Reaching §8.4.3.6
would require the engine to expand zero-length dashes into explicit cap
geometry itself — synthesising a degenerate subpath per dash position rather
than delegating to `kurbo::stroke` — which is a dash-generator of our own, in
the one place the design deliberately shares geometry between both backends
(`stroke.rs`'s whole reason for existing, design brief §6.1). That is a real
project, and it buys 200 pixels at 10% opacity on one corpus file.

**What a future agent must build**, if it is ever revisited: replace the
`Dashes`-to-`kurbo` handoff in `normalize_dashes`/`resolve_stroke` with an
engine-side dash walker that emits, per dash position, either a real segment
(non-zero length) or a zero-length subpath the rasterizer will cap. Both
backends must receive identical geometry, so it belongs in `pdfrum-render`,
not in either raster crate. Verify against `bug_0_length_line.pdf` line by
line, against the table above — the fixture's own text labels are the
acceptance criteria.

**Correction to the audit** (§1 row A15 and §3's A15 paragraph, and §7 item 15):
the fixture is `corpus/fx/path/bug_0_length_line.pdf`, not `dashed_lines`; the
count is 1 row, not ≥2; and `dashed_lines`'s dash defect is the **negative**
entry, which is a separate and legitimate ROBUSTNESS case — §8.4.3.6 requires
non-negative elements and gives a negative one no meaning, so recovering it is
unspecified and matching the oracle is the tie-break, exactly as A16.

### 2.5 A25 — the DCT decoder items

Four sub-items. **The audit is wrong on the one it calls a bug**, and misses a
real defect.

**(a) Scaled decode refused for non-MCU-aligned images.**
`libjpeg_scanline_decoder.cpp:126-157`:

```cpp
  if (orig_width_ % (max_h_samp * DCTSIZE) != 0 ||
      orig_height_ % (max_v_samp * DCTSIZE) != 0) {
    // Reset to 1 (no reduction).
    scale_denom_ = 1;
  }
```

with the comment citing `crbug.com/890745`. This is deliberate correctness:
reduced decode cannot crop encoder edge padding back out. **Not a bug.**
pdfrum has no scaled-decode path at all, so it is unobservable —
`allows_reduced_resolution` (`dct.rs:101-105`) is a dead re-export.
**Ruling: DECLINE. 0 rows.** Worth filing separately that the dead
re-exports (`allows_reduced_resolution`, `scale_denominator`, `scaled_size`,
`ADOBE_CMYK_DECODE`) should be deleted or wired up.

**(b) 4-component JPEGs never channel-reduced.** `:121-123` touches only
3-component images. pdfrum already pins `ZColorSpace::CMYK` for 4 channels
(`dct.rs:144-146`) and **must**, because `zune-jpeg` otherwise emits RGB and
the image is rejected on component mismatch. So this is not a
performance-only difference; it is already implemented and load-bearing.
**Ruling: DECLINE — already correct. 0 rows outstanding.**

**(c) "PDFium treats *any* Adobe marker as transformed, ignoring the transform
byte."** **This is a misreading, and the row should be struck.**
`libjpeg_scanline_decoder.cpp:117-119` sets `jpeg_transform_ = true` on
`saw_Adobe_marker`, but `jpeg_transform_` is used at exactly one place —
`:121`, deciding whether to pin a **3-component** image's output space. The
transform byte is honoured one layer down, in
`third_party/libjpeg_turbo/src/jdapimin.c:185-198`:

```c
  case 4:
    if (cinfo->saw_Adobe_marker) {
      switch (cinfo->Adobe_transform) {
      case 0:  cinfo->jpeg_color_space = JCS_CMYK;  break;
      case 2:  cinfo->jpeg_color_space = JCS_YCCK;  break;
```

PDFium even reads the derived space back at `:364-365`. pdf.js honours the
byte at `jpg.js:1292-1296` (`!!this.adobe.transformCode`); `zune-jpeg` honours
it at `headers.rs:496-508`. **All three agree, and there is no oracle bug
here.** **Ruling: DECLINE — the premise is false.**

**(d) CMYK inversion in the colour space rather than the decoder.**
`cpdf_devicecs.cpp:104-136`. §7.4.8 mandates no inversion; it is expressed
through `/Decode`, which is what both PDFium and pdf.js do
(`jpg.js:1275-1279` skips inversion when `_isSourcePDF`). pdfrum matches, in
`image/mod.rs:901-935`. Pure code organisation, unobservable.
**Ruling: DECLINE. 0 rows.**

**Measured cost.** The audit says 6 rows. Scanning all 1757 rows and decoding
filter chains (`bug_1646` hides its JPEG three filters deep), **153 files
reference `/DCT` and exactly 4 rows carry a 4-component JPEG**:

| row | APP14 transform | status |
|---|---|---|
| `corpus/fx/other/1.pdf` | **2 (YCCK)** | **SSIM 0.99491, `max_channel_diff: 255`** |
| `resources/bug_1646.pdf` | 0 (CMYK) | 1.0 |
| `resources/pixel/bug_718762.pdf` | 0 (CMYK) | 1.0 |
| `resources/pixel/bug_718762.in` | 0 (CMYK) | 1.0 |

Rows hitting the audit's alleged bug: **0**, because it does not exist.

#### The defect the audit did not find: pdfrum drops every YCCK image

Running `zune-jpeg` 0.5.15 exactly as `decode_dct` does:

```
jpeg from corpus/fx/other/1.pdf: input_cs=YCCK
   DECODE ERR "Unimplemented colorspace mapping from YCCK to CMYK"
bug1646.jpg:                     input_cs=CMYK  -> OK 5000x5000 comps=4
```

`zune`'s `worker.rs:63-82` implements `(YCCK, RGB)` and `(YCCK, RGBA)` only;
`(YCCK, CMYK)` falls through to the error arm. So the `output_space` pin from
(b) — added to make the CMYK cases work — **breaks every YCCK image**, which
returns `Error::CodecRejected` and is silently dropped. That is the
`max_channel_diff: 255` on `corpus/fx/other/1.pdf`. PDFium renders it correctly
through libjpeg's `ycck_cmyk_convert`; pdf.js renders it too.

**Ruling: IMPLEMENT — but as a new item, not as A25.** 1 measured failing row.
**What the next agent must build:** after `decode_headers()`, detect
`input_colorspace() == YCCK` and decode to raw components, applying the
YCCK→CMYK transform in pdfrum to match libjpeg's `ycck_cmyk_convert`. Do
**not** take `zune`'s YCCK→RGB path: its baked-in composite bypasses `/Decode`
and the colour space, and `/Decode` is where the CMYK inversion must happen per
(d). The `Adobe_transform == 0` path is load-bearing — `bug_1646` and
`bug_718762` score 1.0 today and must not regress.

### 2.6 A71 — the content generator's colour loss

**This is the item the brief singled out, and its stated reasoning does not
survive contact with the harness.**

**Verified at the line.** `cpdf_pagecontentgenerator.cpp:64-78`:

```cpp
bool WriteColorToStream(fxcrt::ostringstream& buf, const CPDF_Color* color) {
  if (!color || (!color->IsColorSpaceRGB() && !color->IsColorSpaceGray())) {
    return false;
  }
```

consumed at `:819-824` with ` rg ` / ` RG `. Note that the refusal is *only*
this gate: `CPDF_Color::GetRGB()` at `cpdf_color.cpp:116-127` delegates to
`cs_->GetRGB(buffer)` for **any** colour space, so the machinery to convert
CMYK, ICCBased, Separation or Lab to RGB is present and simply not reached.
pdfrum reproduces it exactly (`emit.rs:147-168`, `expressible_rgb`).

**Spec:** §8.6 defines every colour space the emitter drops.
**pdf.js:** does not regenerate page content, so it is silent here (§4).

#### The reasoning, examined

The audit's recommendation reads:

> keep reproducing: Tier-B compares our regenerated page against *the oracle's
> regenerated page*, so implementing the other colour spaces would score as a
> regression against the thing we are measured on.

**Tier-B does not compare regenerated pages, and the oracle cannot produce
one.** Three findings, each at the line:

1. **`pdfium_test` has no save flag.** `conformance/src/saveroundtrip.rs:6-8`
   states it outright: *"the oracle cannot write a document at all, so there is
   no like-for-like invocation to diff (SPEC.md §11's ruling E7)."* There is no
   such thing as "the oracle's regenerated page". The object the audit says we
   are measured against does not exist.

2. **Tier-B compares our render against a golden of the *original*.**
   `compare_tier_b` (`conformance/src/run.rs:339-361`) walks
   `*.png` goldens, which `oracle.rs` produced from the unmodified input.
   `saveroundtrip.rs:34-36` is explicit that regeneration is not in that path:
   *"an ordinary save regenerates nothing, so every file in this sweep is
   expected to hold its original's fidelity exactly."*

3. **The sweep that *does* regenerate compares two renders of the same file,
   and is not on the board.** `conformance/src/mutation.rs:12-17` — the
   comparison is *"between two renders of the same mutated file: the oracle's
   and ours"*. And `:41-44` answers the audit's worry directly:

   > *"A regenerated page's **content** losses do not enter into it, because
   > both sides are reading the same regenerated bytes — whatever the emitter
   > dropped, it dropped for both."*

   That is the exact inverse of the audit's claim. Emitting richer colour
   would be read by **both** renderers, so it cannot score as a regression;
   if anything it raises fidelity on both sides equally. The sweep is also a
   separate command (`mutate-round-trip`, `main.rs:230`), not part of the
   1757-row board, whose rows carry only `tierA`/`tierB` fields.

**Measured cost: 0 rows.** Confirmed against the scoreboard schema: no row has
a mutation field, and the emitter is never exercised by `conformance run`.

**Ruling: OVERTURNED — the decline rests on a false premise.** The behaviour
is a real fidelity loss (§8.6 defines the spaces; a CMYK fill silently becomes
black), it costs nothing to fix, and the argument that protected it —
"fixing it would look like a regression on our own scoreboard" — is both the
kind of argument the oracle-bug rule exists to override *and*, here, factually
untrue.

**What to implement.** `expressible_rgb` in
`crates/pdfrum-edit/src/content/emit.rs:147-168` should convert any colour with
a known space to RGB and emit `rg`/`RG`, rather than returning `None` for
everything but `DeviceRGB`/`DeviceGray` — mirroring `CPDF_Color::GetRGB`'s own
delegation to `cs_->GetRGB(buffer)`, which is the conversion PDFium already has
and declines to call. Patterns must keep returning `None`: a pattern paints
through a resource no `rg` can name, and that is a genuine limit rather than an
oversight. Carry the `[oracle-bug]` label with `cpdf_pagecontentgenerator.cpp:65`
and §8.6, stating at the site that pdf.js does not regenerate content and so is
silent. The module docs at `content/mod.rs:8-19` and `emit.rs:11-19` assert the
loss is required for comparison and must be corrected in the same change —
they are the written form of the false premise.

I did not implement it here: it belongs to `pdfrum-edit`, which the concurrent
agent is touching, and it changes the emitter's contract rather than one
expression. It is the highest-value item in this document — zero cost, real
fidelity, and a reasoning error retired.

### 2.7 A45 — `CountRects` splits per text object

**Verified.** `cpdf_textpage.cpp:465-467` — the only split rule:

```cpp
    if (text_object != charinfo.text_object()) {
      rects.push_back(rect);
      text_object = charinfo.text_object();
      is_new_rect = true;
    }
```

No adjacency, baseline or font-size test exists. `Union` at `:477` accumulates
within one object.

**Spec:** §9.10 says nothing — `CountRects` is a PDFium API with no ISO basis.
**pdf.js:** no rect-count API (§4). So neither of the rule's two authorities
speaks to it; the case rests entirely on the oracle's own TODO.

**The TODO, read in full** (`fpdf_text_embeddertest.cpp:2210-2212`):

> `TODO(crbug.com/40448046): The PDF uses fonts [/F2, /F1, /F2, /F1] with a
> constant size on a single line. FPDFText_CountRects() should merge the text
> into 4 rects.`

followed by 12 literal rects. So the intended predicate is: **merge adjacent
text objects that share a font and size on a common baseline** — four font runs
across twelve objects.

**Measured cost: 0 rows, not 2.** `pdfium_test` has no rect flag (verified
against `--help`: only `--txt` and `--annot` emit text data), so `CountRects`
is never scored. Both `bigtable_mini` rows pass on text/metadata/pageinfo
dumps that never touch it.

**Ruling: DEFER.** Not a decline — the behaviour is wrong by upstream's own
statement and costs nothing to change. But the audit's warning is right that
the predicate must be *designed*, and ruling "implement" obliges me to specify
it, so here it is:

> **Merge two adjacent rects when all four hold:** the two objects' resolved
> font is the same object; their font size is equal within `kSizeEpsilon`;
> their baselines are equal within `kSizeEpsilon`; and the horizontal gap
> between the left object's right edge and the right object's left edge is
> non-negative and no greater than one space advance in that font at that size.
> Otherwise split, as today.

The fourth clause is the one that must be validated rather than assumed: the
`bigtable_mini` rects overlap slightly (`22.2230` then `21.9279`), so the gap
test must admit small negative gaps, and the acceptance criterion is that the
twelve rects above collapse to exactly four. I am not implementing it because
that validation is the whole task and needs the rect data end to end, not
because it is expensive — it is a half-day with a clear target.

### 2.9 A41 + A42 — the soft-hyphen sentinel

**Verified.** `cpdf_textpage.cpp:1339-1362`, the `kHyphen` arm:

```cpp
      CharInfo& charinfo = temp_char_list_.back();
      temp_text_buf_.Delete(temp_text_buf_.GetLength() - 1, 1);
      charinfo.set_char_type(CharType::kHyphen);
      charinfo.set_unicode(0x2);
      temp_text_buf_.AppendChar(0xfffe);
```

`IsHyphenCode` (`:1149-1151`) recognises the real U+00AD on input and then
discards it for two invented values. The sentinel is *specifically exempted*
from the filter that would remove it — `IsControlChar` (`:134-147`) returns
`char_info.char_type() != CharType::kHyphen` for both `0x2` and `0xfffe`.

**The noncharacter reaches interchange.** `GetPageText` (`:590`) slices
`text_buf_` and `fpdf_text.cpp:341-372` `FPDFText_GetText` copies it to the
caller verbatim. Unicode §23.7 permits noncharacters as *internal* sentinels
but forbids them in interchange; a C ABI entry point in a public header is
interchange under any reading. `FPDFText_GetUnicode` (`:68-77`) likewise
returns `0x2` with no mapping back.

**The asymmetry is the load-bearing fact.** `cpdf_linkextract.cpp:154-155`:

```cpp
    // Replace the generated code with the hyphen char.
    strBeCheck.Replace(L"\xfffe", L"-");
```

while `cpdf_textpagefind.cpp:209-211` takes `GetAllPageText()` as its corpus
and `:262` does a plain `Find` with no repair — and U+FFFE is not in its
separator set (`:250`, `:284`). Same buffer, same sentinel, repaired in one
consumer and not the other.

**Spec:** §9.10 mandates nothing about hyphenation or sentinels; it is about
mapping codes to Unicode, and neither U+0002 nor U+FFFE is a character the
document contains. **pdf.js:** `unicode.js:51-62` maps U+00AD to U+002D and
maps the whole Specials block (0xfff0-0xffff) to 0, so it will not emit a
noncharacter at all; the join is a reversible query-time transform
(`pdf_find_controller.js:131`, `:296-306`).

pdfrum reproduces both, and reproduces the asymmetry itself:
`pipeline.rs:923-926` writes both values; `links.rs:81-83` repairs;
`find.rs` contains no occurrence of `FFFE`, `0x2`, `00AD` or `hyphen`.

**Measured cost — the audit is wrong in both directions.** The goldens are
written from the **char list** (`testing/pdfium_test/write.cc:364-366` loops
`FPDFText_GetUnicode`), so `.txt` goldens pin **U+0002** and **never U+FFFE**
(`grep -rl $'\xef\xbf\xbe'` over all golden dirs: 0 files). Grepping the golden
store for U+0002 and mapping through each `manifest.json`:

| half | audit | measured |
|---|---|---|
| **A41 buffer side** (U+FFFE → U+00AD) | — | **0 rows** — no golden captures the text buffer |
| **A41 char side** (U+0002 → U+00AD) | 3 rows | **12 rows**, 11 currently passing |
| **A42** (repair the sentinel in find) | 2 rows | **0 rows** — no golden records search results |

The 12: `bug_431824298`, `bug_650`, `bug_781804`, `bigtable_mini`, `bug_1029`,
`weblinks_across_lines`, `example_046`, `en_uicase_`, `en_uicase_2_`,
`3bigpreview` (already failing), plus `.in` variants.
`control_characters.pdf` is a false positive — its content stream is literally
`(Hello\2\3, world!) Tj`, so its U+0002 is document content.

**A42 — OVERTURNED, implement.** Zero rows. The "matches upstream" defence is
unavailable in an unusually strong form: **upstream does not match itself.**
PDFium applies the repair in `cpdf_linkextract.cpp:154` with the comment

`cpdf_textpagefind.cpp:262`, over the same buffer. There is no coherent

*What to implement:* in `crates/pdfrum-text/src/find.rs`, repair `\u{FFFE}` in
the search corpus before matching, mirroring `links.rs:83` — the same repair,

**A41 — DECLINE as scoped.** Not because the sentinel is defensible: it is a

### 2.10 A76 — auto font size floor and multiline ceiling

**Verified.** `cpvt_variabletext.cpp:31-33` is the 25-step ladder
(`{4, 6, 8, 9, 10, 12, 14, 18, 20, 25, 30, ... 144}`), and `:849-876`:

```cpp
  size_t span_size = IsMultiLine() ? kQuarterSize : kFullSize;   // 6 : 25
  auto font_span = pdfium::span(kFontSizeSteps).first(span_size);
  auto it = std::lower_bound(font_span.begin(), font_span.end(), kUnusedValue,
      [this](uint8_t font_size, bool) { return !IsBigger(font_size); });
  if (it == font_span.end()) { return static_cast<float>(font_span.back()); }
  if (it == font_span.begin()) { return static_cast<float>(*it); }
  return static_cast<float>(font_span[it - font_span.begin() - 1]);
```

`lower_bound` with `!IsBigger` returns the first size that **overflows**, so
the interior case correctly returns the largest that fits. The audit's reading
of both boundaries is **confirmed**: `it == begin()` means every step
overflows and returns 4pt anyway; and multiline never looks past index 5, so
`end()` returns 12 — a *structural* ceiling, not a clamp.

**Spec:** §12.7.3.3 — a size of 0 means the size "shall be computed as a
function of the height of the annotation rectangle". It states no minimum, no
maximum, and no ladder. So **the ladder is spec-legal** (quantising is still a
function of the height), the **12pt ceiling is spec-legal but poor** (a
saturating function of the height), and only the **4pt floor is arguably
non-conforming** — and even then weakly, since the function is unconstrained.
**pdf.js:** continuous, `min(height / LINE_FACTOR, width / textWidth)`
(`annotation.js:2704-2709`), growing `numberOfLines` for multiline
(`:2746-2758`), no floor and no ceiling. Note pdf.js has **no "nothing fits"
branch at all** — there is nothing to copy for the floor case.

pdfrum reproduces all three faithfully (`crates/pdfrum-doc/src/vt/autosize.rs:32-56`,
ladder at `vt/mod.rs:70-73`), documents both boundaries as deliberate, and
pins them with two tests.

**Measured cost: 0 rows for both boundaries — and the audit cites the wrong
fixture family.** All 14 `text_form*` rows carry an **explicit** `/DA` size
(`/F1 12 Tf`, `/TT0 16 Tf`, `/F1 -12 Tf`) and therefore **never auto-size**.
Sweeping the corpus for genuine size-0 `/DA`: 48 occurrences in 46 files; the
non-XFA `/Tx` widgets among them all carry `/Ff 29360128` (bits 23-25, **not**
the multiline bit 4096) and `/Rect [1 1 199 199]` — a 198×198pt box, nowhere
near the 4pt floor and out of reach of the 12pt cap. A direct conjunction test
for "size-0 `/DA` **and** `/Ff` with bit 4096" returns **0 files corpus-wide**:
**no multiline auto-sized field exists anywhere in the corpus.** The only two
tiny size-0 boxes (`344775293.pdf` 15×15, `bug_861842.pdf` 20×20) are
`/FT /Btn` checkboxes that never lay out variable text.

**Ruling: DECLINE — spec-legal and unreachable.** Both boundaries are within
§12.7.3.3's latitude, neither is reachable on any fixture, and both are
faithfully reproduced with accurate comments and deliberate tests. This is the
"genuinely correct-or-arguable" limb, not the cost limb: I would rule the same
way at zero cost, because a quantised ladder's honest analogue of pdf.js's
continuous behaviour at the bottom end *is* "the smallest rung, accepting
overflow" — a renderer must draw something, and clipping is the appearance
stream's `/BBox` job, not the sizer's.

If it is ever revisited, only the ceiling has substance: delete the
`multi_line` span restriction at `autosize.rs:36-41` and always search the full
ladder, since `is_bigger` already measures wrapped multi-line layout and the
cap is redundant with the real constraint. Do **not** substitute a larger
constant — there is no principled value.

**Corrections to the audit:** A76's cost is **0 rows, not ≥14**, and the
`text_form*` citation is the wrong fixture family. Separately, §6 note 1 is
confirmed correct — `docs/design/pdfrum-doc.md:1853-1861` and `:3814-3815`
still describe D16's pre-2026-08-29 inverted-predicate reading as intended,
and D16's test prescription ("a plate that exactly fits step `k`, asserting the
chosen size is step `k-1`") would, if implemented, **re-introduce the bug that
was fixed**. That is a live hazard in a design doc, not just a stale note.

### A methodological note

The audit's cost column counts rows that *use* a feature rather than rows that
*hit* a bug, and it flags this itself. Measured here, that distinction changed
the answer **six times out of nine** — five times downward (A15 2→1, A25 6→4,
A45 2→0, A46 4→0, A76 14→0, A42 2→0) and once sharply **upward** (A41 3→12).
The upward case is the important one: the caveat is usually read as "the real
cost is lower", and A41 shows it cuts both ways. Two of the downward
corrections (A45, A46) share a single mechanical cause worth stating once:
**`pdfium_test` exposes no flag for the API in question**, so the feature is
structurally unscoreable, and any audit row whose behaviour is reachable only
through an unexposed public API is 0 rows by construction. `CountRects` and
`FPDFLink_GetTextRange` are both in that class.
