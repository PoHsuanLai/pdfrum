## The exit criterion

PLAN.md §6 asks for `--txt` Tier-A byte-exact on **≥ 98% of the corpus**, and
SPEC.md §9's 2026-08-29 ruling settles which 98%: the **non-empty** rate, over
the 960 page dumps that actually hold characters, rather than the raw rate
that a tool emitting nothing already scores 47.6% on.

| Metric | M1 baseline | M2 |
|---|---:|---:|
| `--txt` pages compared | 1832 | 1832 |
| byte-exact | 872 | **1813** |
| rate | 47.6% | **99.0%** |
| non-empty pages | 960 | 960 |
| non-empty byte-exact | 0 | **941** |
| **non-empty rate** | **0%** | **98.0%** |

**Met.** The M1 baseline's 872 were all bare-byte-order-mark goldens matched
by a tool that emitted nothing; the non-empty column is the honest one, and it
went from nothing to 98.0% in this milestone.

The rare-value canaries are covered: of the 19 goldens holding `U+0002`
(the soft-hyphen sentinel) or `U+0000` (the character-code-zero passthrough),
all but the ones blocked on CFF outlines now match, and both paths are pinned
by tests over the fixtures the oracle's own embedder tests use.

## What the milestone built

- **`pdfrum-cmap`** — the predefined CJK CMap tables as a committed blob plus
  the embedded-CMap parser.
- **`pdfrum-type1`** — PFB/PFA containers, `eexec`, charstrings, Multiple
  Master.
- **`pdfrum-font`** — encodings, `/ToUnicode`, the three glyph ladders,
  substitution and fallback, the glyph cache.
- **`pdfrum-page`** — the content interpreter and the page-object graph, which
  text extraction consumes (it was M3's crate on paper; text needs it, so it
  landed here).
- **`pdfrum-text`** — the whole of `core/fpdftext/`: reading order, generated
  spaces, line breaks, hyphenation, bidi, `/ActualText`, search and link
  detection. Status: `docs/status/pdfrum-text.md`.
- **`pdfrum-tool --txt`** — the UTF-32LE per-page emitter, plus the
  `/Contents` assembly the tool needed to reach a page graph at all.

## What the text tier taught the rest of the tree

Three defects surfaced *only* because Tier-A text is byte-exact, and all three
were in other crates:

1. **`pdfrum-page` loaded a fresh `Font` per `Tf`.** Text extraction's
   duplicate suppression compares font identity, so it never fired and every
   double-drawn page extracted twice. Fixed with a font-instance cache keyed
   on the resource reference. Rendering would have shown nothing wrong.
2. **`pdfrum-font` reported no metrics for an unmapped code.** PDFium borrows
   the space's, which is what keeps a run of unmappable codes from collapsing
   to a zero-width text object that extraction then drops whole.
3. **`pdfrum-font` returns no glyph box for a CFF-flavoured face**, which is
   the remaining text failure cluster and will be a *rendering* failure too.

That is the argument for the tiering in PLAN.md §5 working as intended: a
byte-exact tier catches what a perceptual one cannot.
