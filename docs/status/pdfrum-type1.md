# `pdfrum-type1` status

**Updated:** 2026-08-29 · **State:** implemented, all gates green

Fifth library crate of M2. Contract: SPEC.md §6; behavior:
`docs/design/pdfrum-font.md` §1.16 and §3.6.

## The OQ-2 finding — what the pinned `read-fonts` actually has

The font brief escalated OQ-2 as *blocking this crate's existence*: does
`read-fonts 0.43.3` — the version DEPS.md pins — expose `ps::type1`, or is that
module only on the unreleased branch PDFium's own skrifa bridge builds against?

**It is in the release, and it covers more than the brief expected.** Verified
by reading
`~/.cargo/registry/src/index.crates.io-*/read-fonts-0.43.3/src/ps/` and by
running it against both Foxit fixtures:

| §1.16.2 item | in `read-fonts 0.43.3`? |
|---|---|
| 1. PFB / PFA / bare container sniffing | **yes** (`RawDicts::new`, `decode_pfb_tag`, `find_eexec_data`) |
| 2. eexec + charstring ciphers, `lenIV` | **yes** |
| 3. PostScript-ish tokenizer for both dictionaries | **yes** |
| 4. Type 1 charstring interpretation → outlines | **yes**, incl. `seac`, `flex`, hint replacement, `div` |
| 5. **Multiple Master** | **partial — and the missing half is the load-bearing one** |
| 6. glyph names → gid, AGL charmap | **yes** |

Item 5 is where it stops. `read-fonts` *honours* a Multiple-Master font: it
parses `/WeightVector` and implements the blend othersubrs 14–18
(`cs.rs::handle_mm_blend`), so it renders both Foxit faces correctly at the
weight vector the file ships with. What it has no way to do is **instantiate at
a different point in design space**, which is the only reason PDFium loads
these fonts at all:

- `Type1Font::weight_vector` is a private field with no setter and no
  `with_coords`-style constructor.
- `/BlendAxisTypes`, `/BlendDesignPositions` and `/BlendDesignMap` — the three
  declarations that define what a design coordinate *means* — are not parsed.
  There is no axis metadata to ask for.
- The escape hatch of implementing the public `CharstringContext` trait over
  their font with an overridden `weight_vector()` does not work either: the
  trait's other methods must hand back charstring and subroutine **bytes**, and
  `Type1Font` exposes no accessor for them.

PDFium's `AdjustVariationParams` (`core/fxge/cfx_face.cpp:1561`) is *entirely*
design-coordinate driven — it reads each axis's min/default/max, sets the
weight axis from the substitution font's weight, and solves for the width axis
by probing the advance width at both ends and interpolating. None of that is
reachable through 0.43.3's public surface.

**So OQ-2 resolves to option 1: first-party, complete.** Recorded as a `[spec]`
amendment to SPEC §6 in the implementing commit.

`read-fonts` remains a dependency, for two things it genuinely owns and we
would otherwise be copying tables for:

- **`ps::agl`** — the Adobe Glyph List, behind the `agl` feature, which is what
  synthesizes the Unicode charmap from glyph names. §3.6 explicitly preferred
  this over duplicating the AGL into `pdfrum-common`.
- **`ps::encoding::PredefinedEncoding`** — the Standard, Expert and
  ISO-Latin-1 vectors. `StandardEncoding` in particular is not optional: `seac`
  names its two components by *`StandardEncoding`* code regardless of the
  font's own `/Encoding`, and getting that table wrong silently swaps accents.

And `ps::type1` earns a third role it is unusually well suited to: **the
differential test oracle** (see below).

### The behaviors that mattered most

- **First declaration wins — and this is the bug the whole crate turned on.**
  A Multiple-Master preamble ends with a `makeblendedfont` procedure, shipped
  as PostScript source for a real interpreter's benefit, whose *body* names
  `/BlendAxisTypes`, `/FontName` and `/WeightVector` as operands. A reader
  taking the last occurrence parses the real declarations correctly and then
  wipes them — which is exactly what both Foxit faces did to the first draft
  here: no PostScript name, no bbox, no encoding, no axes. Recognising the
  procedure would mean interpreting PostScript; taking the first definition is
  what every real reader does instead. Pinned by
  `a_later_mention_inside_a_procedure_does_not_overwrite_a_declaration`.
- **`/Length1/2/3` are not a parameter.** PDFium ignores them (§1.2) because
  they are wrong often enough that trusting them loses fonts. The container is
  self-describing; we sniff.
- **Operands come off the bottom of the stack.** Type 1 operators clear the
  stack, and take their arguments from the *bottom* when more were pushed than
  needed — a hint-replacement subroutine leaves residue behind. Reading from
  the top instead misplaces glyphs in precisely the fonts that use hint
  replacement. `callsubr` is the exception: its index is the last operand.
- **`closepath` does not move the pen.** It closes the subpath and leaves the
  current point where it is, so a following `rmoveto` is relative to *that*.
  Getting this backwards shifts every glyph with more than one contour.
- **`seac`'s side-bearing correction.** The accent draws itself from its own
  `hsbw`, then shifts by `adx - asb + outer_lsb`, where `asb` is what the
  composing glyph *believed* the accent's side bearing to be. The correction
  exists because those two can disagree.
- **`flex` absorbs seven `rmoveto`s into two curves,** and the first collected
  point is a hinting reference that the outline does not use. Othersubr 0 takes
  three advisory arguments and pushes back two for the `setcurrentpoint` that
  follows.
- **An unknown othersubr hands its arguments back through `pop`.** That is the
  published convention, and it is what keeps a font using a private othersubr
  renderable instead of arithmetically desynchronised.
- **A negative `lenIV` discards nothing** rather than erroring — FreeType's
  reading, and the only one that keeps such a font usable.
- **Nothing short of "no charstrings at all" is fatal.** A truncated PFB
  segment, hex stopping mid-byte, a charstring running off its end, an
  inconsistent Multiple-Master declaration: each yields the best-effort result
  plus a diagnostic. A glyph whose charstring aborts still returns the outline
  built so far.

### Multiple Master, concretely

Both faces declare two axes (`/Weight`, `/Width`) over four masters at the unit
square's corners. A design coordinate maps through that axis's piecewise-linear
`/BlendDesignMap` to `[0,1]`, and each master's weight is the product over axes
of `n` or `1-n` by its corner — which sums to 1 by construction. The charstring
machine then consumes the vector through othersubrs 14–18.

| | weight axis | width axis | shipped `/WeightVector` |
|---|---|---|---|
| `ChromeSansMM` | 50–1450 | 50–1450 | `[0.3158 0.1349 0.3849 0.1644]` |
| `ChromeSerifMM` | 110–790 | 100–900 | `[0.2702 0.1048 0.4504 0.1746]` |

`MmAxis::default` is recovered by projecting the shipped weight vector back
onto each axis, so blending at the reported defaults reproduces the file's own
vector — tested, and the property that makes the reported defaults meaningful.

## Test surface — 88 tests, 4 doctests

- **70 unit tests** across the seven modules: container round-trips
  (PFB ≡ PFA), truncation recovery, `eexec` against a recomputed vector,
  `lenIV` ∈ {0, 1, 4, 8}, one test per charstring operator category with exact
  `BezPath` assertions, blend arithmetic including partition-of-unity and
  clamping, and the tokenizer's binary-payload escape hatch.
- **11 acceptance tests over the two real Foxit faces** (`tests/foxit_mm.rs`):
  they parse with the metrics they declare; the built-in encoding maps the
  Latin alphabet; two axes over four masters with the ranges above; every one
  of 230 glyphs draws finitely at three probes across design space, per face;
  the weight axis changes the outline (heavier covers >20% more area) and the
  width axis changes the *advance*, monotonically — the property
  `AdjustVariationParams` bisects on. One test reproduces that whole procedure
  and hits a target advance to within 5% of the axis range.
- **The differential**, `outlines_match_read_fonts_at_the_file_weight_vector`:
  all 460 glyphs of both faces, compared elementwise against
  `read_fonts::ps::type1` at the file's own weight vector. Glyph count, glyph
  names, upem, PostScript name, per-element coordinates and advances. This is
  the strongest available check — there is no C++ unit test to port (§1.16.3)
  and no Type 1 fixture in `testing/resources/`.
- **Never-panic sweeps** over every parse entry point:
  `arbitrary_bytes_never_panic` (empty, malformed PFB headers, absurd declared
  lengths, `/lenIV i32::MIN`, unterminated arrays, pathological repeats, every
  37th prefix and every 211th single-byte corruption of a good font),
  `corrupted_real_fonts_never_panic` (the same over both 66 KiB/113 KiB real
  fonts), and `the_primitives_never_panic_either` (the ciphers and the
  tokenizer directly, including a termination check). Every case that parses is
  then driven through every accessor, every glyph index including out-of-range,
  and `instantiate` at NaN and infinite coordinates.

## Divergences

**D14 (Tier-B, in our favor).** `read-fonts` reproduces FreeType's fixed-point
pipeline bit for bit, which **quantizes every unscaled coordinate to a whole
font unit** (`× 1/64`, discard the low 10 bits, shift back). We keep the
charstring's arithmetic in `f64` and return the unrounded value: the outline is
about to be multiplied by a text matrix and rasterized at device resolution,
where throwing away sub-unit precision is pure loss. The differential test
asserts the stronger property that their coordinate is exactly ours truncated,
so this can never become drift. Same reasoning for the zero-length segments
FreeType's stem-darkening filter suppresses and we emit — suppression is a
rasterizer's concern.

**Accepted API divergences from the brief's §3.6 sketch** (three, all recorded
as `[spec]`): `Encoding::Custom` carries `Box<str>` rather than `GlyphName`,
and `Gid` is defined here rather than imported — both because the alternative
is the `pdfrum-font` dependency cycle §3.6 itself flags; plus
`outline_with_diagnostics` as a sibling of `outline`, so the common path need
not take a `&mut Diagnostics` to learn that a charstring aborted.

## What is deliberately absent

Per §3.6: no CFF, CFF2, OpenType/CFF, TrueType, TTC, or Type 2 charstrings —
`skrifa`/`read-fonts` read all of those natively, including all 14 base-14
Foxit blobs and every `/FontFile3 /Type1C`. No hinting: we render filled
unhinted outlines, so `hstem`/`vstem`/`hstem3`/`vstem3`/`dotsection` and the
`hint_mask` machinery are consumed and discarded (font-brief OQ-4's proposal).
No `FT_Get_PS_Font_Info` surface — PDFium never calls it.

## Follow-ups for `pdfrum-font`

- `GlyphSource::Type1(Type1Font)` wires straight in. `code_to_gid` is the
  `UseType1Charmap` path (§1.8.2); `Encoding::predefined()` answers the
  "does this face carry a built-in Adobe encoding" question that branch turns on.
- `AdjustVariationParams` ports onto `mm_axes` + two `instantiate` calls, as
  §3.6 anticipated. `a_target_advance_can_be_hit_by_bisecting_the_width_axis`
  is the worked example.
- The `GlyphCache` key must include the instantiation, per SPEC §6's OQ-8
  amendment — `Type1Instance` deliberately caches nothing itself.

  `pdfrum-parser` finished to extract.
