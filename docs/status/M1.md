# M1 status — the first live conformance baseline

**Updated:** 2026-08-29 · **State:** `pdfrum-tool` wired up; harness runs
against a real binary for the first time; metadata and pageinfo Tier-A are
byte-exact across the whole corpus.

M0 left the scoreboard as an honest zero: `pdfrum-tool` was a stub, so all
1468 files carried `unsupported-tool` and nothing was actually compared. This
is the first run where the fitness function has something to measure.

### `text-nonempty`

`scoreboard.json`'s `totals.text` carries two rates, and `conformance run` and
`triage` print both:

```
  text                 872/1832 pages (47.6%)
  text-nonempty        0/960 pages (0.0%)
```

**872 of the store's 1832 `--txt` goldens are empty** — the oracle wrote a
byte-order mark and no characters, which the store holds as a zero-length file
after transcoding, because those pages carry no text. A tool that emitted
nothing for every page scores 47.6% on the naive rate while extracting
nothing, and the number would keep flattering it as real extraction landed.
`nonempty_rate`, over the 960 dumps that hold characters, is the honest one,
and SPEC §9 now names it as what M2's "≥ 98% of corpus" criterion means.

## `pdfrum-tool`

`crates/pdfrum-tool/` — `options` · `metadata` · `pageinfo` · `unsupported` ·
`run` · `main`, 1858 lines, 68 tests. Tool ring: `anyhow` only (`clap` is
deliberately unused, see below).

Implemented byte-exactly on `pdfrum-parser`: `--show-metadata`,
`--show-pageinfo`, `--password=`, `--pages=N(-M)`, the `Unsupported feature:`
notices those dumps carry, and the stderr chatter the harness reads a page
count out of. `--png`, `--txt`, `--annot`, `--show-structure` and the save-*
family are *recognized*, noted once on stderr, and produce nothing.

That last decision is load-bearing. The harness runs one fixed set of six
passes against every candidate; a tool that rejected the flags for crates that
do not exist yet would tag rendering and text as a **tool error** rather than
as unimplemented, and would lose the page count the same invocation reports.
`run::dump_page` is the single dispatch point the next format plugs into.

The command line is hand-parsed rather than declared with `clap`, because the
oracle's parser *is* part of the contract: `--pages=` uses `std::stringstream`
extraction (a value that will not parse leaves the number at zero, so
`--pages=x` is page 0 and `--pages=-4` is pages 0 through 4), an unrecognized
`--flag` is one specific stderr line plus the usage text and exit 1, and a
bare word is an input file even when it starts with a single dash.

## Format quirks the oracle's dump code does not show

Four behaviors decide these two dumps and none of them are in `dump.cc`.

**`Unsupported feature: <name>.` goes to stdout, so it lands *inside* the
dumps.** 96 of the corpus's metadata goldens open or close with one. The
position is not decoration: `Portfolios_Packages` and `Attachment` are raised
inside the load call and precede the metadata dump, while `XFA` comes from the
form-fill setup, which `pdfium_test` performs *after* dumping metadata, and so
lands last. Getting that one line's position wrong was one of the three
defects first contact turned up. There is no deduplication anywhere:
`two_signatures.pdf` prints `Digital_Signature.` twice. Two spellings the
oracle can produce are unreachable in the C++ and are not implemented —
`Rights_Management` has no call site at all, and `Unknown` is the default of a
switch every live code covers.

**`--show-pageinfo` reads the five boxes off the page's own dictionary and
stops.** No inheritance — a `/MediaBox` on the `/Pages` node is invisible here
even though every renderer honours it, which is why `No MediaBox.` appears 278
times in the corpus. No normalization: a box written `[0 0 200 -50]` prints
its negative top verbatim (8 corpus lines depend on this). No length check: a
short or empty array still answers, with zeros standing in. And the
letter-sized default a page falls back to for rendering never appears.

**`--show-metadata`'s `(N bytes)` is the C API's figure, not the text's.** It
is the length of a UTF-16LE encoding *including* its two-byte terminator, so
an empty value reads `(2 bytes)` and a three-character CJK title reads
`(8 bytes)`; a character outside the BMP counts as two units. The consequence
that decides whole files: **an absent key still prints a line.** Only a
document with no usable `/Info` suppresses the dump entirely — and "usable"
is strict, because the trailer's `/Info` must be an *indirect reference* (an
inline dictionary is not found) whose target is a dictionary. That is the
difference between an empty golden and an eight-line one.

**A `/Name` in `/Info` is decoded like a string.** `/Title /Hello` prints
`Hello`; numbers, arrays and dictionaries read as empty. Two further edges are
implemented but unexercised by this corpus: `PDFDocEncoding` maps bytes `0x7F`,
`0x92` and `0xA0` to U+0000, so the printed text stops at an embedded NUL
while the byte count covers the whole string; and an unpaired surrogate makes
the C library's `%ls` conversion fail mid-line, truncating the dump with no
newline and no remaining tags. (`pdfium_test` calls
`setlocale(LC_CTYPE, "en_US.UTF-8")`, so non-ASCII metadata is plain UTF-8 —
verified against the goldens rather than assumed.)

**`FPDF_LoadPage` applies a type check the page tree does not.** The tree is
permissive — a `/Kids` entry with no `/Kids` of its own is a leaf whatever it
calls itself, and it counts toward `/Count` — but the loader refuses a leaf
whose `/Type` is present and is not the name `Page`. A missing `/Type` is
fine. `bad_page_type.pdf` reports two pages and produces one. This lives in
the tool, not the parser: it is a property of the page-loading API, and a
caller reading raw dictionaries should still see the node.

## Harness adjustments

**The tool probe is now a positive capability check.** It used to run
`pdfrum-tool --png --md5` and read the output for the strings "not
implemented" / "no functionality implemented". That was right while the tool
printed one fixed line, but it cannot survive a real tool: a partial
implementation legitimately reports the flags it has not grown yet, and the
first live run would have tagged all 1468 files `unsupported-tool` again and
hidden every tier the tool can actually score. The probe now writes a
two-hundred-by-three-hundred one-page PDF and requires the pageinfo line back.

**`text-nonempty`** — the second aggregate described above: `TextScore` on
each row plus `totals.text`, both rates in the JSON and in both reports.

**Triage clusters `tierA-mismatch` by artifact class** — `:metadata`,
`:pageinfo`, `:structure`, `:text`, `:annot`. Without it the tag is a count of
everything at once and says nothing about where the work is.

## One parser fix this run found

The chain walk applied an older cross-reference *stream* section's entries by
merging them *under* the accumulation. The C++ does the opposite — an older
section's entries are written directly onto the merged table, overwriting what
newer sections left there — and then undoes the inversion by re-applying every
section, newest last, once the chain is known. Reading only the first half of
that gets `pixel/bug_345274934.pdf` wrong (a newer section's `/Size` phantom
buries the real object 4 the base section names, costing the document its only
page); reading only the second half gets `bug_781804.pdf` wrong (the wrong
`/Info` object, and so the wrong modification date). Both halves are now
implemented and both files are pinned by tests in
`crates/pdfrum-parser/tests/xref_streams.rs`. All 176 pre-existing parser
tests still pass.

## Known divergence

`resources/cropped_no_overlap.{pdf,in}` — the only two page-count
disagreements. Its `/CropBox` does not overlap its `/MediaBox`, so the oracle's
render pass computes a zero-area page, refuses it, and reports
`Processed 0 pages.`; its `--show-pageinfo` pass reports 1. The golden store
records the *render* pass's count, so a tool that does not render reports 1
where the golden says 0. This resolves itself when `pdfrum-render` lands; it is
not a parser or tool defect, and it is worth remembering that the oracle's own
page count is pass-dependent.
