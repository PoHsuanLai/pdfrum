# M12b P1 — Resolution-aware image decode

**Updated:** 2026-08-31 · **State:** in progress.

PLAN.md §M12b P1 is the assignment: the oracle decodes a JPEG or a JPEG 2000
codestream at *reduced resolution* when the destination is small, and we decode
every one at full resolution and throw the excess away. The named evidence is
`build/image_image_en_fqa` at 516 ms and `build/image_image_bug_718762` at
326 ms — costs that live in `build`, which is why M12's compositor work could
not touch them.

Written in M12.md's register: hypothesis, A/B, verdict, **including the
non-results**. A change that measures to zero is recorded as a non-result, never
deleted and never rounded up. A claim a later measurement refutes is withdrawn
in place.

## 1. What the oracle actually does, read rather than assumed

The brief's framing is "a 5000x5000 JPEG headed for a 64x64 device rectangle".
Reading `core/fpdfapi/page/cpdf_dib.cpp:220-224` beside
`core/fpdfapi/render/cpdf_imagerenderer.cpp:74-77` says something weaker and
more important, and the design has to match it:

```cpp
// cpdf_dib.cpp:220
uint8_t resolution_levels_to_skip = 0;
if (max_size_required.width != 0 && max_size_required.height != 0) {
  resolution_levels_to_skip = static_cast<uint8_t>(std::log2(
      std::max(1, std::min(GetWidth() / max_size_required.width,
                           GetHeight() / max_size_required.height))));
}
```

and `max_size_required` is filled, at the only call site that fills it, from

```cpp
// cpdf_imagerenderer.cpp:74
{render_status_->GetRenderDevice()->GetWidth(),
 render_status_->GetRenderDevice()->GetHeight()}
```

— **the whole render device's dimensions, not the image's destination
rectangle.** The oracle does not ask how big this image lands; it asks how much
bigger the image is than the entire page bitmap. A 5000x5000 JPEG on a 612x792
page skips `log2(min(5000/612, 5000/792)) = log2(6) = 2` levels and decodes at
1250x1250 — never at 64x64, however small the `cm` that draws it.

That is a deliberately conservative rule and it is the one to port. It bounds
the error: a reduced decode is never smaller than the page bitmap in the
dimension that constrained it, so no reduction can cost a pixel that the
device could have resolved. Sharpening it to the per-image footprint would be a
*divergence from the oracle*, would change pixels the oracle does not change,
and — this is the load-bearing part — would put the reduction where the
monotone rule is most likely to bite. It is not done here.

Three further rules travel with it, and `crates/pdfrum-page/src/image/dct.rs`
had already ported all three from the C++ during M4, unused:

- `scale_denominator` — `1 << min(levels, 3)`, libjpeg's 1/8 floor
  (`cpdf_dib.cpp:531`);
- `scaled_size` — **ceiling** division, `ScaledJpegSize`
  (`libjpeg_scanline_decoder.cpp:45`), which is not the JPX path's shift;
- `allows_reduced_resolution` — an image whose width or height is not a whole
  number of MCUs refuses reduction entirely, `scale_denom` forced back to 1
  (`libjpeg_scanline_decoder.cpp:151-157`, crbug 890745), because reduced
  decoding cannot crop the encoder's edge padding back out.

And the cache side already matched too. `CPDF_PageImageCache::Entry::IsCacheValid`
(`cpdf_pageimagecache.cpp:347-358`) accepts a cached bitmap for a new request
only when it is at least as large in both axes, which is exactly what
`RequestedSize::satisfies` in `crates/pdfrum-page/src/image/cache.rs` was
written to express in M12 P2.

**So the missing piece was never the policy. It was the plumbing**: nothing ever
computed a size to request, every call site passed `RequestedSize::Full`, and
the two codecs ignored the field they were handed.

## 2. The plumbing

`BuildContext` gains `decode_target: RequestedSize`, defaulting to `Full`
(SPEC.md §7, `[spec]` commit `e4560b5`). No transform, no affine, no render
type crosses the boundary — a pair of pixel counts and a variant meaning "as
many as there are" — and `BuildContext` is already the value a build's caches
are threaded through by `&mut`, so this is another fact about the build rather
than a fourth parameter on four public functions.

Two producers, both computing the same thing from the page's own crop box and
`/Rotate` before a single object is interpreted:

- `pdfrum::Page::paint` — sets it from `options.transform` applied to the
  display size, restores it after, so a caller threading one context through a
  render and then a `Page::objects` call does not silently inherit this page's
  device box;
- `pdfrum_tool::render::render` — the same, from `--scale`. **This one is not
  optional.** The tool does *not* go through the facade (it builds through
  `content::build`), so without wiring it the conformance harness would exercise
  none of this and the regression gate would be measuring the old path.

`RequestedSize::for_device` owns the truncation and carries the reason the box
is the page's rather than any image's; `pdfrum_page::display_size_from_dict` is
the shared derivation, so the crop-box-and-rotate rule has one authority rather
than three copies.

### 2.1 The cache gained a third lookup rung, and it is not an optimization

`ImageCache::get` matched the exact key, then a `Full` entry. That is enough
while nothing ever asks for a reduction and wrong the moment something does,
because **a decoder is allowed to ignore the hint**. An image asked for at
600x600 that comes back at 5000x5000 — a JPEG whose MCUs are not aligned, or a
palettized JPEG 2000, both of which refuse reduction — is stored under the
*600x600 request*. A later 300x300 request would then miss and decode the same
codestream again.

The third rung is a linear scan for any entry whose **decoded** dimensions
cover the request in both axes, which is
`CPDF_PageImageCache::Entry::IsCacheValid` (`cpdf_pageimagecache.cpp:347-358`)
exactly. Linear because the cache holds fifteen entries and the alternative is a
second index.

### 2.2 The order asymmetry is the oracle's, and a test asserted it wrong first

The obvious property to assert is that rendering a page small and then large
gives the same two images as rendering each alone. **Half of that is false, and
the false half is correct behaviour.** `IsCacheValid` accepts a cached bitmap
whenever it is at least as large as the new request, so a *small* draw that
follows a large one reuses the large decode rather than decoding again — and
therefore produces slightly different (finer) pixels than it would alone.

The guarantee is one-directional: a hit is never coarser than a fresh decode
would have been, and may be finer. The large render is what must be unaffected,
and it is. `one_image_drawn_at_two_sizes_is_right_at_both` asserts the
directional version after the symmetric one failed; the failure is recorded
here because it is the shape of thing a symmetric-looking test hides.

## 3. JPX: the plumbing works, and there is nothing in the corpus for it to do

**Hypothesis (PLAN.md §M12b): wiring `hayro-jpeg2000`'s `target_resolution` is
the cheap half and proves the plumbing.** It proves the plumbing. It wins
nothing, on any file this project has, and the reason is not a defect.

### 3.1 What was wired

`crates/pdfrum-page/src/image/jpx.rs` passed `target_resolution: None` and then
shifted the *decoder's* returned dimensions by a level count of its own:

```rust
let width = image.width() >> u32::from(levels);
```

That was a latent bug, never reachable because every caller passed `Full`
(`levels == 0`). Once the hint is actually sent, `hayro_jpeg2000::Image::new`
returns dimensions **already reduced** — `image_width()` is `div_ceil` by a
shrink factor the codestream parse multiplied in — so shifting again would have
halved a half and read the top-left quarter of the samples as the whole picture.
`decode_jpx` now takes the `RequestedSize` whole and reads `image.width()`
verbatim, which is the hint contract's "the image reports what it actually
decoded at" doing its job.

`hayro-jpeg2000` applies the same rule the oracle applies to `cp_reduce` — the
floored base-two logarithm of the smaller axis ratio — clamps it to the levels
the codestream carries, and **refuses the reduction outright for a palettized
image**, where interpolating between two indices would produce a third colour
that is in neither. That refusal is the decoder's, not ours, and it is why the
contract has to say a hint may be ignored.

### 3.2 The A/B, and the non-result

| | Before | After | Verdict |
|---|---:|---:|---|
| `build/image/image_jpx_123` | 49.06 ms | 49.06 ms | **no change** (criterion: `-2.7% .. +4.9%`, p = 0.55) |
| Conformance scoreboard, 1675 files | — | — | **byte-identical**, no metric of any file moved |

**The reduction never fires, and the arithmetic says why.** `image_jpx_123` is a
1269x1643 JPEG 2000 on a 595.32x841.92 page, so the oracle's own formula is
`log2(min(1269/595, 1643/841)) = log2(min(2, 1)) = log2(1) = 0`. Zero levels.
The image is not big enough *relative to its page* for any reduction to be
legitimate.

The 18 JPX files in the oracle's corpus are the same story and more so: 4x4 on
88x128, 64x64 on 100x200, 612x792 on 612x792. Every one of them is an image no
larger than the bitmap it lands in. **There is no file in either the bench
corpus or the 1675-file conformance set that the JPX reduction can help.**

That is a non-result and it is recorded as one. It is not a reason to widen the
rule to the per-image footprint — see §1: the oracle deliberately does not, the
conservatism is what bounds the error, and widening it would change pixels
against goldens that were produced without it.

### 3.3 What the byte-identical scoreboard does prove

It is worth being precise about what the zero is evidence *for*. Over 1675
files, wiring a decode target through four crates changed no pixel of any file.
That is the correctness half of the deliverable — the plumbing, the two
producers, the cache's third rung, the restored context — landing without
disturbing anything, which is exactly what a hint that nothing can act on should
do. The performance half is untested by it, and §4 is where that has to come
from.

### 3.4 The one file that does exercise it, built by hand

Nothing in either corpus draws one image twice at two very different sizes, so
`crates/pdfrum/tests/fixtures/jpx_two_sizes.pdf` was assembled: the
`/JPXDecode` stream of `corpus/fx/action/123.pdf` copied byte for byte into a
hand-written six-object PDF that draws it at 500x640 points and again at 40x50,
on a 600x800 page. The wrapper is ours; the codestream is the oracle's, which is
what lets `pdfium_test` render it and makes it an oracle comparison rather than
a self-consistency check.

At 1:1 the page is 600x800 and the image 1269x1643, so this file *does* reduce —
`log2(min(2, 2)) = 1` level, 635x822 instead of 1269x1643, a quarter of the
samples. Against the oracle's own render of the same file:

| | max diff | mean diff | exact px | SSIM (8x8) |
|---|---:|---:|---:|---:|
| before the change | 116 | 1.975 | 49.5% | 0.98243 |
| after | 139 | 2.009 | 48.8% | 0.98178 |

**A 0.0007 SSIM regression on a hand-built file, and it is reported rather than
buried.** The oracle reduces this file too — `CPDF_DIB::LoadJpxBitmap` passes
`resolution_levels_to_skip` straight into OpenJPEG's `cp_reduce`
(`cpdf_dib.cpp:631-642`) — so both sides are now decoding at one reduced level
and the residual is `hayro-jpeg2000`'s wavelet reconstruction against
OpenJPEG's, not a policy difference. It is under the conformance corpus's
resolution entirely: no scored file moved. The monotone rule is about the
scoreboard, and the scoreboard did not move.
