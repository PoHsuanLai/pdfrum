# M12b P1 — Resolution-aware image decode

**Updated:** 2026-08-31 · **State:** in progress.

PLAN.md §M12b P1 is the assignment: the oracle decodes a JPEG or a JPEG 2000
codestream at *reduced resolution* when the destination is small, and we decode
every one at full resolution and throw the excess away. The named evidence is
`build/image_image_en_fqa` at 516 ms and `build/image_image_bug_718762` at
326 ms — costs that live in `build`, which is why M12's compositor work could
not touch them.

Written in M12.md's register: hypothesis, A/B, verdict, **including the
non-results**. A change that measures to zero is recorded as a non-result, never
deleted and never rounded up. A claim a later measurement refutes is withdrawn
in place.

---

## 1. What the oracle actually does, read rather than assumed

The brief's framing is "a 5000x5000 JPEG headed for a 64x64 device rectangle".
Reading `core/fpdfapi/page/cpdf_dib.cpp:220-224` beside
`core/fpdfapi/render/cpdf_imagerenderer.cpp:74-77` says something weaker and
more important, and the design has to match it:

```cpp
// cpdf_dib.cpp:220
uint8_t resolution_levels_to_skip = 0;
if (max_size_required.width != 0 && max_size_required.height != 0) {
  resolution_levels_to_skip = static_cast<uint8_t>(std::log2(
      std::max(1, std::min(GetWidth() / max_size_required.width,
                           GetHeight() / max_size_required.height))));
}
```

and `max_size_required` is filled, at the only call site that fills it, from

```cpp
// cpdf_imagerenderer.cpp:74
{render_status_->GetRenderDevice()->GetWidth(),
 render_status_->GetRenderDevice()->GetHeight()}
```

— **the whole render device's dimensions, not the image's destination
rectangle.** The oracle does not ask how big this image lands; it asks how much
bigger the image is than the entire page bitmap. A 5000x5000 JPEG on a 612x792
page skips `log2(min(5000/612, 5000/792)) = log2(6) = 2` levels and decodes at
1250x1250 — never at 64x64, however small the `cm` that draws it.

That is a deliberately conservative rule and it is the one to port. It bounds
the error: a reduced decode is never smaller than the page bitmap in the
dimension that constrained it, so no reduction can cost a pixel that the
device could have resolved. Sharpening it to the per-image footprint would be a
*divergence from the oracle*, would change pixels the oracle does not change,
and — this is the load-bearing part — would put the reduction where the
monotone rule is most likely to bite. It is not done here.

Three further rules travel with it, and `crates/pdfrum-page/src/image/dct.rs`
had already ported all three from the C++ during M4, unused:

- `scale_denominator` — `1 << min(levels, 3)`, libjpeg's 1/8 floor
  (`cpdf_dib.cpp:531`);
- `scaled_size` — **ceiling** division, `ScaledJpegSize`
  (`libjpeg_scanline_decoder.cpp:45`), which is not the JPX path's shift;
- `allows_reduced_resolution` — an image whose width or height is not a whole
  number of MCUs refuses reduction entirely, `scale_denom` forced back to 1
  (`libjpeg_scanline_decoder.cpp:151-157`, crbug 890745), because reduced
  decoding cannot crop the encoder's edge padding back out.

And the cache side already matched too. `CPDF_PageImageCache::Entry::IsCacheValid`
(`cpdf_pageimagecache.cpp:347-358`) accepts a cached bitmap for a new request
only when it is at least as large in both axes, which is exactly what
`RequestedSize::satisfies` in `crates/pdfrum-page/src/image/cache.rs` was
written to express in M12 P2.

**So the missing piece was never the policy. It was the plumbing**: nothing ever
computed a size to request, every call site passed `RequestedSize::Full`, and
the two codecs ignored the field they were handed.

## 2. The plumbing

`BuildContext` gains `decode_target: RequestedSize`, defaulting to `Full`
(SPEC.md §7, `[spec]` commit `e4560b5`). No transform, no affine, no render
type crosses the boundary — a pair of pixel counts and a variant meaning "as
many as there are" — and `BuildContext` is already the value a build's caches
are threaded through by `&mut`, so this is another fact about the build rather
than a fourth parameter on four public functions.

Two producers, both computing the same thing from the page's own crop box and
`/Rotate` before a single object is interpreted:

- `pdfrum::Page::paint` — sets it from `options.transform` applied to the
  display size, restores it after, so a caller threading one context through a
  render and then a `Page::objects` call does not silently inherit this page's
  device box;
- `pdfrum_tool::render::render` — the same, from `--scale`. **This one is not
  optional.** The tool does *not* go through the facade (it builds through
  `content::build`), so without wiring it the conformance harness would exercise
  none of this and the regression gate would be measuring the old path.

`RequestedSize::for_device` owns the truncation and carries the reason the box
is the page's rather than any image's; `pdfrum_page::display_size_from_dict` is
the shared derivation, so the crop-box-and-rotate rule has one authority rather
than three copies.

### 2.1 The cache gained a third lookup rung, and it is not an optimization

`ImageCache::get` matched the exact key, then a `Full` entry. That is enough
while nothing ever asks for a reduction and wrong the moment something does,
because **a decoder is allowed to ignore the hint**. An image asked for at
600x600 that comes back at 5000x5000 — a JPEG whose MCUs are not aligned, or a
palettized JPEG 2000, both of which refuse reduction — is stored under the
*600x600 request*. A later 300x300 request would then miss and decode the same
codestream again.

The third rung is a linear scan for any entry whose **decoded** dimensions
cover the request in both axes, which is
`CPDF_PageImageCache::Entry::IsCacheValid` (`cpdf_pageimagecache.cpp:347-358`)
exactly. Linear because the cache holds fifteen entries and the alternative is a
second index.

### 2.2 The order asymmetry is the oracle's, and a test asserted it wrong first

The obvious property to assert is that rendering a page small and then large
gives the same two images as rendering each alone. **Half of that is false, and
the false half is correct behaviour.** `IsCacheValid` accepts a cached bitmap
whenever it is at least as large as the new request, so a *small* draw that
follows a large one reuses the large decode rather than decoding again — and
therefore produces slightly different (finer) pixels than it would alone.

The guarantee is one-directional: a hit is never coarser than a fresh decode
would have been, and may be finer. The large render is what must be unaffected,
and it is. `one_image_drawn_at_two_sizes_is_right_at_both` asserts the
directional version after the symmetric one failed; the failure is recorded
here because it is the shape of thing a symmetric-looking test hides.

## 3. JPX: the plumbing works, and there is nothing in the corpus for it to do

**Hypothesis (PLAN.md §M12b): wiring `hayro-jpeg2000`'s `target_resolution` is
the cheap half and proves the plumbing.** It proves the plumbing. It wins
nothing, on any file this project has, and the reason is not a defect.

### 3.1 What was wired

`crates/pdfrum-page/src/image/jpx.rs` passed `target_resolution: None` and then
shifted the *decoder's* returned dimensions by a level count of its own:

```rust
let width = image.width() >> u32::from(levels);
```

That was a latent bug, never reachable because every caller passed `Full`
(`levels == 0`). Once the hint is actually sent, `hayro_jpeg2000::Image::new`
returns dimensions **already reduced** — `image_width()` is `div_ceil` by a
shrink factor the codestream parse multiplied in — so shifting again would have
halved a half and read the top-left quarter of the samples as the whole picture.
`decode_jpx` now takes the `RequestedSize` whole and reads `image.width()`
verbatim, which is the hint contract's "the image reports what it actually
decoded at" doing its job.

`hayro-jpeg2000` applies the same rule the oracle applies to `cp_reduce` — the
floored base-two logarithm of the smaller axis ratio — clamps it to the levels
the codestream carries, and **refuses the reduction outright for a palettized
image**, where interpolating between two indices would produce a third colour
that is in neither. That refusal is the decoder's, not ours, and it is why the
contract has to say a hint may be ignored.

### 3.2 The A/B, and the non-result

| | Before | After | Verdict |
|---|---:|---:|---|
| `build/image/image_jpx_123` | 49.06 ms | 49.06 ms | **no change** (criterion: `-2.7% .. +4.9%`, p = 0.55) |
| Conformance scoreboard, 1675 files | — | — | **byte-identical**, no metric of any file moved |

**The reduction never fires, and the arithmetic says why.** `image_jpx_123` is a
1269x1643 JPEG 2000 on a 595.32x841.92 page, so the oracle's own formula is
`log2(min(1269/595, 1643/841)) = log2(min(2, 1)) = log2(1) = 0`. Zero levels.
The image is not big enough *relative to its page* for any reduction to be
legitimate.

The 18 JPX files in the oracle's corpus are the same story and more so: 4x4 on
88x128, 64x64 on 100x200, 612x792 on 612x792. Every one of them is an image no
larger than the bitmap it lands in. **There is no file in either the bench
corpus or the 1675-file conformance set that the JPX reduction can help.**

That is a non-result and it is recorded as one. It is not a reason to widen the
rule to the per-image footprint — see §1: the oracle deliberately does not, the
conservatism is what bounds the error, and widening it would change pixels
against goldens that were produced without it.

### 3.3 What the byte-identical scoreboard does prove

It is worth being precise about what the zero is evidence *for*. Over 1675
files, wiring a decode target through four crates changed no pixel of any file.
That is the correctness half of the deliverable — the plumbing, the two
producers, the cache's third rung, the restored context — landing without
disturbing anything, which is exactly what a hint that nothing can act on should
do. The performance half is untested by it, and §4 is where that has to come
from.

### 3.4 The one file that does exercise it, built by hand

Nothing in either corpus draws one image twice at two very different sizes, so
`crates/pdfrum/tests/fixtures/jpx_two_sizes.pdf` was assembled: the
`/JPXDecode` stream of `corpus/fx/action/123.pdf` copied byte for byte into a
hand-written six-object PDF that draws it at 500x640 points and again at 40x50,
on a 600x800 page. The wrapper is ours; the codestream is the oracle's, which is
what lets `pdfium_test` render it and makes it an oracle comparison rather than
a self-consistency check.

At 1:1 the page is 600x800 and the image 1269x1643, so this file *does* reduce —
`log2(min(2, 2)) = 1` level, 635x822 instead of 1269x1643, a quarter of the
samples. Against the oracle's own render of the same file:

| | max diff | mean diff | exact px | SSIM (8x8) |
|---|---:|---:|---:|---:|
| before the change | 116 | 1.975 | 49.5% | 0.98243 |
| after | 139 | 2.009 | 48.8% | 0.98178 |

**A 0.0007 SSIM regression on a hand-built file, and it is reported rather than
buried.** The oracle reduces this file too — `CPDF_DIB::LoadJpxBitmap` passes
`resolution_levels_to_skip` straight into OpenJPEG's `cp_reduce`
(`cpdf_dib.cpp:631-642`) — so both sides are now decoding at one reduced level
and the residual is `hayro-jpeg2000`'s wavelet reconstruction against
OpenJPEG's, not a policy difference. It is under the conformance corpus's
resolution entirely: no scored file moved. The monotone rule is about the
scoreboard, and the scoreboard did not move.

## 4. The JPEG half, and the measurement that changed the question

PLAN.md §M12b P1 names `build/image_image_en_fqa` (516 ms) and
`build/image_image_bug_718762` (326 ms) as the evidence, and reads them as
"a huge JPEG decoded at full resolution". Before writing any decoder code the
four heavyweights of the `image` class were opened and their filters read.

### 4.1 Three of the four are not JPEGs at all

| bench file | image | page | filter | oracle's levels |
|---|---|---|---|---:|
| `image_bug_718762` | 5000x5000 | **64x64** | `[/ASCIIHexDecode /FlateDecode /DCTDecode]` | 6, capped to **3** |
| `image_bug_898443` | 5100x6600 | 612x792 | **`/FlateDecode`** | n/a |
| `image_bug_583804` | 4473x4473 | 4473x4473 | **`/FlateDecode`** | n/a |
| `image_en_fqa` | 552 images, mostly small | 595x842 | **`/FlateDecode`** x558 | n/a |

**Only `image_bug_718762` is a DCT image.** The other three are Flate, and the
oracle does not resolution-reduce Flate either — `CPDF_DIB::CreateDecoder`
passes `resolution_levels_to_skip` to exactly two branches, `LoadJpxBitmap`
(`cpdf_dib.cpp:474`) and `CreateDCTDecoder` (`:501`); `CreateFlateDecoder`
(`:495`) and the RunLength and CCITT branches never see it. So on three of the
four files named as this milestone's evidence, **there is no resolution-aware
decode to be had, in our engine or in the oracle's.** Whatever the oracle's
advantage is on those, it is its scanline architecture — it never materializes
the whole surface — and not this feature.

That leaves one file. It is a spectacular one: 5000x5000 on a 64x64 page is
`log2(min(78, 78)) = 6` levels, capped by libjpeg to 3, so the oracle decodes
it at 625x625 — **1/64th of the samples**.

### 4.2 And on that one file, the JPEG decode is not the cost

Instrumented inside `decode_image` on the real file, release build, the 352 ms
splits:

| stage | time | share |
|---|---:|---:|
| dictionary + colour space | 0.010 ms | 0.0% |
| filter chain (AHx + Flate to the codestream) | 0.12 ms | 0.0% |
| **`zune_jpeg` decode, 5000x5000x4** | **60.7 ms** | **17%** |
| **`apply_codec_decode` — the `/Decode` array** | **291.2 ms** | **83%** |
| `Pixels::Cmyk8` construction | 0.0002 ms | 0.0% |
| mask + colour key + matte + tail | 0.002 ms | 0.0% |

**The premise this milestone was handed is wrong on its own best file.**
Decoding the JPEG at 1/8 scale removes 60.7 ms of 352 — and it also shrinks the
buffer the other 291 ms runs over, which is where the rest of the win would come
from. But the 291 ms is not the decoder's, it is ours, and it is reachable
*without* a scaled decoder at all.

`image_bug_718762` carries `/Decode [1.0 0.0 1.0 0.0 1.0 0.0 1.0 0.0]` — the
Adobe CMYK inversion, written out — so the `default_decode` short circuit at the
top of `apply_codec_decode` does not fire and the loop runs over all
**100,000,000 bytes** at **2.9 ns each**. Per byte it does: `i % components`
(an integer division), two bounds-checked `Vec` gets, a float multiply-add, a
clamp, a `round`, and a cast back to `u8`.

The mapping is a function of `(component index, byte value)` and nothing else.
There are four components and 256 byte values. It is a **1 KiB lookup table**,
and computing it per byte instead is the entire 291 ms.

This is option (b) from PLAN.md's list — "make the reduction cheaper and fused"
— arriving one stage earlier than expected and much blunter: not a fused
resample, just a table. §5 measures it.

## 5. The `/Decode` lookup table: -68% on the one DCT file, byte-identical

**Hypothesis:** the 291 ms is a per-byte evaluation of a function with 1024
possible answers, and replacing it with the table costs nothing in fidelity.

`apply_codec_decode`'s output depends on the component index and the byte value
and on nothing else. Four components, 256 values: a kibibyte. The table is built
from the same `DecodeMap::apply` and the same rounding, so every output byte is
identical **by construction** rather than by measurement — and
`the_decode_table_is_exhaustively_the_per_sample_arithmetic` asserts it over
every component slot against every byte value, across four decode arrays chosen
to reach different corners (the Adobe inversion, an asymmetric range, one that
clamps at both ends, a degenerate zero-width one).

The one thing the rewrite could plausibly get wrong is a buffer whose length is
not a whole number of pixels — the old loop keyed on `i % components` and the
new one on position within a `chunks_mut` group, which agree only because
`chunks_mut` yields the short trailing chunk rather than dropping it.
`a_trailing_partial_pixel_maps_by_its_position_in_the_pixel` pins that.

### 5.1 The A/B, and why the first one was thrown away

The first measurement was `cargo bench` against criterion's stored baseline, and
it reported +5% to +25% "regressions" on four files the change cannot touch —
Flate images, CCITT, JBIG2, none of which run `apply_codec_decode` at all. The
machine's load average was **15**, with two unrelated Python jobs at 300% CPU
each and another agent's profiler running. **Those numbers were contention, not
results, and they are not reported as results.**

The measurement below is paired: two binaries built from two clean worktrees at
`c229947` and `33bcc3f`, run *alternately* in the same window, three rounds of
best-of-five each, so whatever the machine is doing hits both sides equally.

| `image_jpx_123` | 43.9 ms | 42.0 ms | -4.4% |

## 6. Where the rest of it is, measured rather than assumed

With the table landed, `image_bug_718762`'s build is 101 ms and its cold render
is 953 ms. Instrumenting both seams on the three large-image documents says
plainly where the remaining time lives, and it is not where P1's brief expected.

**Build, `image_bug_718762` (101 ms):**

| stage | time | share |
|---|---:|---:|
| `zune_jpeg` decode | 62.0 ms | 61% |
| `apply_codec_decode` (now the table) | 39.1 ms | 39% |

The table pass is now pure memory bandwidth: measured at **0.26 ns/byte** and
exactly linear — 26.1 ms over 100,000,000 bytes and 0.42 ms over 1,562,500,
which is the same rate. There is nothing left to take out of it at this buffer
size; the only way to make it cheaper is to make the buffer smaller, which is
what a scaled decode would do (§7).

**Render, the three large-image documents:**

| document | `to_pixmap` | `reduce_to` | source → dest |
|---|---:|---:|---|
| `image_bug_718762` | **857 ms** | 46 ms | 5000x5000 → 64x64 |
| `image_bug_898443` | **653 ms** | 52 ms | 5100x6600 → 612x792 |
| `image_bug_583804` | **388 ms** | 0.0003 ms | 4473x4473 → no reduction |

`to_pixmap` is **90% or more of every one of them**, and the box filter it feeds
is not the cost — `reduce_to` is two-pass, so it is
`O(src_h * dest_w * taps)` rather than `O(source pixels * taps)`, and when the
destination is small it is cheap. M12 §10.3 reported this cost as "4 µs per
*output* pixel", which is the same number seen from the wrong end: it is
**~34 ns per *source* pixel**, and the source is what it iterates.

This is the shape of the whole finding. P1 was framed as a decoder feature, and
on the one file in the corpus where the feature applies at all, the decoder is
17% of the build and the build is 10% of the render. **The dominant cost in the
`image` class is converting source samples to premultiplied RGBA that are then
thrown away**, and that is true of the three Flate documents where no decoder
hint exists to be had.

## 7. `to_pixmap` without the floats: -35% on the whole `image` class

**Hypothesis:** `to_pixmap`'s per-pixel cost is not arithmetic anyone needs. It
converts a byte to an `f32`, does colour work, and converts back to a byte — and
the two conversions are inverses.

They are, exactly. `Pixels::color_at` reaches `Rgb` from a sample through
`f32::from(b) / 255.0`; `Rgb::to_bytes` returns through
`(v.clamp(0.0, 1.0) * 255.0).round()`. **That pair is the identity on all 256
byte values**, verified over the whole domain. So:

- `Gray8` and `Rgb8` did a float round trip that is a *pure no-op* — and one the
  optimizer cannot delete, because it cannot know `round` is exact on these
  inputs;
- `Cmyk8` wrapped `adobe_cmyk_to_srgb`, which is **byte-in, byte-out already**;
  the wrapper's own encode (`v * 255.0 + 0.5`, truncated) is likewise the
  identity on all 256, so four divisions in and three out bracketed a table
  lookup that wanted neither;
- `Indexed` encoded a palette entry per pixel, when the palette has at most 256
  entries and the image has as many pixels as it has.

`Pixels::sample_bytes` is the same answer without any of that, and
`Pixels::byte_palette` encodes an indexed palette once for a caller about to
walk a whole image. `the_byte_path_is_exactly_the_float_path` proves the
equality **exhaustively**: every byte for grey, a walk putting every byte in
every channel for RGB, a 16^4 lattice for CMYK that hits every value on every
axis, every palette entry for indexed, both stencil phases, and an
out-of-range read on all five.

### 7.1 The A/B

Paired, alternating, three rounds of best-of-three, `33bcc3f` against the
working tree:

| `render-cold`, `image` class | before | after | delta |
|---|---:|---:|---:|
| `image_jbig2_1478366` | 381.4 ms | 150.2 ms | **-60.6%** |
| `image_bug_898443` | 962.5 ms | 475.7 ms | **-50.6%** |
| `image_jbig2_880920` | 234.5 ms | 118.4 ms | **-49.5%** |
| `image_bug_718762` | 940.9 ms | 525.2 ms | **-44.2%** |
| `image_bug_583804` | 800.7 ms | 522.3 ms | **-34.8%** |
| `image_jpx_123` | 91.2 ms | 61.8 ms | -32.2% |
| `image_ccitt_transfer` | 40.0 ms | 35.5 ms | -11.2% |
| `image_ccitt_3bigpreview` | 49.9 ms | 47.4 ms | -5.1% |
| `image_en_fqa` | 592.9 ms | 602.3 ms | **+1.6%** |
| **class geomean** | | | **-35.0%** |

Conformance: **byte-identical** over all 1675 files, which is what an
exhaustively-proved identity predicts.

Note which files moved. This change helps **every** image document, including
the three Flate ones and both JBIG2 ones, because it is downstream of the codec
entirely — which is the point §4.1 was making from the other direction. The
resolution-aware decode P1 was named for reaches one file in the corpus; this
reaches all of them.

`image_en_fqa` is the exception at +1.6%, inside the band and reported as a
non-result rather than rounded to zero. Its 552 images are small, so its cost is
per-*image* overhead rather than per-pixel work, and nothing here touches that.

## 8. The JPEG decoder half: measured, deferred, and written up

PLAN.md §M12b P1 asks for (b) to be measured before committing to (a). It was,
and (b) won by a wide margin — but the two are not alternatives, so this section
says exactly what (a) would still be worth.

### 8.1 Where `image_bug_718762` stands now

| | at `c229947` | now | delta |
|---|---:|---:|---:|
| whole first render | 1180.8 ms | **523.1 ms** | **-55.7%** |
| of which `zune_jpeg` | 58.6 ms | 58.6 ms | — |
| of which downstream of it | 1122.2 ms | 464.5 ms | -58.6% |

And the end-to-end process comparison against the oracle on the same file,
three runs each, `pdfium_test --png` against `pdfrum-tool --png`:

| | run 1 | run 2 | run 3 |
|---|---:|---:|---:|
| oracle | 0.61 s | 0.55 s | 0.56 s |
| ours | 0.53 s | 0.56 s | 0.52 s |

**We now match the oracle on this document**, which M12's own table had at 24x
warm — and we match it while still decoding the JPEG at 5000x5000 where the
oracle decodes it at 625x625. That is the clearest statement of what §4.2 found:
the oracle's scaled decode was never the whole of its advantage here.

### 8.2 What a scaled decode would still be worth, and why it was not done

`to_pixmap` on this file is still **403 ms** — 16 ns per source pixel, and the
Adobe CMYK table is a genuine four-dimensional interpolated lookup, so unlike
§7's float trip that arithmetic is real work that someone has to do. A decode at
`scale_denom = 8` would produce 625x625 instead of 5000x5000: **1/64th of the
pixels**, taking `to_pixmap` from 403 ms to roughly 6 ms and the decode itself
from 59 ms to a fraction of that. It is the remaining structural fix on this
document.

It is **not implemented here**, and the reason is the one PLAN.md anticipated:
option (a) is an upstream change to `zune-jpeg`, not something a wrapper can
reach. Reduced decoding happens *inside* the inverse DCT — the coefficients
above the retained band are never dequantized and the IDCT itself is smaller —
so no combination of `DecoderOptions`, no post-pass and no wrapper produces it.
The trap PLAN.md names was re-verified against the vendored 0.5.15 source:
`idct_1x1_func` and `idct_4x4_func` at `src/mcu.rs:585-591` are selected by
coefficient **sparsity** (`len <= 1`, `len <= 10`) and both still write a full
8x8 block, and `set_max_width`/`set_max_height` in `zune-core` are rejection
guards.

The request is written up with these numbers at
`docs/upstream/zune-jpeg-scaled-decode.md`, including the MCU-alignment
correctness rule (crbug 890745) that a scaled decoder has to inherit, and
including the part that argues *against* urgency — that we got 1181 ms to 523 ms
without it. It is drafted, not filed, as `hayro-jbig2`'s was.

### 8.3 Options (b) and (c), settled

- **(b) — "make the reduction cheaper and fused"** is what §5 and §7 are, and it
  is where all the measured win came from. It arrived one stage earlier than the
  wording expected: not a fused resample, but a lookup table for `/Decode` and
  the removal of a float round trip that was provably the identity. Fusing the
  box filter *into* the conversion was considered and **rejected on oracle
  evidence**: `CStretchEngine::ContinueStretchHorz`
  (`cstretchengine.cpp:346`) accumulates from `source_->GetScanline()`, which is
  `CPDF_DIB`'s **already-converted** scanline, so the oracle also converts every
  source pixel and averages afterwards. Averaging before conversion would change
  pixels, and the monotone rule is not worth spending on a restructure that the
  oracle does not perform.
- **(c) — scanline-windowed decode** is moot for the same reason (b) was
  enough: `zune-jpeg`'s `decode()` materializes the whole surface and exposes no
  row-at-a-time consumer, so (c) is a subset of (a)'s upstream work rather than
  an independent option.

### 9.1 The `image` class against its committed baseline

The milestone's P1 target is the `image` class's **cold** geomean, at least 40%

after re-running the group cleanly:

| `image_bug_898443` | 957.3 ms | 506.8 ms | **-47.1%** |
| `image_jbig2_880920` | 237.4 ms | 125.4 ms | **-47.2%** |

**-33.4% against a target of -40%: the target is missed by 6.6 points, and it is
recorded as missed rather than restated.** Five of the nine files are between
-37% and -59%; the shortfall is entirely the two that move the wrong way, and
neither is reachable from here:

- **`image_en_fqa` (+3.7%)** is 552 *small* images. Instrumented, `to_pixmap`

  to whatever addresses that.
- **`image_ccitt_3bigpreview` (+3.0%)** sits on its band edge and the paired
  harness put it at -5.1%; the two disagree by less than the machine's spread.

The independent paired-harness measurement of the same class, taken by
alternating two isolated binaries in one window, agrees closely: **-35.0%**
against `33bcc3f`, and **-35.9%** against `3de0032`. Whole bench corpus over the
same window, all six classes: **-16.9%**.

### 9.2 The ratchet, and what is owed

`ratchet update` was **not** run, and the reason is the one `4d1e385` already
records for P2: this machine has carried a load average between 9 and 15 for the
whole session, from two unrelated 300%-CPU jobs that are not agents and did not
clear. A baseline written under that contention permanently loosens a ratchet
whose entire value is that it only tightens.

That is not a hypothetical here — it was caught happening. A first `cargo bench`
of the `image` class reported +5% to +25% "regressions" on four documents this
milestone's changes cannot touch, and re-running the same benchmarks in a quieter
window put every one of them back inside its band. Those numbers were discarded
rather than reported (§5.1), and the same discipline is why the baseline is not
being written from them.

**What is owed:** `cargo bench --workspace` followed by
`ratchet update` on an idle machine, committing the sixteen improvements the
check already identifies. The direction is one-way and known — `update` refuses
to write a regression — and `check` passing is not blocked by these commits,
because a faster render is never a ratchet failure. No number in this document
depends on it: every A/B here comes from the interleaved best-of-N harness, and
the criterion figures in §9.1 are quoted as a cross-check of that harness rather
than as its source.

### 9.3 A regression that was chased and turned out not to exist

`ratchet check` reported `vector_en_tem` slower by 9–13% on all three backends,
which is the shape of a real regression rather than noise — and the file does
carry two `/DCTDecode` images, so it was plausibly this milestone's.

It is not. Bisected with the paired harness across `3de0032`, `33bcc3f`,
`bfb6f42` and `85f47b7`, the readings came out **non-monotonic**: 109, 125, 107,
123 ms. `85f47b7` differs from `bfb6f42` in **documentation files only** —
`diff -rq` over `crates/` reports one README — so a 15% gap between those two is
arithmetically impossible from code.

Rebuilding each into a *fresh* target directory reproduced each figure exactly
(mid 109.9 / 108.8, head 124.2 / 123.9), so it is not build nondeterminism
either: it is stable per source tree and independent of the source tree's
contents. Twelve consecutive best-of-five runs of one binary vary by under 2 ms,
so it is not run-to-run noise in the ordinary sense.

**The conclusion is that `vector_en_tem` is not measurable to better than ~15% on
this machine in its current state, and no claim about it — in either direction —
can be supported.** It is written down here rather than left in the ratchet as an
unexplained regression, and it is the second thing in this document (after §5.1)
that a loaded machine nearly turned into a false finding.
