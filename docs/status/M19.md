# M19 — The `pdfrum` command line

**Design:** `docs/design/pdfrum-cli.md` (§9 is the scoped version).
**Started:** 2026-09-05.

## Phase 1 — foundation and the read-only core

`crates/pdfrum-cli`, binary `pdfrum`, on `clap` + `serde_json` and the
facade crate only. Commands: `info`, `doctor`, `render`, `extract
text|links|toc|attachments|annotations|signatures`; `--json` on every
inspection command, `--pages` with the `1-3,5,7-end` grammar, `--password`,
`-` for a single PNG to stdout, notices on stderr, a closed pipe treated
as the reader being done. Exit codes 0 / 1 / 2 (clap) / 3 (`doctor
--strict`).

**Facade fills** (each on `pdfrum`'s API baseline): `Document::id()` (the
trailer `/ID` pair), `Page::{bleed_box, trim_box, art_box}`,
`Page::page_links()` with `PageLink { rect, target: LinkTarget::{Page, Uri,
Other} }` — the raw `Page::links()` needed the catalog, the limits and a
page-index closure to resolve, which no facade client should have to hold.

**Tests:** `crates/pdfrum-cli/tests/cli.rs` runs the binary on nine
fixtures (`tests/fixtures/PROVENANCE.md`) and compares stdout with
`tests/expected/*.txt`; every `--json` output parses and is checked for its
keys; piping into a closed reader exits 0.

**Deviations from the design:** none in scope; `--color`, `--hyperlinks`
and the terminal crates arrive with phase 3, so no flag without a reader
exists yet.

## Phase 2 — surgery, forms, whole-file commands

`pages merge|split|slice|reorder|create|nup|booklet`, `forms
dump|fill|flatten`, `repair`, `optimize`, `security decrypt`, and
`--deterministic` on every writing command (the `/ID` seeded from the
input's bytes, so the same input gives the same output bytes anywhere).

**Library work the design under-scoped.** §9.1 called `pages create` and
`slice` composition; neither was. The edit crate had page import and N-up
and nothing else that touches the page tree, so `pdfrum-edit` gained
`pages.rs`: `add_blank_page`, `delete_pages` (unlinking from any depth of
tree, every `/Count` above decremented), `set_page_rotation`,
`set_page_box`, with five tests over flat and nested trees. The facade
gained `Document::blank(width, height)` (a correct four-object file written
in memory), `DocEdit::{import_pages, delete_pages, add_page, set_rotation,
set_page_box, n_up}`, `SaveOptions::id_source` with `IdSource` and
`PageBox` re-exported.

**How the commands compose.** `merge` imports every other file into the
first; `split` and `slice` delete from the source, so a page keeps its
identity and can be rotated or cropped by its own index; `reorder`, `nup`
and `booklet` import into a blank document and then delete the blank's
own page, which is why they cannot also rotate — that is `slice`'s job
and the help says so. `booklet` pads to a multiple of four with blank
pages through a first in-memory save, then lays the folding order out
two-up. `create` first builds a document with one blank page per image,
saves it in memory, and only then draws on the pages, because a page has
to exist before it can be edited. `repair` and `optimize` are the same
full rewrite; their help says so.

**Dependencies:** `png` (already a tool row) for decoding PNG input to
`pages create`; JPEG input is embedded as it is, with the frame size read
from the SOF marker.

**Tests:** nine more in `tests/cli.rs`, three new fixtures with provenance
(`text_form.pdf`, `encrypted.pdf` with its password, `mona_lisa.jpg`), a
PNG generated in the test. Byte-identical `--deterministic` output is
asserted, not assumed.

**Not done, and named:** `forms fill` does not run the document's
calculation scripts — that needs the `javascript` feature and a
`FormSession`, phase 5's territory alongside `security encrypt`.

## Phase 3 — the terminal

`preview` (one page, right there), `view` (a pager: `j`/`k`, `g`/`G`,
`+`/`-` zoom, `/` search with `n`, `q`; raw mode and the alternate screen
restored whatever happens), `search` (`grep` for a document: every hit
with its line, page and boxes; exit 1 when nothing matched), and three
global flags — `--color`, `--hyperlinks`, `--graphics` — each
`auto|always|never` (or a protocol), decided once in `term.rs` from the
flags and the environment (`NO_COLOR`, `TERM=dumb`, `TERM_PROGRAM`,
`KITTY_WINDOW_ID`, `COLORTERM`) and off whenever stdout is not a terminal.
`extract links` and `extract toc` wrap targets in OSC 8 (`file://…#page=N`
for pages); `search` paints hits. An encrypted file opened at a terminal
without `--password` asks for one, silently.

**Pictures without `viuer`:** its half-block path pulls an LGPL crate, so
kitty's APC chunks, iTerm2's OSC 1337 and truecolor half-blocks are written
directly, ~120 lines with a base64 encoder pinned to the RFC vectors. No
sixel: the only Rust implementation on offer wraps libsixel.

**Dropped, and why:** `comfy-table` and `indicatif` were admitted and then
removed in the same phase: tables and progress only render at a terminal,
which the tests never are, so they were options without a reader the tests
could see. `DEPS.md` records all three.

**Tests:** search text, JSON and exit code; a half-block preview forced
through `--graphics halfblock` into a pipe; `--hyperlinks always` and
`--color always` in a pipe, and `NO_COLOR` winning over `auto`; `view`
refusing a pipe with a pointer to `render`.

## Phase 4 — `pdfrum-markdown`

A library crate beside `pdfrum-text` and `pdfrum-doc`, not on the facade:
its inputs are the page graph, the resolver and the structure tree, and the
facade's `Page::markdown()` / `Page::layout_text()` (feature `markdown`)
are one call each into it. The command line gains `extract markdown` and
`extract text --layout`.

**Two tiers, one line model.** `lines.rs` walks the extractor's characters
into lines with a box, a median font size, bold/mono votes from the fonts'
names (the graph walked in the extractor's own numbering, so the join is
exact) and the marked-content id per character run; a character drawn
twice in one place (faux bold) is kept once. `tagged.rs` reads the tree —
headings by level or nesting depth, paragraphs, lists with labels, tables
through `THead`/`TBody`, figures with `/Alt` or `/ActualText`, a figure
nested in a paragraph still a figure — joining each element to the text
under the ids it names. **What the tree does not claim is not lost:** an id
the tree marks invalid (PDFium's rule for a kid whose element names no
page, which this crate follows) leaves its text to the typographic tier,
appended after the tree's blocks. `heuristics.rs` is that tier: body size
by weighted mode, 1.6×/1.3× headings, short bold `###`, monospaced code,
bullets and numbers, paragraph reflow with de-hyphenation, ligatures, an
8% margin band that only applies once a page has enough lines to have a
header. `layout.rs` prints the same lines where they sit, one cell per
half-em, rows by baseline, blank lines by the space between them.

**A convention learned:** the text page's boxes are y-down. The first
draft assumed page space; the reading order of the fixture's links said
otherwise, and every comparison flipped.

**MinerU:** the rules are the ones its non-learned pipeline uses,
implemented from their description; no code was copied (DEPS.md, and the
crate's README credit the method).

**Tests:** unit tests over synthetic lines for every rule, the renderer's
block kinds, and the RFC base64 vectors are elsewhere; three tagged
fixtures with provenance pin the tree tier, the unclaimed-text rule, and
`--layout` keeping the same words with columns placed.

## Phase 5 — forensics and polish

### `security encrypt` (kept by the user, 2026-09-05)

AES-256, revision 6 only. `pdfrum-crypt` gained `standard_r6`: ISO 32000-2
algorithms 8, 9 and 10 written as the inverse of the checks the crate
already made when opening such a file — `/U`, `/UE`, `/O`, `/OE`, `/Perms`
from the same `revision6_hash` and AES primitives, and the handler handed
back is built from the dictionary through `from_encrypt_dict` with the
owner password, so what was written is what a reader will verify.
Randomness is the caller's 64 bytes (file key and four salts), and
`IdSource::entropy` derives them — fresh from the OS for `Random`, a
fixed hash chain for `Fixed`, so `--deterministic` gives byte-identical
encrypted output. `pdfrum-edit`'s `SaveOptions::encrypt` (and the
facade's) carries `Encryption { user_password, owner_password,
permissions, encrypt_metadata }`; a document that already has a handler
is refused (`EncryptedSaveUnsupported`): decrypt, then encrypt. Save
options are no longer `Copy`, since one can now carry passwords.

**Tests without an oracle, then with one.** The edit crate round-trips
through its own parser: either password opens, a wrong one does not, the
permissions come back as asked, the content stream decodes to the same
bytes, the plaintext is absent from the file, a fixed seed is
byte-identical, re-keying is refused. Then the oracle: `pdfium_test
--password` extracts the same text from the locked file as from the plain
one — the test runs when `PDFRUM_ORACLE_CHECKOUT` is set and skips with a
message otherwise. The command: `security encrypt --user-password
--owner-password --allow print,copy,… --plain-metadata`.

### The rest of phase 5 (2026-09-05)

**Facade fills first**, as the rule says: `Document::stream_data` (a
stream's decoded bytes by reference), `Document::embedded_fonts`
(`EmbeddedFontFile { name, kind, object, data }` with `FontFileKind::{Type1,
TrueType, Cff, OpenType}` and its `extension`/`name`),
`Document::revisions` / `revision_bytes` (the `/Prev` chain as the parser
walked it, each revision's cross-reference offset, whether it was a stream,
and where its `%%EOF` ends — `pdfrum-parser`'s `Xref` now records its
`sections` on the way through the chain), `Page::images` (`PageImage`
with the decoded pixmap and, when the stream's only filter is an image
codec, the raw bytes under `RawImage { data, encoding }`),
`Page::structure` (the page's `StructTree`, and `Kid`/`StructElement`
re-exported), plus `Object`, `Dict`, `Name`, `PdfString`, `Array`,
`Stream`, `XrefEntry` and `Section` on the facade for a client that prints
syntax.

**Commands.** `extract images -o DIR` writes JPEG, JPEG 2000, JBIG2 and
CCITT data as it is in the file — the `pages create` JPEG comes back byte
for byte — and decodes everything else to PNG; masks are marked. `extract
fonts -o DIR` writes each program under its base name and object number
with the extension its format takes. `inspect object N [G] [--decode]`
prints one object in canonical PDF syntax (`syntax.rs`: names `#`-escaped,
strings with the four escapes or hex as the file had it, reals with the
shortest round-tripping digits, streams as their dictionary and a length)
or a stream's decoded bytes. `inspect xref` lists every entry — offset,
in-stream with the container and index, free — and the trailer's
effective keys (the parser keeps a chain's duplicates as the file wrote
them; the printer and the digest ask for the last value of each).
`inspect revisions` and `inspect revision --rev N -o` expose the update
history and cut an earlier file out whole. `inspect structure` walks the
tree with marked-content ids, `/Alt` and `/ActualText`. `diff A B` is a
longest-common-subsequence over each page's non-blank lines, `--visual`
renders both and counts differing pixels with their bounding box, writing
`diff-<n>.png` (changes in red over the faded page) when asked; exit 1 on
any difference, the way `diff` and `cmp` do. `hash` prints the file's
SHA-256, the trailer's `/ID` pair, and a semantic digest over the
canonical dump of every object in number order with `/ID`, the `/Info`
dates and the XMP `/Metadata` stream masked and stream data included —
two rewrites of one document with fresh `/ID`s hash the same.
`completions <shell>` and `manpage -o DIR` come from the clap tree itself
(`clap_complete`, `clap_mangen`; clap's own `help` gets no page).

**Fixtures** (`tests/fixtures/PROVENANCE.md`): `rotated_image.pdf`
(Flate image → PNG), `bug_674771.pdf` (a mask), `bug_1484283.pdf` (two
revisions, table then stream, one object in an object stream),
`bigtable_mini.pdf` (CFF), `bug_488948351.pdf` (TrueType). Ten tests
pin the text output against expected files and the JSON keys, the JPEG
round trip, the first revision being the file's first 633 bytes and
opening on its own, the diff's exit code and picture, the semantic hash
surviving a rewrite, and the generated completions and pages.

## Close

M19 MET 2026-09-05: five phases, every command in `docs/design/pdfrum-cli.md`
§9's kept scope, each on a facade fill that a `cargo add pdfrum` user has
too. Not built, by decision: linearization (M16), date stamping, luminance

### Output style (2026-09-05, after the user tried the tool)

The user's verdict on the first walk-through: too inconsistent — colours
per command, layouts per command, wording per command. The rules are now
`docs/design/cli-style.md`: stdout/stderr split, a palette of eleven
colour roles and nothing painted outside them, four layout forms (record,
table, section, summary), one wording for an empty answer, human sizes,
no emoji anywhere. `out.rs` grew `record`, `Table` (header row, alignment,
empty columns dropped, escape-aware widths), `heading`, `summary`, `none`
and `bytes`; `term.rs` replaced the raw `sgr` with `paint(Style, …)`.
Every printer was rewritten onto them and every expected file
regenerated and read.

### Reading objects, and what an image list is for (2026-09-05)

Two more findings from the walk-through. `inspect object` was a plain
dump nobody could read: it is now highlighted through the palette (keys
dim, names and references cyan, framing bold) and every top-level
reference carries a `% …` hint naming what it points at — `/Pages 2 0 R
% Pages`, `/Info 196 0 R  % dict, 8 keys` — resolved one level, so the
dump answers the next question without a second command; the trailer in
`inspect xref` gets the same, and the cross-reference table a WHAT
column (`Catalog`, `Page`, `Font Type1`, `ObjStm, stream raw 78 B`). The
hint is plain text, so a pipe sees it too; only the colour is terminal.

`extract images` listed every draw: 301 rows of a two-pixel spacer for
one corpus file. It now lists pictures — one row per image `XObject` with
a USES count for repeats, images under four pixels on a side left out —
and `--all` gives the per-draw list back. Written files are numbered by
that row.

### The pager, after use (2026-09-05)

Three complaints from the user's first session in `view`: a page change
froze the tool while the page rendered, the picture sat at the left edge,
and nothing said where in the document one was. Now: a render thread
(scoped, borrowing the `Document`, which is `Sync`) takes frame requests
over a channel and fills a cache keyed by page, zoom and screen size; on
every keypress the pager asks for the current page and its neighbours
(next, previous, next-but-one), so the common `j`/`k` shows a cached
frame at once and only a jump waits, with `rendering` on the status row
while it does. Frames fit the screen at zoom 100 — width less one
column, height less the status row — using the cell size in pixels the
terminal reports (kitty, WezTerm, Ghostty, iTerm2) or 8x16 when it does
not, and are centred: the pixel protocols by cursor position, the
half-block rows by a margin. The status row is pinned to the last line
and reads `page 3/11  zoom 100%  j/k next/prev  g/G first/last  +/- zoom
/ find  q quit`; arrows, `h`/`l` and `0` (reset zoom) work too. The
layout arithmetic is unit-tested; the terminal itself is not, so the
user's next session is the test.

**Second pass, same day: "still not very smooth".** The render cache was
not the bottleneck; the terminal traffic was. Each keypress cleared the
screen and re-sent the whole picture — on the kitty protocol a few
hundred KB of base64 per page, every time — so the eye saw a blank, then
a page arriving. Now a frame is drawn inside a synchronized update
(DEC 2026) with no full clear, only the rows below the picture wiped; on
kitty each page is transmitted once under an id (`a=t`) and thereafter
placed with a twenty-byte command (`a=p`), the previous placement taken
down by id, and the neighbouring pages are transmitted while the pager
waits for a key, so the next `j` is a placement, not a transfer; frames
that fall out of the cache are deleted from the terminal too (`a=d`).
Half-block and iTerm2 output keep their inline bytes but gain the
synchronized update and the no-clear draw.

**Third pass: two bugs the user hit at once.** `q` froze the tool: the
scoped render thread blocks on the request channel, and the sender was
dropped only after `thread::scope` had already joined it — a deadlock
that raw mode made unescapable (Ctrl-C is a keypress there). The sender
now lives inside the scope and is dropped, with a stop flag set, before
the scope ends. And the status bar crept down one row per page: the
picture ran one row past its computed height when the terminal's cell
size differed from the estimate, the cursor fell off the bottom and the
screen scrolled. Kitty placements now name their cell box (`c=`, `r=`)
and leave the cursor alone (`C=1`), iTerm2 images are sized in cells,
half-block rows are cut at the bar, and the bar itself stops one cell
short of the last column so the pending-wrap can never fire.

### Plain words, and links you can see (2026-09-05)

Two more from the user. Column headers and record keys carried the
specification's abbreviations — `OBJ`, `GEN`, `PLACE`, `XREF`, `MCID`,
`@471` — which mean nothing to someone who has not read ISO 32000; they
are plain words now (`OBJECT`, `WHERE` with `byte 471`, `CONTENT ID`,
`document id`, `table`), the generation column appears only when a
generation is not zero, and the rule is in the style guide §4. And links
were invisible in VS Code's terminal, which marks OSC 8 links only on
hover: link text is now underlined in the identifier colour whenever
colour is on (`Style::Link`), so a link reads as one at rest.

### JavaScript behind a feature (2026-09-05)

The user asked how to try the scripts and there was no way from the
CLI; the design had reserved a `javascript` feature and nothing was
wired. Measured first: the engine is 133 → 270 crates and 9.0 → 21.1 MB
stripped on the tool, so it stays a feature, off by default, as in the
facade. The facade fill is `FormSession::open_document` — the open-time
walk the tool had kept to itself: `/Names /JavaScript` by index, then a
dictionary `/OpenAction` and its `/Next` chain, each once, `/Named`
actions recorded — and `script_failures` to report what threw. The CLI
gains `scripts run FILE [--time] [--json]` (the transcript, a raw
stream, diffable against PDFium's `_expected.txt`) and `forms fill
--scripts` (save, then open the saved file as a viewer would and write
back what the scripts assigned). Found on the way: `Action::javascript`
read a script stream's raw bytes, so a script survived only until the
first save Flate-encoded it; it now decodes the filter chain as
`CPDF_Stream::GetUnicodeText` does. A second bug fell out of the same fixture: a text field that already
carried `/V ()` — the shape every authoring tool writes — kept it through
`forms fill`, which reported the field set; the merged field-and-widget
edit folded the widget's untouched copy back over the edited dictionary
and the old `/V` won (`pdfrum-doc` `form::apply`). The widget's edit now
starts from the edited dictionary, the fold is gone, and a facade test
pins the round trip. Fixtures: two PDFium transcripts the engine already
matches and one hand-written open-action form; the gate runs the CLI
tests with the feature on.


### Markdown, second look (2026-09-05)

The user put `extract markdown` beside MinerU on the Foxit quick-start
guide (`text_quick_start.pdf`, tagged) and the PhantomPDF products sheet
(`text_foxit_products.pdf`, untagged) and found it "really not good". It
was; the defects were in the crate, not the text page, and each had a
number behind it.

*Orientation.* The text page's boxes are PDF user space, y up: three
consecutive body lines of the products sheet sit at y 709.7–718.8,
694.1–703.2 and 678.5–687.6 on an 841.68 pt page. `heuristics::continues`
had assumed y down, so no wrapped line ever joined its predecessor and
the sheet came out one paragraph per line; `layout` sorted rows by
ascending y, so `--layout` printed the page bottom first, the footer on
top. Both read y up now, and a unit test at those coordinates joins the
three lines and keeps a line thirty points lower apart.

*Size.* The sheet sets `Tf 1` and sizes its text through `Tm` (scales of
10.56 and 13.92), so every line was 1 pt to the crate: a 6.5 pt gap was
six line heights, every line a paragraph, no line a heading.
`Line::font_size` is now the size drawn — the font size in force times
the matrix's y scale. The sheet's 43 lines are four paragraphs and a
`##`. What it still gets wrong: "Business Ready PDF – Robust and Secure"
is set in the same Calibri at the same size with the same render mode as
the body under it, and nothing typographic tells them apart; that is the
layout model MinerU has and this crate does not.

*Repeats.* "Welcome to Foxit MobilePDF Welcome to Foxit MobilePDF" was
the tagged tier, not the lines: Word writes `Span(/ActualText …)` for a
run and then draws it again under the next `Span`; the extractor drops
the second drawn object as a repeat, so the first span keeps only its
`/ActualText` and the second its characters, and `text_of` appended
both. Element text is now assembled from pieces that carry their line
indices and boxes; a piece that says what the piece before it said, on
top of it or never drawn at all, is dropped. The line builder's own
check — the same character at the same place — was generalised from the
previous character to any earlier one on the line, boxes overlapping by
half or origins within a point.

*Spaces inside words.* "Local d ocuments", "Wi - Fi": `tagged::append`
invented a space at every kid boundary, and Word cuts its `/ActualText`
spans wherever kerning changes, mid-word. Pieces on one line are now put
end to end — the text page's spacing is the contract, and `text_by_mcid`
no longer trims it away — and pieces on different lines meet across the
break with a space or a de-hyphenation; an `/ActualText` replaces what
its element drew but keeps the whitespace at the drawn text's edges.

*Leaders.* Word draws a contents line as three or four 32-dot spans;
five or more dots, spaces between allowed, are a leader and become
` ... `: "Different Views ... 2". Three dots is an ellipsis and stays.

*Headers and footers as headings.* On the guide's page 1 the running
title sits at y 795–805 and 776–786 and the folio `1 / 11
www.foxitsoftware.com` at 69.5–79.7 on an 841.92 pt page, and the
structure tree claims none of them. The 8% band (67.4 pt) missed the
footer; the three leftovers went to typography alone, fell under the
"fewer than four lines" rule and came out as three `###`, on every page.
The band is 10%; a line in it goes when it looks like a folio (every
word a number, a punctuation mark, a URL, or `page`/`of`), or is short
and stands apart from the body, or is short and beside a line that goes
— the guide's page 2 has "Quick Guide" twelve points above the `H1`,
closer than it stands apart, but beside "Foxit MobilePDF", which does.
The leftovers of a tagged page are now judged among all the page's lines
(`heuristics::blocks_among`), so a header is a header even when the tree
took the body. The guide went from 41 headings to the eight `H1`
sections it has. What one page cannot see is the same line in the same
band on the next page; that needs a document-level entry point the crate
does not have.

*Bullets.* Word draws its bullet as a Symbol-font glyph with no Unicode
(U+F0B2 here) into the list body, and the item came out as `- ` plus an
invisible character. Any private-use character at the head of a line
followed by a space is a bullet, in both tiers.

*Faux bold.* A text object filled and stroked (`2 Tr`) now votes bold
along with a font name that says so. The products sheet does neither
for its headings, so it gained nothing there; it is right in general.

Not changed: the image placeholder is still `![alt](image)` with the
tree's alternative text; the CLI's `-o DIR` needs an image index on
`Block::Image` to number and name the files.

Expectations that move with the orientation fix and are the CLI owner's
to regenerate: `crates/pdfrum-cli/tests/expected/layout_weblinks.txt`
(the rows reverse — `weblinks.pdf` draws "Hello, world!" at y 50, the
bottom), and the same test's assertion that `--layout` and plain text
have the same words in the same order, which was only ever true with
the rows upside down. The `pdfrum-markdown` API baseline moves too
(`Line::segments` is a `Vec<Segment>` with a box per stretch,
`McidText::runs`, `heuristics::blocks_among`).

### Markdown, paragraphs (2026-09-05)

The second look left the products sheet over-merged: with the gap rule
reading y up, the sheet's feature items — `XFA Form Filling - XFA (XML
Form Architecture) form allows …`, `High Performance - Up to 3 times
faster …`, one after another at the body's normal line pitch — joined
into one paragraph per section, 23 text lines against the Python MinerU
reference's 225 (the one-paragraph-per-line state before it had been 23
as well). Two rules now decide within the gap, in `heuristics`:

*Ragged right.* A line that stops short of its column's right edge is
its paragraph's last — the rule every layout engine applies to justified
and left-aligned prose. The edge is the furthest right any body line
sharing the line's left edge (within a character width) reaches; short
is more than two character widths, 0.9 × the font size each, before it;
and the rule fires only when the next line opens with a capital or a
digit, so a justified paragraph's short last line met by a lower-case
wrap still joins, and `(32-bit` / `& 64-bit).` still joins. On the
sheet the column's edge is 507.6 and the items end at 493.8, 363.7,
298.8, 172.7; the two that end within two characters of the edge
(`… existing XFA forms.` at 493.8, `… from PDF documents.` at 499.9)
are split by the next rule.

*Lead-in.* A line whose head is drawn bold and turns plain, or whose
first six words at most are a capitalised phrase — the first word and at
least half of them — closed by ` - ` or ` – `, begins a paragraph
whatever the gap. `Line` carries `bold_prefix`, the bytes at its head
drawn bold, and a paragraph that opens on one is written
`**Redaction** - Lets you …`: the marks are the crate's own and the one
piece of markup a `Block::Paragraph` holds, `ast::lead_in` takes them
apart, `render` escapes the page's text on either side, and
`Block::text` gives the words without them. The items stay paragraphs;
the reference does not make them a list. The sheet itself draws no bold,
so only the dash form fires on it.

Products sheet, 0.972 word similarity before and after (the script
strips the paragraph breaks it is measuring); 7 headings and 23 text
lines before, 7 and 265 after, against the reference's 8 and 225. The
excess is the "Features & Benefits" pages, where the reference joins a
feature's name to the benefit under it and each is a short line of its
own here, and paragraphs that cross a page break. The guide is byte for
byte what it was: 0.953, 8 headings, 85 text lines against 19 and 90.
Both are integration tests now (`tests/corpus.rs`, the facade as a
dev-dependency the way `pdfrum-text` has it), with the synthetic cases
in `heuristics`: a short line then a capital splits, a short line then a
lower-case wrap joins, a capital after a full-width line joins, seven
capitalised words before a dash is a sentence, and bold throughout is a
bold paragraph rather than a lead-in.

### Markdown, images and running headers (2026-09-05)

The two items the paragraphs pass left open.

*Images.* `Block::Image` carries `index`, the image's place among the
page's images in drawing order — the order `Page::images` lists them in;
`lines::collect` and the facade's `collect_images` walk the graph the same
way, a form's images where the form is drawn. A tagged page's `Figure` is
the first image drawn under a marked-content id it names: Word draws the
guide's figures as `/P <</MCID 101>> BDC q … /Image80 Do Q EMC`, and the
id was already on every image object's `marks`; `ObjectFacts` now records
the images as it walks, with their ids and boxes. A figure that drew no
image keeps its alternative text and `index: None`. An image the tree puts
in no figure — the guide's bullet under a `P`, its banner — is not read;
the tree said what the page's pictures are. The untagged tier gains images
too: one drawn at least 4 pt on each side (a rule or a spacer is narrower)
is placed before the first line below its centre that it overlaps across,
and ends the paragraph or list that was open. `render_with_images` links
each block where the caller says; `render` keeps `![alt](image)`.

The graph the facade read Markdown from was built with
`RequestedSize::NoSamples`, which emits no image object at all; it is
built with `Reduced { width: 1, height: 1 }` now — one pixel, enough to
carry each image's place and id. A no-samples build that still emitted
the object would remove that decode; that is a `pdfrum-page` change and
was not made here.

CLI: `extract markdown FILE -o DIR` writes every image the Markdown shows
as `DIR/<stem>-p<page>-<n>.<ext>` — `n` the image's place on its page in
drawing order, the format `extract images`' rule through the same
`write_image` — and links it; without `-o` nothing changes. On the guide,
85 figures over eleven pages, all linked, none left as `image`, and page
2's first figure is the 1203x705 screenshot, `text_quick_start-p2-13.jpg`.

*Running headers.* `running::mask` over every page's lines: a line whose
centre is in the top or bottom 12% of its page, keyed by band and by its
text with each run of digits made `#` (`Page 3 of 11` → `Page # of #`,
`3 / 11 www.foxitsoftware.com` → `# / # www.foxitsoftware.com`), found on
three pages or more and on more than half of them, goes from every page
before either tier reads it. `document_blocks(pages, …)` is the entry
point; the facade's `Document::markdown_blocks(pages)`, `markdown_pages()`
and `markdown()` — the `---`-joined string the CLI prints — sit on it, and
`Page::markdown` is unchanged. The CLI reads more than one page as a
document and a single page as a page. On the guide the rule marks exactly
three lines on each of the eleven pages — `Foxit MobilePDF`, `Quick
Guide`, `N / 11 www.foxitsoftware.com` — and nothing on two pages of it;
the second look's per-page rule had already dropped all three, so the
guide's Markdown is byte for byte what it was, and so is the products
sheet's. `hello_world_2_pages.pdf` goes through the document path now and
its expected output did not move.

Numbers, by word-level `difflib` against the `MinerU` references with
image lines dropped (the paragraphs pass's script was not recorded, so
its 0.953 and 0.972 are not this script's): guide 0.915 before and after,
8 headings and 85 text lines against 19 and 90; products sheet 0.970
before and after, 7 and 265 against 8 and 225. The guide shows 85 image
lines against the reference's 23: `MinerU` drops the eighteen-pixel icons,
the tree calls each one a figure.

Surface: `Page::markdown_blocks`, `Document::{markdown, markdown_pages,
markdown_blocks}`, and `pdfrum::markdown::{render, render_with_images}` —
the facade's first nested module, the two functions a holder of `Block`s
needs and nothing else of the crate; flat names would do as well if the
module reads wrong. In the crate: `Block::Image::index`, `DrawnImage`,
`ObjectFacts::images`, `tagged::Drawn`, `heuristics::blocks` and
`blocks_among` taking the images, `running`, `PageInput`,
`document_blocks`, `render_with_images`.
