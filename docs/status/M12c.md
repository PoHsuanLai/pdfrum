# M12c — GPU backend: `vello` on `wgpu`

**Updated:** 2026-08-31 · **State:** landed. **§10 is the verdict; read it and
§1 if you read nothing else.**

PLAN.md §M12c is the assignment. This document is written in M12.md's register:
hypothesis, method, measurement, verdict, **including the non-results**. A claim
a later measurement refutes is withdrawn in place with the measurement that
refuted it, never deleted. Three are withdrawn here: the milestone's own version
premise (§1), an early claim that the GPU tree had no build dependencies (§2),
and this document's first mapping of alpha masks onto vello's layer model,
which a GPU test proved inert (§4.2).

The short version: the backend renders all 44 corpus documents with **zero
Tier-C interior differences**, is **2.64x slower than `vello_cpu` on
rasterization** overall while being **4.8x faster on the heaviest vector page**,
and its isolation from the core ring is a committed CI check verified by
negative control. The exemption that paid for it, however, **cannot currently
be spent**: vello 0.10 pins `wgpu` 29 and no released Rust GUI frontend is on
it.

The milestone's two non-negotiables frame everything below:

- **Isolation.** `pdfrum-raster-vello-gpu` is its own crate that nothing in the
  core ring depends on. A headless build must resolve a tree with zero `wgpu`,
  and the proof is a committed CI check rather than a sentence here.
- **Device injection, not device creation.** The primary constructor borrows a
  caller-supplied `wgpu::Device` and `Queue`.

## 1. The version premise is wrong, and it blocks the milestone's own argument

This is the milestone's headline finding and it is not a pin correction. Read
this section before §8's numbers: **device injection is implemented, tested and
working, and there is currently no released Rust GUI frontend it can accept a
device from.**

### 1.1 What was claimed, and what is true

**PLAN.md §M12c states: "`vello` 0.10 targets `wgpu` 30, which is current, so
the shared-device story with today's frontends is real rather than a
version-skew fight." Checked 2026-08-31 against crates.io: this is false.**

```
$ cargo add vello@=0.10.0 wgpu@=30.0.1        # in a scratch crate
$ grep -A2 'name = "wgpu"' Cargo.lock
name = "wgpu"  version = "29.0.4"
name = "wgpu"  version = "30.0.1"
```

Two `wgpu` versions resolve, because `vello 0.10.0` depends on `wgpu` **29**.
`vello` 0.10.0 is the newest published `vello` — the version list ends there —
so no vello release targets `wgpu` 30 today.

### 1.2 Why that is fatal to the argument rather than awkward for it

PLAN.md justifies relaxing the pure-Rust guarantee on one specific claim, and
the commit that promoted this milestone states it in as many words: pdfrum's
likely consumer is a Rust GUI frontend, "so in that process wgpu is already in
the dependency tree and a device is already open." **The whole exemption is
bought with that sentence.** If the device cannot actually be handed over, the
exemption buys a backend that opens a second device — which is precisely the
waste the milestone says it exists to avoid.

Two `wgpu` majors in one tree are not merely awkward; they are unrelated types.
Compiled rather than reasoned about:

```rust
// a crate depending on vello =0.10.0 AND wgpu =30.0.1
pub fn inject(device: &wgpu::Device) -> Result<vello::Renderer, vello::Error> {
    vello::Renderer::new(device, vello::RendererOptions::default())
}
```

```
error[E0308]: mismatched types
  |     vello::Renderer::new(device, vello::RendererOptions::default())
  |     -------------------- ^^^^^^ expected `vello::wgpu::Device`, found `wgpu::Device`
note: there are multiple different versions of crate `wgpu` in the dependency graph
```

There is no conversion, no trait, and no unsafe transmute that would be sound —
the layouts are unrelated. The frontend either matches vello's major or cannot
participate.

### 1.3 Which frontends match: none of the three PLAN.md names

PLAN.md names egui, iced and dioxus. Their published `wgpu` requirements,
resolved against crates.io on 2026-08-31:

| Frontend | latest | requires `wgpu` | matches vello 0.10's 29? |
|---|---|---|---|
| `egui-wgpu` / `eframe` | 0.36.1 | `^30.0` | **no** — one major ahead |
| `iced_wgpu` | 0.14.0 | `^27.0` | **no** — two majors behind |
| `dioxus` | 0.8.0-alpha.1 | (pre-release) | not assessed |
| `vello` | 0.10.0 | `29` | — |

**Not one of them matches.** This is worse than the single-version skew the
title of the earlier draft implied: `wgpu` 29 is not "the old version the
ecosystem is moving off", it is a version *between* two frontends that are
themselves a major apart. vello sits in a gap.

### 1.4 The honest statement of what this backend delivers

Stated plainly, since the milestone asked for it plainly:

- **Device injection works, and is the primary constructor.**
  `VelloGpuBackend::new(&Device, &Queue)` is implemented, is what every test
  and benchmark uses via `request_adapter`, and is not a stub.
- **It works today only for a caller on `wgpu` 29** — one that depends on
  `pdfrum_raster_vello_gpu::wgpu` (re-exported for exactly this reason) or
  independently pins 29.
- **For an egui or iced application today, the shared-device story does not
  work.** Such a caller must either hold its whole graphics stack back to
  vello's `wgpu`, or let this backend open its own device — which is the cost
  the exemption was granted to avoid.
- **The block is upstream and the fix is a version bump, not a redesign.** When
  vello publishes against `wgpu` 30, the pin in `Cargo.toml` is the only line
  in this workspace that changes, and egui becomes a matching consumer that
  day. Nothing in the backend's structure assumes 29.

So the exemption's *cost* is being paid now and its *benefit* arrives on
someone else's release schedule. That is a real finding about the milestone's
premise and PLAN.md §M12c is amended to say so, rather than left claiming the
skew is not a fight.

### 1.5 What follows for this crate

- Pin `wgpu` transitively through `vello = "=0.10.0"` rather than depending on
  `wgpu` directly, so the two can never disagree in our own manifest.
- **Re-export vello's `wgpu`** as `pdfrum_raster_vello_gpu::wgpu`, so an
  embedder can see which one they must hand us instead of discovering it from
  a type error.
- Keep `request_adapter()` — the device-creating path — genuinely supported
  rather than a token fallback, because until the upstream bump it is the path
  most real callers will actually be on. It is still not the primary
  constructor, and it still says loudly that it leaks.

## 2. The pure-Rust tree, measured rather than assumed

DEPS.md's guarantee is enforced by `cargo-deny` bans on `cc`/`cmake`/
`pkg-config`/`bindgen` plus `scripts/ci.sh`'s `cargo tree` grep for `*-sys`.
The GPU tree was measured against both.

- **85 crates** in the normal dependency tree of `vello 0.10` + `wgpu`; 111 in
  the crate as built here.
- **Two `-sys` crates**, which `scripts/ci.sh`'s grep rejects: `renderdoc-sys`
  and `wayland-sys`. Both are `dlopen`-style declaration shims. §4.4 records
  how the check is scoped so the guarantee stays mechanically enforced
  everywhere else.

**Withdrawn in place.** An earlier revision of this section stated: *"Build
dependencies: none of `cc`, `cmake`, `pkg-config`, `bindgen`. No C is compiled.
The `cargo-deny` bans therefore need no exception at all."* The first sentence
is **false** and the claim is withdrawn. It was measured with `cargo tree -e
normal`, which excludes build dependencies — the exact category the sentence
was about. Running `cargo deny check`, which does not make that mistake, fails:

```
error[banned]: crate 'pkg-config = 0.3.34' is explicitly banned
  pkg-config <- (build) wayland-sys <- wgpu-hal <- wgpu <- vello
  pkg-config <- (build) khronos-egl <- wgpu-hal <- wgpu <- vello
error[rejected]: hexf-parse 0.2.1 — license CC0-1.0 not allowed
  hexf-parse <- naga <- wgpu-core
error[rejected]: libloading 0.8.9 — license ISC not allowed
  libloading <- ash <- gpu-allocator <- wgpu-hal
```

All of these arrive **only** through `pdfrum-raster-vello-gpu`; no other
workspace crate reaches any of them.

Note that `cargo tree` shows only the `wayland-sys` parent and `cargo-deny`
shows both: `cargo-deny` resolves across all target platforms by default and
`cargo tree` resolves for the host. **The tool that found the second parent is
the tool that was not making the first mistake either**, which is the argument
for gating on `cargo deny` rather than on a `cargo tree` grep.

The *conclusion* the withdrawn sentence drew — that no C is compiled — turns
out to survive, but for a narrower and more fragile reason than "there is no
build script". In both cases `wgpu-hal` selects a feature that turns the probe
off:

- **`wayland-sys`** is built with **`dlopen`** (measured:
  `wayland-sys v0.31.11 client,dlopen,egl,once_cell`), and its `build.rs`
  opens with `if CARGO_FEATURE_DLOPEN { /* Do not link to anything */ return; }`
  — so its four `pkg_config::Config::probe` calls never run.
- **`khronos-egl`** is built with **`dynamic`, not `static`** (measured:
  `khronos-egl v6.0.0 1_0,…,default,dynamic,libloading`), and its entire probe
  is `#[cfg(all(feature = "static", not(feature = "no-pkg-config")))]` — so
  `pkg_config` is not even compiled into the build script.

`pkg-config` is therefore in the graph and does nothing in it. That is a
materially weaker guarantee than "the crate is not there", because it rests on
a feature resolution a future `wgpu-hal` could change — so it is recorded as a
*scoped, named* exception (§4.4) rather than waved through, and the two
features it rests on are written down here so a reader can re-check them.

The licence rejections are not about C at all: `CC0-1.0` and `ISC` are both
permissive and OSI/FSF-recognised; neither was in `deny.toml`'s allowlist
because nothing in the tree had needed them before.

64x64 `Rgba8Unorm` storage texture, `copy_texture_to_buffer`, `map_async`,
readback — returns `[255, 0, 0, 255]` at the centre and `[255, 255, 255, 255]`
at the corner. So the full pipeline this milestone needs (scene → GPU →
texture → host) works on this machine before a line of the backend existed.

## 4. Where the trait and vello's scene model actually differ

The brief calls the mapping "largely mechanical" for the six primitives and
names three places where it is not. Reading `vello 0.10.0`'s `Scene` against
`RenderDevice` found the mechanical half is indeed mechanical and the
non-mechanical half is *structural*, in a way the `vello_cpu` backend does not
prepare you for.

### 4.1 Clips and layers are one stack, not two

`pdfrum-raster-vello`'s `VelloDevice` carries a `Vec<Frame>` because `vello_cpu`
keeps clips and layers on **separate** stacks and each `pop` must name which.
GPU `vello` has the opposite shape: `Scene::push_layer`, `push_clip_layer` and
`push_luminance_mask_layer` all push onto **one** stack, all are undone by the
same `pop_layer`, and — the part that matters — **every layer carries a clip
shape**. There is no "layer without a clip" and no "clip without a layer".

That makes `RenderDevice`'s two-stack contract *easier* to satisfy here, not
harder, and the `Frame` bookkeeping is unnecessary:

- `push_clip(path, rule)` → `push_clip_layer(Fill::from(rule), IDENTITY, path)`
- `push_clip_rect(rect)` → the same with the rect as the shape
- `push_layer(blend, alpha, None)` → `push_layer(Fill::NonZero, blend, alpha,
  IDENTITY, <full device rect>)` — a layer whose clip is the whole target
- `pop()` → `pop_layer()` in every case

The one thing that must not be lost is that vello's docs state plainly that
**the transform is not saved or modified by the layer stack**: the `transform`
argument applies to the clip *shape only*. Our clips already arrive in device
space (`clip::push` transforms them before the call), so identity is correct
and this is a non-issue — but it would silently double-transform every clip on
a backend that tried to be clever about it.

### 4.2 There is no arbitrary alpha-mask layer, and that is the real gap

`RenderDevice::push_layer` takes `Option<&AlphaMask>` — a device-sized plane of
8-bit coverage the engine computed. `vello_cpu` consumes exactly that
(`Mask::from_parts`). **GPU vello has no equivalent.** Its only masking layer is
`push_luminance_mask_layer`, where the mask is *content drawn into the scene*
between the push and the pop, and where the luminance is taken with vello's own
coefficients rather than the NTSC ones the oracle's soft masks use — the same
trap `pdfrum-raster-vello` documents about `Mask::new_luminance`.

So a supplied `AlphaMask` has to be turned back into drawable content, expanded
to RGBA where `R = G = B = m` and `A = 255`. The byte survives exactly because
vello's luminance of a neutral grey is `luma(m, m, m) == m` under any
coefficient set whose weights sum to one — the BT.709-versus-NTSC question only
has an answer for *coloured* mask content, and ours is neutral by construction.

**Withdrawn in place: the ordering above was wrong, and a GPU test caught it.**
The first implementation followed the reading written here — push the luminance
layer, draw the mask, pop, *then* push the real layer:

> 1. `push_luminance_mask_layer(NonZero, 1.0, IDENTITY, <device rect>)`
> 2. draw the mask plane as an image at identity
> 3. `pop_layer()` to end the mask, then `push_layer(...)` for the real layer

That reads as "establish a mask, then draw under it", which is how
`vello_cpu`'s `Mask` argument behaves and is why the mistake was easy. It is
not what vello does. `Scene::push_luminance_mask_layer`'s own documentation
says the content drawn inside it "will serve as a luminance mask **for the
prior content in this layer**", and `DrawBeginClip::luminance_mask` confirms it
in the encoding: the mask is a *blend mode applied when the layer is composited
back*, not a state established before drawing. Encoding it first therefore
masks an empty layer and does nothing at all.

The symptom was unambiguous once it ran on hardware —
`a_device_sized_mask_halves_what_it_covers` read back alpha **255** where a
half-coverage mask must give roughly 128 — and it is exactly the class of
silent failure the trait's own doc comment warns about for a mismatched mask:
it fails *open*, producing unmasked output.

The correct mapping inverts the nesting and defers the mask to the `pop`:

1. `push_layer(NonZero, blend, alpha, IDENTITY, <device rect>)` — the real
   layer, pushed immediately so the engine's content lands inside it
2. …engine draws the layer's content…
3. at `pop()`: `push_luminance_mask_layer(...)`, draw the mask plane as an
   image at identity, `pop_layer()` — the mask now applies to the content that
   exists
4. `pop_layer()` for the real layer

which still costs one extra layer and one image upload per masked layer, but
cannot be encoded at `push_layer` time because *the content it masks does not
exist yet*. That is why `VelloGpuDevice`'s frame stack holds a value
(`Frame::Masked(ImageData)`) rather than a count: the mask rides on the frame
until its `pop`. The corrected version passes on hardware; the unit test
`a_mask_is_carried_to_the_pop_rather_than_encoded_at_the_push` pins the
ordering so a future simplification cannot quietly restore the broken one.

**This is the milestone's clearest argument for testing a GPU backend on a
GPU.** Every structural check — that the mapping compiles, that the frame
counts balance, that the mask converts to the right bytes — passed on the
broken version. Only running it found that the whole construction was inert.

**Measured relevance, recorded so the work is sized honestly:** the engine
currently passes `None` at all four of its `push_layer` call sites
(`walk.rs:573, 1569, 1717, 1846` — all `(blend, 1.0, None)`), because soft
masks are applied *by the engine* to a readback pixmap
(`pixels.multiply_alpha_mask`) rather than handed to the device. So this path
is dead on today's engine. It is implemented anyway, and tested directly,
because a backend may not assume a caller's current habits — but no corpus
number below exercises it, and that is stated rather than implied.

### 4.3 Retained scene, immediate readback: the offscreen-target problem

This is the finding that most shapes the performance envelope, and it is not
one of the three the brief listed.

`RasterBackend` is a *factory of targets*, and the engine uses it heavily: a
transparency group, a soft mask's group, every tiling-pattern cell, the mesh
scratch buffer and the fill+stroke knockout buffer each get their own
`new_target`, are drawn into, and are then read back as a `Pixmap`
(`walk.rs:138, 519-523, 616, 1393, 1501, 1556, 1786, 1834, 1934`;
`paint.rs:280`; `pattern.rs:539`). On CPU a target is a buffer and `finish` is
a rasterize. On GPU each one is a texture allocation, a full `Renderer`
dispatch, a `copy_texture_to_buffer`, and a **`map_async` round trip that
stalls the host on the GPU**.

`new_target_with_backdrop` and `snapshot` make it worse in the same direction:
`snapshot` reads pixels *back* mid-page, and `new_target_with_backdrop` then
uploads them again as a starting image. A page with a non-isolated group pays
a full readback and re-upload at that point.

None of this is a defect in the trait — it is the CPU-shaped assumption that
a rendered surface is cheap to look at. It is *the* reason to expect the GPU
backend to lose on pages with many small offscreen targets and win on pages
that are one big scene, and §8's crossover is read in exactly those terms.
Fixing it properly means giving the engine a way to composite a group without
a host round trip, which is an engine change and explicitly out of scope here.

### 4.4 What the isolation and pure-Rust checks actually assert

PLAN.md demands the isolation claim be "a committed check, not an assertion",
and that any `cargo-deny` exception be scoped to this crate with its extent
stated. Both are landed.

**`scripts/check-no-wgpu.sh`** (run by `scripts/ci.sh`) asserts three things,
in the order a violation would arrive:

1. `pdfrum`'s default feature set reaches none of `wgpu`, `wgpu-core`,
   `wgpu-hal`, `wgpu-types`, `vello`, `vello_encoding`, `vello_shaders`. This
   is the claim an embedder cares about: `cargo add pdfrum` must not put a
   graphics driver in their tree.
2. `pdfrum-tool`'s default features likewise — the CLI is what a headless build
   runs.
3. **Every other workspace crate**, enumerated rather than spot-checked. This
   catches the realistic accident (a crate reaching for the GPU backend "just
   for a test") at the point where it is one line to undo.

Plus a fourth assertion that exists to keep the other three from going vacuous:
that `pdfrum-raster-vello-gpu` itself *does* still depend on `vello`. A check
that would pass if the backend quietly stopped using vello is measuring
nothing.

**Verified by negative control**, because a green check proves nothing until it
has been seen to go red. Adding `pdfrum-raster-vello-gpu` as a dependency of
`pdfrum-raster-exact` — a leaf backend, deliberately not the facade — was
caught on four crates at once:

```
error: the pdfrum facade (default features) reaches the GPU stack:
error: pdfrum-tool (default features) reaches the GPU stack:
error: pdfrum reaches the GPU stack:
error: pdfrum-raster-exact reaches the GPU stack:
```

The change was reverted and the check is green again. The propagation is the
point: one edge in a leaf reached the facade, which is exactly the failure mode
the rule exists to prevent.

**`cargo-deny`'s bans stay enforced everywhere else**, and the exception is
narrow in a specific way. `cc`, `cmake` and `bindgen` are **not** relaxed at
all — none of them is in the tree. `pkg-config` is banned as before except
through two named wrappers:

```toml
{ crate = "pkg-config", wrappers = ["wayland-sys", "khronos-egl"], … }
```

`wrappers` rather than a blanket allow, because the reason it is safe is a
property of *how `wgpu-hal` builds those two crates* (§2's measured features),
not of `pkg-config`. A third crate reaching for it fails the build, which is
what makes this an exception rather than a hole. Two permissive licences —
`CC0-1.0` (`hexf-parse`) and `ISC` (`libloading`) — are added to the allowlist
with their paths recorded in `deny.toml`.

`scripts/ci.sh`'s own `*-sys` grep exempts `renderdoc-sys` and `wayland-sys`
**by name**, not by pattern, for the same reason: a third `-sys` crate arriving
should be a decision someone makes deliberately.

All four `cargo deny` checks pass: `advisories ok, bans ok, licenses ok,
sources ok`.

## 5. What the backend implements, and what it deliberately does not

Working, and asserted on hardware by 13 integration tests in
`crates/pdfrum-raster-vello-gpu/tests/gpu.rs`:

- all six `RenderDevice` primitives plus `push_clip_rect`
- all four `RasterBackend` methods, including `new_target_with_backdrop` (the
  backdrop is encoded as the scene's first image, since
  `RenderParams::base_color` is a single colour and cannot carry one) and
  `snapshot` (which does not consume the target)
- all sixteen PDF blend modes, via the same `peniko::Mix` mapping the CPU
  backends use
- alpha-mask layers, by the deferred construction §4.2 arrives at
- a translucent `draw_image` **without** the opacity-layer wrapper
  `pdfrum-raster-vello` needs: `vello_cpu 0.2.0` panics on
  `ImageSampler::alpha != 1.0`, whereas GPU vello encodes it as an 8-bit
  multiplier in the draw tag (`vello_encoding::Encoding::encode_image`). A test
  pins that, so re-adding the wrapper "for symmetry" would be a deliberate
  rounding change rather than a tidy-up.
- an unbalanced page (layers left open by damaged content) closed at `finish`
  rather than handed to vello malformed
- non-256-multiple widths read back unsheared — `wgpu` requires a
  texture-to-buffer copy's `bytes_per_row` to be a multiple of 256, so a
  100-pixel row is copied at a 512-byte stride and must be un-padded. Missing
  that shears the image diagonally, which looks like a rasterizer bug and is
  not one.

### 5.1 `AntiAlias` has no per-primitive expression, and this is a stated divergence

`RenderDevice::AntiAlias` has three variants because AGG has three, and the
distinctions are load-bearing on the CPU side: `Off` is the oracle's
`aliased_path` (coverage thresholded `> 127 → 255`), and `FullCover` keeps the
rasterizer's choice of covered pixels while discarding their coverage value —
which is what stops a subdivided Coons patch showing white pin-holes along
every internal seam.

`vello_cpu` expresses both exactly through `set_aliasing_threshold`
(`Some(128)` and `Some(1)`). **GPU vello has no equivalent.** Antialiasing is
chosen once per render via `RenderParams::antialiasing_method` and there is no
per-primitive knob. So on this backend all three variants render antialiased.

The consequences, stated rather than absorbed:

- a `re W n` clip keeps one soft pixel along each edge where the CPU backends
  binarize it — and `push_clip_rect` exists precisely because that clip is the
  commonest in the corpus, so this affects a large fraction of pages
- `FullCover`'s pin-hole avoidance is unavailable, so mesh-shading seams may
  show

The alternative — thresholding the whole target on readback — was rejected
rather than untried: it would apply to *every* pixel of a page, including the
ordinary antialiased fills that must stay soft, so it is not a per-primitive
control by another route. Making the GPU agree here would require either an
upstream vello feature or changing what the engine sends, and **changing the
engine is the forbidden direction** — the CPU output is what the oracle
validates. §7 measures what this costs against `raster-exact`.

`PINNED_AA` is `AaConfig::Area` — vello's analytic winding-number integration —
rather than either multisampling mode, because it is the closest of the three
to what `pdfrum-raster-exact` computes. That keeps the Tier C budget about
drivers rather than about a sampling policy we chose differently on purpose.

### 5.2 What is deliberately left for later

- **Pattern cells and shadings keep the CPU decomposition.** The engine
  decomposes these into thousands of tiny fills — the same decomposition that
  made SIMD useless in M12 §3.9 — and a GPU would want the opposite structure:
  one scene, one dispatch. PLAN.md says to note it and not rewrite the engine
  for it in this milestone, and that is what has been done. §4.3's
  offscreen-target cost is the same finding from the other end.
- **`draw_image`'s prescale contract is untouched.** It is CPU-shaped and
  backwards on a GPU, M12b P1 is concurrently making decode resolution-aware,
  and the two interact. §6 records what the right GPU answer looks like; no
  contract changes here.
- **No `Backend::VelloGpu` on the facade.** Adding one would put `wgpu` in the
  facade's tree, which is the one thing the isolation rule forbids. A caller
  reaches this backend by naming the crate.

## 6. How the two harnesses measure, and what they cannot say

`cargo run --release -p pdfrum-raster-vello-gpu --example tier-c` (§7) and
`--example bench` (§8). Both share `examples/shared/harness.rs`, which builds
page 0 of a corpus document **once** and hands the same page graph to both
columns. That is not an optimisation: if each column built its own page, an
output difference could be a difference in the build and a timing difference
would include work the other column also paid.

Three properties of the instrument, stated because they bound what §7 and §8
are allowed to claim:

- **Both columns enter at `pdfrum_render::render_page_with_caches`**, not at
  the facade. `pdfrum::Backend` is a closed enum and adding a GPU arm would put
  `wgpu` in the facade's tree — the one thing the isolation rule forbids. The
  comparison is therefore *symmetric*, which is what these sections need, and
  deliberately **not** comparable to the oracle's column. Nothing below is
  compared to an oracle number.
- **Annotation appearances are not overlaid**, because that is the facade's
  private step. The `forms` class here measures the page under the widgets
  rather than the widgets. Both columns lose it equally, so the ratio stands;
  the absolute forms numbers are not the facade's.
- **The build uses `Page::objects()`**, which does not set the per-page decode
  target the facade's render path sets. Images are decoded at full resolution.
  Deliberate: the decode target is M12b P1's live work and this milestone stays
  out of it, and both columns render the identical graph, so it is not a
  difference between them.

## 7. G2 — Tier C: the divergence, and its budget

### 7.1 The budget, stated before the measurement

PLAN.md requires the budget up front and justified. It is
`conformance/src/tierc.rs`'s, unchanged, because inventing a friendlier metric
for the backend being graded is the obvious way to get a meaningless number:

- **Interior pixels: zero tolerance beyond 1 count.** An interior pixel is one
  whose neighbourhood is flat in *both* images — no rasterizer has a claim on
  it, so a difference there is an engine-level disagreement. `> 0` such pixels
  is a **hard failure** at any count.
- **Edge pixels: 8 counts, and the rate is reported not gated.** An
  antialiased edge is a coverage ramp; two integrations of the same ramp land a
  good way apart at the steepest point without either being wrong.
- The edge mask is the neighbourhood proxy **dilated one pixel from the
  intersection** of the two images' boundaries — never from the union, which
  would let a difference manufacture its own licence.

The reference column is **`pdfrum-raster-exact`**: the conformance default, and
the backend whose edge quantisation is closest to the oracle's own (SPEC §8
item 7). Comparing against the closest-to-oracle CPU backend is the strictest
available choice.

**The stated budget: zero interior differences on all 44 documents, and the
edge rate reported per document with any document above 5% explained by
mechanism rather than averaged away.** The interior half is the real gate; the
edge half is where a GPU is entitled to differ and the number is only
meaningful with a cause attached.

### 7.2 The measurement

Adapter: **NVIDIA GeForce RTX 4090 (Vulkan, DiscreteGpu, driver NVIDIA
595.84)**.

```
# summary over 44 documents
mean edge divergence:     3.579%
worst edge divergence:   69.372%  (shading_tensor)
documents with interior differences: 0 of 44
documents where exactly one backend painted: 0

# mean edge divergence per class
forms         0.000%  (7 documents)
mixed         0.005%  (5 documents)
text          0.192%  (9 documents)
image         0.240%  (9 documents)
vector        1.804%  (6 documents)
shading      17.845%  (8 documents)
```

**The gate passes outright: zero interior differences on all 44 documents, and
no document where one backend painted and the other did not.** Whatever the GPU
does differently, it is not disagreeing with the engine about what to draw —
which is the property Tier C exists to establish.

Thirty-four of 44 documents are at or below 0.4%. The divergence is
concentrated, not spread: five documents carry essentially all of it.

| document | edge% | maxdiff | why |
|---|---|---|---|
| `shading_tensor` | 69.4% | 255 | type 6/7 patches — `FullCover` |
| `shading_axial_radial` | 36.4% | 255 | contains types 6 and 7 |
| `shading_tcpdf_030` | 33.9% | 254 | contains type 6 |
| `vector_en_system` | 9.3% | 239 | 28k+ small fills |
| `shading_tcpdf_058` | 2.7% | 142 | types 2/3 only |

### 7.3 The cause, traced rather than guessed

The shading concentration is **§5.1's antialiasing gap**, and the mechanism is
specific. `AntiAlias::FullCover` is used in exactly one place in the engine —
`crates/pdfrum-render/src/shading/patch.rs:480`, the Coons/tensor patch
rasterizer — and the ShadingTypes present in each document line up with the
divergence exactly:

```
shading_tensor        types 6,7        69.4%
shading_axial_radial  types 1-7        36.4%
shading_tcpdf_030     types 2,3,6      33.9%
shading_tcpdf_058     types 2,3         2.7%
shading_tcpdf_056     types 2,3         0.4%
shading_type4_5       type 5            0.0%
```

Every document containing a type 6 or 7 patch diverges by more than 30%; every
document without one is under 3%. `FullCover` exists precisely because
thresholding drops a pixel two abutting patch cells each half-cover, so a
subdivided patch shows white pin-holes along every internal seam. vello has no
per-primitive aliasing control, so those seams are antialiased here and the
cells no longer paint each other's shared pixels at full alpha. **That is the
predicted failure appearing exactly where it was predicted**, which is the
useful outcome: the gap is one named mechanism in one named file, not a diffuse
inaccuracy.

`vector_en_system`'s 9.3% has the same shape from the other direction: it is
the 28k-fill document from M12 §3.9, so almost every pixel it draws is on an
edge, and a rasterizer difference has nowhere else to land.

### 7.4 A zero that is not evidence, found by checking

`shading_coons` and `shading_gouraud` both report **0.000% with maxdiff 0** —
byte-identical output. That looked like the strongest possible agreement and it
is worth nothing, which is why it was checked rather than reported:

```
shading_coons     distinct_colours=1   inked_px=0
shading_gouraud   distinct_colours=1   inked_px=0
```

Both render a **blank page** under `raster-exact`. Their agreement is the
agreement of two backends drawing nothing. Recorded because a table of 44 rows
with two vacuous zeros in it would otherwise read as two documents' worth of
evidence that does not exist — and because `shading_coons` is a type-6 document
that would otherwise look like a counter-example to §7.3's mechanism.

The genuine zero in that class is **`shading_type4_5`**: 65 025 inked pixels
across 64 870 distinct colours, and 0.000% divergence with maxdiff 0. A free-
form Gouraud mesh, byte-identical between an analytic CPU rasterizer and a GPU.
That one is real evidence, and it is the reason §7.3 can attribute the shading
divergence to the *patch* path rather than to mesh shading generally.

### 7.5 Verdict

**Tier C passes on its stated gate and the residue is explained.** Zero
interior differences, no blank-page disagreements, 34 of 44 documents under
0.4%, and the concentrated remainder traced to one engine call site
(`patch.rs:480`) that a GPU cannot express.

Per PLAN.md this backend is **reported, never gated**, and joins no scoreboard.
The conformance scoreboard is untouched by this milestone — nothing in the core
ring changed, so it is byte-identical by construction rather than by
re-measurement.

**And the forbidden direction stays closed.** Making the GPU agree on the patch
seams would mean changing what the engine sends — dropping `FullCover`, which
exists to match `CFX_AggRenderer::GetSrcAlpha` and is worth pin-hole-free
patches on the CPU backends the oracle validates. That is exactly the trade
PLAN.md forbids. The divergence is reported and the CPU output is left alone.

## 8. G3 — the benchmark, upload and readback included

### 8.1 Method

`--example bench`, median of 10 renders after a warm-up, one pixel per PDF
point, on the RTX 4090 named above. The CPU column is **`vello_cpu`** — the
facade's default, the backend an API user actually gets. (`raster-exact` is the
*correctness* reference in §7 for the opposite reason: it has no SIMD and does
not try to be fast, so timing against it would flatter the GPU for a reason
that has nothing to do with the GPU.)

**The timed region is a whole `render_page_with_caches` call**, which on the
GPU column ends in `RasterBackend::finish` — texture allocation, vello
dispatch, `copy_texture_to_buffer`, and the host stall waiting on `map_async`.
Nothing is subtracted. PLAN.md is explicit that excluding these would be
marketing rather than measurement.

### 8.2 The headline, and why it is not the interesting number

```
geometric mean gpu/cpu:   2.10x      (below 1.0 = GPU faster)
documents where GPU wins: 11 of 44

forms     3.12x  wins 0 of 7      vector   1.34x  wins 3 of 6
mixed     4.69x  wins 0 of 5      image    1.35x  wins 5 of 9
shading   2.28x  wins 1 of 8      text     1.92x  wins 2 of 9
```

The GPU backend is **2.10x slower than `vello_cpu` on the corpus**, and PLAN.md
anticipated that a backend can lose the corpus and still be a success with a
documented envelope. But the raw table has a defect that has to be removed
before the envelope can be read, and finding it changed the conclusion.

### 8.3 The correction: four of the eleven "GPU wins" are not wins

The heaviest image documents sit suspiciously close to 1.00x
(`image_jbig2_1478366` 1.00x, `image_bug_898443` 0.99x, `image_jbig2_880920`
1.01x). A ratio that close on a 300–900 ms render is not two rasterizers
performing identically; it is a render where rasterization is a rounding error.

Measured, with a null backend that accepts every device call and draws nothing
— so its time is the engine's walk, the decode, and everything else neither
backend can avoid:

| document | null ms | cpu ms | backend-independent |
|---|---|---|---|
| `image_jbig2_1478366` | 327.96 | 323.79 | **101%** |
| `image_bug_898443` | 705.19 | 711.58 | **99.1%** |
| `image_bug_718762` | 835.10 | 841.56 | **99.2%** |
| `image_jbig2_880920` | 176.78 | 176.49 | **100%** |
| `vector_tcpdf_009` | 166.48 | 167.27 | **99.5%** |

These documents are 99–101% decode. **Their "GPU wins" measure nothing about
the GPU** — both columns are waiting on the same JBIG2 and JPEG decoders. This
is M12 §10.3's finding arriving from a new direction: single-image work is
where the engine is behind, and no rasterizer change reaches it.

### 8.4 Rasterization-only, which is the honest comparison

Subtracting the null-backend time from both columns isolates what the backends
actually do. (One document, `image_jbig2_1478366`, is dropped: its
rasterization is 0.27 ms against a 328 ms decode, which is below the noise.)

```
rasterization-only geometric mean: 2.64x     GPU wins 10 of 43

vector   1.20x  wins 3 of 6       shading  2.96x  wins 1 of 8
image    1.46x  wins 4 of 8       forms    4.30x  wins 0 of 7
text     2.54x  wins 2 of 9       mixed    7.83x  wins 0 of 5
```

The geomean gets *worse* (2.10x → 2.64x) once the decode is removed, because
the decode was flattering the GPU. But the **wins get much larger**, which is
the envelope PLAN.md asked for:

| document | cpu-rast ms | gpu-rast ms | ratio |
|---|---|---|---|
| `vector_en_system` | 28.90 | **6.02** | **0.21x** — 4.8x faster |
| `image_bug_583804` | 245.88 | **116.14** | **0.47x** |
| `image_bug_718762` | 58.61 | **27.68** | **0.47x** |
| `image_jpx_123` | 6.05 | **2.98** | **0.49x** |
| `image_bug_898443` | 13.18 | **7.04** | **0.53x** |
| `vector_tcpdf_009` | 2.51 | 1.60 | 0.64x |
| `text_bug_1029` | 3.12 | 2.01 | 0.64x |

`vector_en_system` is the corpus's heaviest vector page — the 28k-fill document
— and the GPU rasterizes it **4.8x faster**. That is the milestone's target
class behaving as predicted, and it is a large effect rather than a marginal
one.

### 8.5 The crossover, and why it is not a threshold

PLAN.md asks for "the page complexity below which the CPU backend wins". The
measurement does not support a single number, and saying so is more useful than
inventing one:

```
cheapest page the GPU still wins on:  1.40 ms of CPU work  (shading_coons)
dearest page the CPU still wins on: 180.51 ms of CPU work  (image_jbig2_880920)
```

Those overlap by two orders of magnitude, so **page cost does not predict the
winner**. What predicts it is *shape*:

- **The GPU wins on pages that are one big scene**: many primitives, few
  offscreen targets. `vector_en_system` (0.21x), `vector_tcpdf_009` (0.64x).
- **The GPU loses on pages that build many small offscreen targets** — §4.3's
  structural cost. `mixed` at 7.83x is the worst class and `forms` at 4.30x the
  second worst, and both are dominated by widget appearance forms and
  transparency groups, each of which is a texture allocation, a dispatch and a
  `map_async` host stall. `mixed_tcpdf_045` at 24.96x is the extreme.
- **`image_en_fqa` at 50.77x is the single worst document** and is the same
  mechanism at its limit: M9 established it draws **87 separate masked images**,
  so it pays 87 round trips.

So the envelope is: **this backend is for pages whose cost is vector
rasterization, and against pages whose cost is compositing structure.** That is
a statement about page shape, not page size, and an embedder can act on it.

### 8.6 What would move it, none of which is in this milestone

The losses are one cause — a host round trip per offscreen target — and it is
an *engine* interface property, not a backend defect. `RasterBackend` hands
back a `Pixmap`, so a group must come back to the host even when its only
consumer is the next GPU draw. Fixing it means letting the engine composite a
group without a readback, which is an engine change and explicitly out of scope
here (PLAN.md: "Note it; do not rewrite the engine for it in this milestone").

Recorded as the measured prerequisite for any future GPU work: **the 2.64x is
not a shader problem and no amount of vello tuning reaches it.**

## 9. `draw_image`'s prescale contract — what the right GPU answer is

PLAN.md is explicit here: the contract is CPU-shaped and backwards on a GPU,
M12b P1 is concurrently making decode resolution-aware, the two interact, and
**this milestone must not change the contract unilaterally.** It must measure,
write down the right GPU answer, and route any change through `[spec]` once
P1's outcome is known. So: no contract change, and no edit to
`crates/pdfrum-page/src/image/`, `crates/pdfrum-render/src/stretch.rs` or
`crates/pdfrum-render/src/image.rs`. Here is the finding.

### 9.1 What the contract says and why it is backwards here

`RenderDevice::draw_image`'s doc comment states that an image being *reduced*
"has already been box-filtered down to roughly its device size by
`prescale`", so the two-tap kernel runs near 1:1. On a CPU that is obviously
right: a box filter over the source is cheaper and better than point-sampling a
large texture, and it is what `CStretchEngine` does.

On a GPU it inverts. The reduction is being done by the *host*, on the CPU, in
`stretch::prescale`, and its output is then uploaded — so the GPU column pays
the CPU's filtering cost **and** the upload, and gets no benefit from the
sampler and mip hardware that exists precisely for this. The right GPU answer
is to upload the source once and let the sampler reduce, with mipmaps where the
reduction is large.

### 9.2 The measurement, and why it does not justify acting yet

The image class is where this would show, and §8.4 measures it at **1.46x with
the GPU winning 4 of 8** — the second-best class, behind `vector`. The
documents that win are exactly the large-source ones (`image_bug_583804` 0.47x,
`image_bug_718762` 0.47x, `image_jpx_123` 0.49x).

**So the prescale contract is not currently costing the GPU backend its image
class.** That is the measurement, and it argues for patience rather than for a
contract change:

- The prescale work is on the shared path, so it lands in *both* columns and
  §8.4's subtraction removes most of it from the ratio.
- The one catastrophic image document, `image_en_fqa` at 50.77x, is **not** a
  prescale problem — M9 established it as 87 separate masked images, so it is
  §4.3's round-trip cost with a different label. Changing the prescale contract
  would not move it.
- P1 is actively changing what arrives at this seam. A contract negotiated
  against today's full-resolution decode could be wrong the week after P1
  lands: if decode becomes resolution-aware, the "full source texture" the GPU
  wants to upload may no longer exist at full resolution at all.

### 9.3 The recommendation, for whoever holds the `[spec]` change

When P1's outcome is known, the shape that serves both backends is a
**capability the device declares** rather than a policy the engine fixes:

- A backend that reduces well in hardware says so; the engine skips `prescale`
  and passes the source with the full device transform.
- A backend that does not — every CPU backend — keeps today's behaviour
  exactly, so the oracle-validated CPU output does not move by one count. That
  is the property that makes this safe to propose at all: it is additive, and
  the forbidden direction stays closed by construction.

That is a `RenderDevice` surface change and therefore a `[spec]` commit, and it
should be made **after** P1, with P1's decode target in hand, by whoever owns
that seam. It is deliberately not made here.

## 10. Verdict

**The backend works, is isolated, and is a success with a narrow envelope.**

What was asked for and what was delivered:

| Target (PLAN.md §M12c) | Outcome |
|---|---|
| Every corpus document renders without panic or device loss | **Met** — 44 of 44, no panic, no device loss |
| Tier-C divergence inside a stated budget | **Met** — zero interior differences on 44 of 44; edge residue traced to one call site (§7) |
| Measured speedup on `vector` and `shading` at a stated resolution | **Half met** — `vector` yes and large (4.8x on the heaviest page); **`shading` no, and it is the worst class after `mixed`** (§8.4) |
| Upload and readback included | **Met** — nothing subtracted (§8.1) |
| CPU-wins crossover documented | **Met, and it is not a threshold** — page *shape*, not size (§8.5) |
| Facade default backend unchanged | **Met** — the facade cannot even name this backend |
| Conformance scoreboard byte-identical | **Met by construction** — nothing in the core ring changed |
| Isolation proven by a committed check | **Met** — `scripts/check-no-wgpu.sh`, verified by negative control (§4.4) |
| `forbid(unsafe)` intact | **Met** |
| DEPS.md row stating the exemption, blast radius, and bounding check | **Met** |

**The shading target is missed and that is the honest headline of §8**, not a
rounding. It was the milestone's named hope, and the same mechanism that
explains §7's divergence explains it: the engine decomposes patches into
thousands of tiny fills (M12 §3.9), which is the structure a GPU is worst at,
and PLAN.md forbade restructuring the engine to suit it. So the class is slow
here for the same reason it diverges here, and both are one finding.

Two things are worth carrying forward more than the numbers:

1. **The exemption's benefit is not yet available** (§1). Device injection
   works, and no released Rust GUI frontend can use it, because vello 0.10 sits
   on `wgpu` 29 between egui's 30 and iced's 27. The cost is paid; the benefit
   waits on an upstream release.
2. **The 2.64x is an interface property, not a shader problem** (§8.6).
   `RasterBackend` hands back a `Pixmap`, so every transparency group, soft
   mask and pattern cell is a host round trip. That is the one measurement any
   future GPU work should start from.

**Deliberately left undone**, each for a stated reason rather than for time:
the prescale contract (§9 — belongs to P1's `[spec]`); pattern and shading
restructuring (PLAN.md forbids it here); a group-composite path that avoids the
readback (§8.6 — an engine change); and a facade `Backend` arm (§5.2 — it would
break isolation). The crate stays `publish = false` and out of the M13 set.
