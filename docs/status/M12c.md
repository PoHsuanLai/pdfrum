# M12c — GPU backend: `vello` on `wgpu`

**Updated:** 2026-08-31 · **State:** in progress.

PLAN.md §M12c is the assignment. This document is written in M12.md's register:
hypothesis, method, measurement, verdict, **including the non-results**. A claim
a later measurement refutes is withdrawn in place with the measurement that
refuted it, never deleted.

The milestone's two non-negotiables frame everything below:

- **Isolation.** `pdfrum-raster-vello-gpu` is its own crate that nothing in the
  core ring depends on. A headless build must resolve a tree with zero `wgpu`,
  and the proof is a committed CI check rather than a sentence here.
- **Device injection, not device creation.** The primary constructor borrows a
  caller-supplied `wgpu::Device` and `Queue`.

## 1. The version premise is wrong, and it changes the pin

**PLAN.md §M12c states: "`vello` 0.10 targets `wgpu` 30, which is current, so
the shared-device story with today's frontends is real rather than a
version-skew fight." Checked 2026-08-31 against crates.io: this is false.**

```
$ cargo add vello@=0.10.0 wgpu@=30.0.1        # in a scratch crate
$ grep -A2 'name = "wgpu"' Cargo.lock
name = "wgpu"  version = "29.0.4"
name = "wgpu"  version = "30.0.1"
```

Two `wgpu` versions resolve, because `vello 0.10.0` depends on `wgpu 29`, not
30. `vello` 0.10.0 is the newest published `vello` (the version list ends
there), so there is no vello release that targets `wgpu` 30 today.

This is not a cosmetic pin correction. **Device injection only typechecks
against the exact `wgpu` a `vello::Renderer` was compiled with** — a
`wgpu::Device` from the 30 tree is a different type from the 29 tree's, and no
conversion exists. So:

- the crate pins `wgpu = "=29.0.4"`, matching vello's own resolution, and
- the crate **re-exports its `wgpu`** so an embedder can see which one it must
  hand us, and
- the shared-device story with a `wgpu` 30 frontend is *not* available today.
  It becomes available when vello publishes against 30, and the only change
  required here is the pin.

The milestone's underlying argument survives intact — an embedder already
holding a device should not be made to open a second one — but its "no
version-skew fight" clause is withdrawn on this measurement. A frontend on
wgpu 30 today would have to either hold back to 29 or run this backend on its
own device, which is exactly the cost the milestone wanted to avoid. Recorded
here so a reader does not rediscover it, and so the DEPS.md row states the real
version rather than the planned one.

## 2. The pure-Rust tree, measured rather than assumed

DEPS.md's guarantee is enforced by `cargo-deny` bans on `cc`/`cmake`/
`pkg-config`/`bindgen` plus `scripts/ci.sh`'s `cargo tree` grep for `*-sys`.
The GPU tree was measured against both before the crate existed:

- **85 crates** in the normal dependency tree of `vello 0.10` + `wgpu`.
- **Build dependencies:** none of `cc`, `cmake`, `pkg-config`, `bindgen`. **No
  C is compiled.** The `cargo-deny` bans therefore need no exception at all —
  a finding worth stating plainly, because the milestone brief anticipated
  having to scope one.
- **Two `-sys` crates**, which `scripts/ci.sh`'s grep rejects: `renderdoc-sys`
  and `wayland-sys`. Neither compiles C (no `cc` build-dep anywhere in the
  tree); both are `dlopen`-style declaration shims. §4 records how the check is
  scoped so the guarantee stays mechanically enforced everywhere else.


`PowerPreference::HighPerformance` selects the first RTX 4090 over Vulkan;
`request_device` succeeds with `max_texture_dimension_2d = 8192` at default
limits (the adapter's own limits raise this — see §6).

**`llvmpipe` is in that list, and it is exactly the silent-fallback hazard the
brief warned about.** `wgpu`'s adapter selection will happily hand back a
software rasterizer that reports as `Vulkan`, and a benchmark taken on it would
be a CPU number labelled GPU. Every measured number below therefore records the
adapter's `device_type` and `name` alongside it, and the bench harness refuses
to report a GPU figure from a `DeviceType::Cpu` adapter.

An end-to-end smoke test — `vello::Renderer` on that device, a red rect into a
64x64 `Rgba8Unorm` storage texture, `copy_texture_to_buffer`, `map_async`,
readback — returns `[255, 0, 0, 255]` at the centre and `[255, 255, 255, 255]`
at the corner. So the full pipeline this milestone needs (scene → GPU →
texture → host) works on this machine before a line of the backend existed.

## 4. Where the trait and vello's scene model actually differ

The brief calls the mapping "largely mechanical" for the six primitives and
names three places where it is not. Reading `vello 0.10.0`'s `Scene` against
`RenderDevice` found the mechanical half is indeed mechanical and the
non-mechanical half is *structural*, in a way the `vello_cpu` backend does not
prepare you for.

### 4.1 Clips and layers are one stack, not two

`pdfrum-raster-vello`'s `VelloDevice` carries a `Vec<Frame>` because `vello_cpu`
keeps clips and layers on **separate** stacks and each `pop` must name which.
GPU `vello` has the opposite shape: `Scene::push_layer`, `push_clip_layer` and
`push_luminance_mask_layer` all push onto **one** stack, all are undone by the
same `pop_layer`, and — the part that matters — **every layer carries a clip
shape**. There is no "layer without a clip" and no "clip without a layer".

That makes `RenderDevice`'s two-stack contract *easier* to satisfy here, not
harder, and the `Frame` bookkeeping is unnecessary:

- `push_clip(path, rule)` → `push_clip_layer(Fill::from(rule), IDENTITY, path)`
- `push_clip_rect(rect)` → the same with the rect as the shape
- `push_layer(blend, alpha, None)` → `push_layer(Fill::NonZero, blend, alpha,
  IDENTITY, <full device rect>)` — a layer whose clip is the whole target
- `pop()` → `pop_layer()` in every case

The one thing that must not be lost is that vello's docs state plainly that
**the transform is not saved or modified by the layer stack**: the `transform`
argument applies to the clip *shape only*. Our clips already arrive in device
space (`clip::push` transforms them before the call), so identity is correct
and this is a non-issue — but it would silently double-transform every clip on
a backend that tried to be clever about it.

### 4.2 There is no arbitrary alpha-mask layer, and that is the real gap

`RenderDevice::push_layer` takes `Option<&AlphaMask>` — a device-sized plane of
8-bit coverage the engine computed. `vello_cpu` consumes exactly that
(`Mask::from_parts`). **GPU vello has no equivalent.** Its only masking layer is
`push_luminance_mask_layer`, where the mask is *content drawn into the scene*
between the push and the pop, and where the luminance is taken with vello's own
coefficients rather than the NTSC ones the oracle's soft masks use — the same
trap `pdfrum-raster-vello` documents about `Mask::new_luminance`.

So a supplied `AlphaMask` has to be turned back into drawable content. The
mapping that preserves the byte values exactly is:

1. `push_luminance_mask_layer(NonZero, 1.0, IDENTITY, <device rect>)`
2. draw the mask plane as an **image** — expanded to RGBA where R=G=B=`m` and
   A=255 — at identity, so vello's luminance of a neutral grey `m` is `m`
3. `pop_layer()` to end the mask, then `push_layer(...)` for the real layer

which costs one extra layer and one extra image upload per masked layer.
Whether that is exact depends on vello's luminance being `luma(m,m,m) == m` for
a neutral grey under any sane coefficient set (the weights sum to one), which
it is — the coefficient question only bites on *coloured* mask content, and
ours is neutral by construction. §7 records the measured check.

**Measured relevance, recorded so the work is sized honestly:** the engine
currently passes `None` at all four of its `push_layer` call sites
(`walk.rs:573, 1569, 1717, 1846` — all `(blend, 1.0, None)`), because soft
masks are applied *by the engine* to a readback pixmap
(`pixels.multiply_alpha_mask`) rather than handed to the device. So this path
is dead on today's engine. It is implemented anyway, and tested directly,
because a backend may not assume a caller's current habits — but no corpus
number below exercises it, and that is stated rather than implied.

### 4.3 Retained scene, immediate readback: the offscreen-target problem

This is the finding that most shapes the performance envelope, and it is not
one of the three the brief listed.

`RasterBackend` is a *factory of targets*, and the engine uses it heavily: a
transparency group, a soft mask's group, every tiling-pattern cell, the mesh
scratch buffer and the fill+stroke knockout buffer each get their own
`new_target`, are drawn into, and are then read back as a `Pixmap`
(`walk.rs:138, 519-523, 616, 1393, 1501, 1556, 1786, 1834, 1934`;
`paint.rs:280`; `pattern.rs:539`). On CPU a target is a buffer and `finish` is
a rasterize. On GPU each one is a texture allocation, a full `Renderer`
dispatch, a `copy_texture_to_buffer`, and a **`map_async` round trip that
stalls the host on the GPU**.

`new_target_with_backdrop` and `snapshot` make it worse in the same direction:
`snapshot` reads pixels *back* mid-page, and `new_target_with_backdrop` then
uploads them again as a starting image. A page with a non-isolated group pays
a full readback and re-upload at that point.

None of this is a defect in the trait — it is the CPU-shaped assumption that
a rendered surface is cheap to look at. It is *the* reason to expect the GPU
backend to lose on pages with many small offscreen targets and win on pages
that are one big scene, and §8's crossover is read in exactly those terms.
Fixing it properly means giving the engine a way to composite a group without
a host round trip, which is an engine change and explicitly out of scope here.
