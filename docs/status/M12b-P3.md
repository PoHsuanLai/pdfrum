# M12b P3 — the walk's per-object interpretation overhead

**Status: complete** (2026-09-01). Written incrementally, in M12.md's and
M12b-P2.md's register: hypothesis, A/B, verdict — non-results included, because
this item's whole method is to rank before touching and to write down what
measured to zero.

## 0. The target this item inherited, and what it is not

P2 (docs/status/M12b-P2.md §9) left exactly one bucket standing after closing
the arena question and landing three no-dep changes. **Interpretation is 60–90%
of the engine half**, and on `vector_paths_1751` it is 3.98 ms across 5010
objects — **794 ns per object** — spread over the dispatch `match`, the cull
test, `GraphicsState` reads, the `RenderCtx` threading, and `draw_path`'s
five-case decision tree.

This is **per-object constant overhead**. It is not a loop to vectorize
(`fearless_simd` stays declined — M12 §3.9's reopening condition is about span
length and nothing here touches it), not an allocation to pool (P2 closed
`bumpalo` with an A/B showing +265%/+121%/+97% *slower* against the tuned
baseline, and allocation in the walk is now 0.6% of a render), and not
`to_pixmap`'s per-pixel work (P1 took that; the `image` phase is 1.2% of a warm
engine half). The only lever is **doing less per object**.

Also inherited, unowned: `shading_axial_radial`'s engine half is **61%
`pattern.rs` residue**. §-below folds it into the ranking.

## 2. Measurement hygiene, stated before any number

This machine carried a load average of **8–13** for the whole session, from
unrelated jobs (one python3 at 455% CPU, three `osmium` processes at ~99% each)
across 32 cores. P1 and P2 each nearly published a false finding to exactly this
cause. Every absolute number below therefore comes from a **paired A/B
interleaved in one window** — before, after, before, after — with the
best-of-N taken, and anything surprising was re-measured. Where a number could
not be taken honestly it is recorded as debt rather than published.

## 4. A harness trap that almost produced a fifth withdrawn claim

Before any verdict below can be read, the harness it was taken on has to be
named, because the first A/B this item ran said something false and said it
consistently.

`pdfrum-bench`'s `profile` binary has **two render loops**, and they measure
different things:

- **the plain loop** (`run`, no `--sample`) builds a fresh `RenderSession` per
  iteration and calls `page.render_session()`, which **re-derives the page graph
  every iteration**. On a content-heavy document that is mostly `pdfrum-page`.
- **`--sample`** (`timed_render`) builds the page graphs **once, outside the
  loop**, reports the build separately, and reuses one `RenderCaches`. Its TOTAL
  is the render.

On `vector_en_tem` the plain loop reports **34 ms** and `--sample` **6.2 ms**.
The 28 ms difference is the page-graph rebuild, and it is 82% of what the plain
loop was timing.

Measured on the plain loop, §5's changes looked like a **+5.0% regression on
`vector_en_tem`** — reproducible across twelve interleaved rounds, every round,
median and minimum agreeing. Bisected, *each half of the change* regressed it
independently (+6.4% and +13.5%), which is already incoherent: two changes that
each cost 6–13% do not compose to 5%.

The instrument settled it in one run. On the same document the changed code is
**cull 0.9% + rect test 0.3% + path xform 0.9% = 2.1% of an engine half that is
23% of the render** — about half a percent of the whole. A 5% regression there
is arithmetically impossible. And the `--sample` phase table before and after
agrees to three decimals on every row, RASTER and ENGINE alike:

| | before | after |
|---|---:|---:|
| `draw_image` | 1.147 ms | 1.155 ms |
| `clip` (device) | 2.866 ms | 2.828 ms |
| RASTER | 4.806 ms | 4.770 ms |
| ENGINE | 1.426 ms | 1.428 ms |
| **TOTAL** | **6.232 ms** | **6.199 ms** |

Re-run on `--sample`, `vector_en_tem` is **−1.1%**. The regression was never in
the render.

**So every number in §5 onward is `--sample`'s TOTAL, paired and interleaved,
best-of-N.** The self-A/B noise floor on that harness — the same binary copied
to two inodes, run through the same loop — is **±1.6%** on `vector_paths_1751`
and **±0.1%** on `vector_en_tem`, so the band is taken as **4%** as M12 measured
it, and anything inside it is a non-result. This is the third time in this
milestone that a false finding got as far as a bisection; it is written down at
this length so it is the last.

## 5. What landed, with the A/B beside it

Two changes, taken in the order the ranking put them, each committed on its own
so its number is its own.

### 5.1 The cull test: bracket the exact box, solve only between (`b7fe49e`)

**Hypothesis.** The cull is 156 ns per object and 17.4% of `vector_paths_1751`'s
engine half, for 5010 answers of "keep" out of 5010. The cost is honest:
`object_bbox` unions each segment's *exact* box, and kurbo computes that by
solving the cubic's extrema. That precision is load-bearing — it is what makes
the cull decision identical to the transformed-clone spelling `path_bbox`
replaced — so it cannot be dropped. It can be *skipped* when the answer is not
in doubt.

**The change.** Two boxes bracket the exact one at one pass of `min`/`max`, no
segment reconstruction: the box of the **on-curve endpoints**, which the exact
box contains, and the box of **every control point**, which contains it. A
subset that reaches the clip proves the exact box does — keep. A superset that
misses proves the exact box misses — cull. Only a path whose curve bulges across
an edge its endpoints and hull straddle differently pays for the solve, and it
gets the same answer.

Two shapes are declined rather than bracketed, because on them the endpoint box
would stop being a subset: a `MoveTo` goes only into the superset (a move
followed immediately by another starts no segment and is in no exact box), and a
path that does not open with a move goes straight to the exact spelling.

**Guarded by construction, not by hope.** The test slides a clip across every
shape the cull can meet — a rectangle, a curve whose control points sit far
above its peak, a two-move path, a bare move, a move-and-close, and an empty
path — half a unit at a time on both axes under three matrices, and requires the
bracket to agree with `path_bbox` at every position.

**A/B** (`--sample` TOTAL, paired, best of 5 x 30 iterations):

| Document | before | after | delta |
|---|---:|---:|---:|
| `vector_paths_1751` | 3.907 ms | 3.327 ms | **−14.8%** |
| `vector_en_system` | 51.577 ms | 50.564 ms | −2.0% |
| `text_foxittext` | 2.417 ms | 2.366 ms | −2.1% |
| `mixed_tcpdf_045` | 5.112 ms | 5.140 ms | +0.5% |

**Verdict: −14.8% on the path-heavy document, everything else inside the band.**
Which is what the phase table predicted: the cull is 17.4% of that document's
engine half and 0.1–0.3% of the other three's.

### 5.2 The path object's five buffers, reduced to one (`d51ef60`)

**Hypothesis.** Three sites in `paint.rs` and `path.rs` allocate per path object
and none was in P2's census:

- `hard_clip(&(to_device * path.clone()))` — **two** whole `BezPath`s per fill,
  the first discarded at the device call;
- `path_rect`'s candidate, normalized and transformed `Vec<Point>` — **three**
  per fill-only object, to answer "not a rectangle" 4970 times out of 4970;
- `nudge_degenerate_subpaths`'s two `to_vec`s, which hand `should_nudge` slices
  that `BezPath::elements` already is.

**The change.** None of it was dynamic. The clamp composes with the transform on
points, so the two `BezPath` passes fuse into one buffer reserved to the source's
length (`transform_hard_clip`). `rect_candidate_points` already bailed above 32
points and `normalize_points` already returned exactly five or nothing, so a
fixed inline `Points` array with a length is the shape those three `Vec`s were
approximating — and a `push` past its capacity is a *rejection* rather than a
panic, which STYLE forbids in a library, because a path with more points than it
holds is one the candidate scan was going to decline regardless. The two
`to_vec`s become a borrow.

**A/B** (`--sample` TOTAL, paired, best of 5 x 30 iterations, on top of §5.1):

| Document | before | after | delta |
|---|---:|---:|---:|
| `vector_paths_1751` | 3.253 ms | 2.820 ms | **−13.3%** |
| `vector_en_system` | 50.720 ms | 50.632 ms | −0.2% |
| `text_foxittext` | 2.366 ms | 2.368 ms | +0.1% |
| `mixed_tcpdf_045` | 5.154 ms | 5.090 ms | −1.2% |

**Verdict: −13.3%, everything else inside the band.**

## 6. What measured to zero, and one thing that measured backwards for a reason

Three hypotheses were tried and are recorded here rather than in the tree.

### 6.1 Hoisting the stroke split out of the fill's way — zero

**Hypothesis.** `draw_path`'s ordinary case computed `split_for_stroke(to_device)`
— a matrix inverse and a multiply — *before* the fill arm, so a fill-only object
paid for it and threw it away. On `vector_paths_1751` that is 4970 fills against
939 strokes: 4031 wasted inverses per render.

**A/B** (`--sample` TOTAL, best of 6 x 30):

| Document | before | after | delta |
|---|---:|---:|---:|
| `vector_paths_1751` | 2.819 ms | 2.825 ms | +0.2% |
| `vector_en_system` | 50.726 ms | 50.723 ms | −0.0% |
| `text_foxittext` | 2.389 ms | 2.414 ms | +1.0% |
| `mixed_tcpdf_045` | 5.177 ms | 5.189 ms | +0.2% |
| `vector_tcpdf_009` | 8.665 ms | 8.683 ms | +0.2% |

**Verdict: zero, on every document.** LLVM already sinks the computation into
the arm that reads it — the value is pure and unused on the fill-only path, so
the "waste" existed only in the source. **The change was reverted rather than
kept**, because a diff that moves code and moves no number is churn dressed as
an optimisation, and the next reader would have to re-derive that it does
nothing. Recorded here so they do not have to.

### 6.2 A length threshold on the cull bracket — worse, and instructive

**Hypothesis.** §5.1's bracket saves a cubic solve and pays for a pass. A short
path — a rectangle is five elements, four of them lines, and a line segment's
exact box *is* its endpoints — has no solve worth skipping, so below some length
the bracket should be pure overhead. This was tried to explain §6.3's shading
figure.

**A/B** with the bracket gated at 12 elements:

| Document | without the gate | with it | |
|---|---:|---:|---|
| `vector_paths_1751` | **−27.9%** | **−13.3%** | half the win given back |
| `shading_tcpdf_030` | +3.1% | +2.1% | barely moved |

**Verdict: refuted, twice over.** The gate cost `vector_paths_1751` half its
improvement — so that document's paths *are* short and the bracket wins on them
anyway — and it did not fix the shading figure, so the shading figure was never
about path length. **Not landed.** The hypothesis it was built on was wrong, and
§6.3 says what the right answer turned out to be.

### 6.3 The shading documents' +2 to +3% — real, measured, and not in the walk

`shading_tcpdf_030` measured **+3.1%** against a self-A/B noise floor of ±0.9%,
reproducibly, and `shading_axial_radial` +1.1%. Inside the 4% band, so a
non-result by the rule — but reproducible enough to deserve an explanation
rather than a shrug, especially after §4.

Bisecting gave incoherent halves (+2.4% and +0.2% on one run, +2.4% and +1.6% on
another, summing to more than the +3.1% whole), which is the same signature §4
diagnosed. The phase table settles it:

| | before | after |
|---|---:|---:|
| `fill_path` (RASTER) | 36.204 ms | 36.750 ms |
| `draw_image` (RASTER) | 3.848 ms | 3.713 ms |
| **ENGINE** | **13.021 ms** | **13.061 ms** |
| TOTAL | 53.925 ms | 54.337 ms |

**The engine half is 13.021 against 13.061 ms — 0.3%.** The whole difference is
in `fill_path`, which is the rasterizer, and which neither commit touches: 51854
identical `fill_path` calls with identical geometry, taking half a percent
longer because the binary's layout moved. It is instruction cache, not the walk.

**A finding about this document that is not a non-result**, and which corrects
P2's characterisation: `shading_axial_radial`'s engine residue is **not**
`pattern.rs`. §7 has it.

## 7. `pattern.rs`, which P2 flagged as unowned — and what it actually is

P2 §4 recorded, as territory belonging to no P-item, that
`shading_axial_radial`'s engine half is 39% shading evaluation and **61%
residue across only 17 shading draws and 33 clips**, concluding "the residue is
the *pattern* machinery in `pattern.rs`, not the walk".

**It is neither.** Two probes settle it, and the second required an instrument
the tree did not have.

**First**, the seam counter says the document makes **28368 `fill_path` calls**
on a page with 33 objects. Grepping for who else calls `fill_path` finds exactly
one caller outside `paint.rs`: `crates/pdfrum-render/src/shading/patch.rs:472`,
the Coons and tensor **mesh** rasterizer. And the walk's own phases confirm the
paths do not come through it — `path prep` is entered **0 times** on
`shading_axial_radial` and **4 times** on `shading_tcpdf_030`, whose engine half
is 12.3 ms.

**Second**, the reason it had no bucket. `Phase::Shading` wraps
`shading::draw_to_pixmap`, and the mesh kinds **never reach it**:
`draw_shading_into`'s `CoonsMesh | TensorMesh` arm calls `draw_patches` against
a scratch device instead, and that call was outside every phase in the
instrument. So its cost fell into the interpretation residue by subtraction —
which is exactly what "61% `pattern.rs` residue" was reading.

P3 added `Phase::Patches` (`1790568`) and the residue names itself:

| Document | ENGINE | `shading` | **`patches`** | patch calls | RASTER |
|---|---:|---:|---:|---:|---:|
| `shading_axial_radial` | 9.51 ms | 3.50 ms | **28.73 ms** | 16 | 26.2 ms |
| `shading_tcpdf_030` | 12.27 ms | 1.15 ms | **47.12 ms** | 3 | 41.0 ms |
| `shading_tensor` | 2.75 ms | 0 | **11.92 ms** | 13 | — |
| `shading_coons` | 0.02 ms | 0 | 0 | 0 | — |

`patches`, like `path prep`, wraps the device calls it makes, so its figure
exceeds the engine half. Netting the RASTER it contains leaves roughly **2.5 ms**
of engine-side patch work on `shading_axial_radial` and **6.1 ms** on
`shading_tcpdf_030` — which is essentially the whole of each document's
unattributed residue.

**So `pattern.rs` needs no owner, and the item P2 flagged should be re-aimed.**
Nothing in `pattern.rs` is 6 ms: its per-tile loop computes one
`Affine::translate` and re-enters the walk, and on these four documents
`draw_tiling_per_tile` is not on the path at all. What is expensive is
**subdividing and filling a Coons/tensor mesh**, in `shading/patch.rs`, and it
is the largest unattributed engine cost left in the corpus. It is a genuine
target — 28368 `fill_path` calls for 16 patches is roughly 1800 quads per patch,
which is a subdivision-depth question — but it is a *shading* question, not a
walk question, and this item deliberately does not open it on its last
measurement. It is named here with its numbers so the next item can.

**`shading_coons` is the control**: zero patch calls, a 0.02 ms engine half, and
it is a Coons document. Whatever it does differently from `shading_tensor` is
where a reader should start.

**The dispatch `match` is a non-finding and it is worth saying so.** It was one
of the five names, and no measurement in this item found a cost in it. A `match`
over a five-variant enum compiles to a jump table; the expensive thing was never
choosing the arm, it was what the arm did. Every millisecond this item moved came
from three functions the arms *call*, and the residue that is left is those same
functions' remaining work rather than the dispatch that reached them.

## 9. The bench ratchet: the debt stands, and one thing to know before paying it

**`benches/baseline.json` is not re-baselined by this item either.** The debt
`4d1e385` recorded is unchanged and now carries this item's improvements too.

**A `ratchet check` run during this session is not evidence about this work, and
it looked like it was.** `ratchet check` reads `target/criterion/**`, which is
whatever the last `cargo bench` left there. On this machine that was **2026-08-30
06:30** — two days before any commit in this item existed. Its output named a
`vector_en_tem` regression across all three backends, which is neither this
item's doing nor, per §4, a render regression at all. Anyone reading a ratchet
verdict must check the mtime under `target/criterion` first.

**One attempt was made and abandoned honestly.** A window opened at load 6.8
(the `osmium` jobs that had held the machine all session finished) and
`cargo bench -p pdfrum-render` was started on cores 8–31. It was contaminated
within two minutes — by a conformance sweep this session started alongside it,
which is nobody's fault but this one's — and the log shows the tell:
`text_cjk_page` reporting **+66.8%**, on a document with no path objects in the
groups this item touched. The run was discarded rather than read.

**What is owed is unchanged and mechanical:**

```
cargo bench -p pdfrum-render                       # on an idle machine, alone
cargo run --release -p pdfrum-bench --bin ratchet -- update
```

`update` writes improvements and fails on regressions, so it cannot loosen
anything by accident, and the direction is known: every change in this item is
strictly less work per object and the interleaved A/Bs put `vector_paths_1751`
28% on the faster side with nothing outside the band. **No number in this
document comes from criterion**; §5 and §6 are all `--sample`, paired,
best-of-N, on a harness whose noise floor is measured in §4.
