# M18 — Data layout pass

**Design:** `docs/design/dod-layout.md`. **Started:** 2026-09-05.
**Method:** callgrind `Ir` on the `profile` binary (`perf` is closed on this
box), cold render unless stated; wall-clock quoted with the load it was taken
at. Conformance board byte-identical after every landing (1757 rows,
1539 / 218).

## 1. `Face::name_index` builds its name map once

**Before** (`crates/pdfrum-font/src/glyphs/face.rs:379-395`): every name
lookup walked `0..num_glyphs` calling `post.glyph_name(gid)`, and for a
`post` 2.0 table that call walks the Pascal-string array from the start —
quadratic per lookup, and a simple font with `/Differences` performs up to
256 lookups against one face. The CFF branch scanned the charset the same
way per name.

**After:** `Face` carries `names: Arc<OnceLock<HashMap<Box<[u8]>, u16>>>`,
built on the first lookup by `build_name_map` in one pass: the CFF charset
once, or the `post` table's index array plus its string array read
sequentially once, first glyph id winning on a duplicate name. The
`cff_unicode_to_gid` path goes through the same map. The old scan is kept
under `cfg(test)` as `name_index_by_scan`, and
`the_name_map_answers_what_the_scan_answered` checks every name of every
TrueType fixture against it plus a miss.

**Why not read-fonts' own `glyph_names()` iterator:** it stops at the first
entry it cannot read (`?` in its V2 arm), where the scan skipped that glyph
and went on. The one-pass build keeps the scan's semantics exactly.

|---|---:|---:|---:|
| whole process `Ir` (2 iterations + open) | 1,097.5 M | 458.0 M | **−58%** |
| `Page::build` inclusive | 852.2 M | 211.7 M | **−75%** |

## 2. The content lexer borrows, and plain decimals take the exact fast path

**Before** (`crates/pdfrum-page/src/tokenize.rs`): `next_element` boxed every
operator keyword (`Element::Keyword(Box<[u8]>)`), the object grammar's
`next_word` returned `word.to_vec()` per token and the reader kept
`last_word: Vec<u8>`, and every real went through `str::from_utf8` plus
`str::parse::<f32>` — a correctly-rounded parse that is exactly what the
oracle does (`fx_string.cpp`, `fast_float`) and exactly what has to be kept.

**After:** `Element<'a>` carries `Keyword(&'a [u8])`; `next_word` returns a
slice of the stream (every token, delimiters included, is contiguous source
bytes, so the truncation rules are a `min` on the length); the reader's
`last_word` is a slice. `parse_real` tries `parse_real_fast` first: the
mantissa as a `u64` and the fractional digit count, accepted only when the
mantissa is below `2^24` and there are at most ten fractional digits, so
both the mantissa and the power of ten are exact in `f32` and one IEEE
division is the correctly rounded value — the same bits the parse gives. An
exponent, a longer mantissa or more digits fall through to the parse
unchanged. Pinned by
`the_real_fast_path_agrees_with_the_parse_bit_for_bit`: 200 000 generated
decimals plus the edges (`-0.0`, `-.`, `.`, `1.2e`, `16777216.0`,
`123.4567890123`, …), `to_bits` equality on every accepted word.

| `vector_paths_1751`, cold render, agg, `Ir` | before | after | |
|---|---:|---:|---:|
| whole process (2 iterations + open) | 287.0 M | 231.2 M | −19% |
| `Page::build` inclusive | 194.3 M | 138.5 M | **−29%** |
| `content::parse_content` | 134.2 M | 78.3 M | −42% |
| `word_to_number` | 63.8 M | 27.2 M | −57% |
| `_int_free` self | 15.3 M | 9.4 M | −39% |

Design exit for this item (`build/vector_paths_1751` −25% or better): **met

`text_foxittext`'s parse is 5.7% of its cold render, so text documents move
little here; their build is fonts (§1).

## 3. `Object::Stream(Box<Stream>)`

`Object` 56 → **32** bytes, a dictionary pair 80 → **56**, `Stream` itself
56. 100 sites touched, almost all match arms that read through the box
unchanged; constructions box, three moves unbox. The API baseline for
`pdfrum-object` records the one changed line. Board byte-identical.

**Peak RSS did not move.** The design's exit asked for RSS on the ten
largest corpus files, measured with the tool's `--txt` (a full pass over
every page), old binary against new, system fonts excluded so the number
is the object store and the page data:

| file | before | after |
|---|---:|---:|
| `text_quick_start` | 31,132 KiB | 29,624 KiB |
| `forms_widgets_407` | 19,308 | 18,952 |
| `image_bug_898443` | 212,732 | 212,336 |
| `mixed_formfield` | 22,452 | 22,920 |
| the other six | 12–21 MB | within ±3% |

The object store is not where a document's memory is: decoded images,
fonts and the page graph are. The change is kept for what it is — a
smaller `Object` in every array and dictionary, and a public type that no
longer pays for a variant it cannot hold in those positions — and the
"memory change" expectation in the design doc is corrected here: it is a
layout change with no RSS number to show for it.

Found by the same measurement, and larger than every item above:
**with system fonts on, six of the ten files peak at 1.1 GB** (§5).

## 4. The clip stack is shared across the objects that carry it

**The measurement the design asked for**, taken over all 44 corpus
documents under callgrind (one cold render each, `agg`): the inclusive
`Ir` of `GraphicsState::clone` as a share of `Page::build`. Forty-three
documents sit at or below **1.5%** (`forms_widgets_407` 1.5%, `text_cjk_page`
1.1%, every image document 0.0%). One trips the 3% threshold:
**`vector_paths_1751` at 9.6%** — 6.46 M of 67.5 M, and only because §2
took 56 M out of the same build; the share was 3.3% before. A 5 010-path
page under one clip clones a `Vec<ClipEntry>` holding a `BezPath` for
every path emitted.

**Change:** `ClipStack.entries` is `Arc<Vec<ClipEntry>>`. The clone every
emitted object takes of its state is one reference count; a `W n`
(`push_path`, `push_text`, `push_empty`) goes through `Arc::make_mut`, which
copies the vector only when an emitted object still shares it — once per
clip change, not once per object. `entries()`, `len`, `bounds` read through
the `Arc` unchanged; no public type moves.

| `vector_paths_1751`, cold render, `Ir`, 1 iteration | before | after |
|---|---:|---:|
| `GraphicsState::clone` inclusive | 6,459,071 | 2,119,617 |
| `Page::build` inclusive | 67,519,121 | 65,038,327 (**−3.7%**) |

The rest of the clone is the 344-byte copy itself and the `Arc` bumps for
colour spaces and fonts, and §1.3 B's verdict stands: sharing the whole
state is not worth a public type for 2 M instructions on the worst
document.

## 5. The system font scan keeps a path per face, not a copy of every font, and runs once per process

**Found** while taking §3's RSS row: six of the ten largest corpus files
peaked at 1.1 GB resident on a full text pass, and the tool's
`--no-system-fonts` took the same files to 12–30 MB. `SystemFontDb::scan`
(`crates/pdfrum-font/src/subst/db.rs`) called `face_bytes_of` on every
face `fontdb` enumerated, which copied the face's bytes out of `fontdb`'s
mapping into an `Arc<[u8]>`, and kept all of them in `sources` — the whole
of `/usr/share/fonts` (490 MB, 1 183 faces here) in the heap on top of the
mapping, for the one face the ladder picks. And the scan was not cached:
once per substituted font.

**After:** `sources: Vec<FaceSource>` holds a path and index per face
(bytes only for a source `fontdb` had in memory already); `describe` reads
the name and `OS/2` tables from the mapped bytes without a copy; the
chosen face is read from disk in `face_bytes` when the ladder picks it.
The host scan is cached in a process-wide `OnceLock` (the code's own note
asked for a measurement before that; it is below). A `--font-dir` scan —
the hermetic test path — stays unshared. The ladder's order is by face
name, so no answer moves.

| tool `--txt`, peak RSS / wall, load ~9 | before | copies removed | + cache |
|---|---:|---:|---:|
| `vector_en_tem` (2 substituted fonts) | 1,162,288 KiB / 1.40 s | 58,148 KiB / 0.43 s | **57,784 KiB / 0.26 s** |
| `text_quick_start` | 1,149,020 / — | 63,612 / 0.29 s | 64,076 / 0.28 s |
| `forms_push_button` | 1,153,564 / — | 60,752 / 0.70 s | **60,616 / 0.24 s** |
| `forms_widgets_407` | 1,147,852 / — | — | 64,732 / 0.24 s |
| same files, `--no-system-fonts` | 15–30 MB / 0.01–0.06 s | | |

The remaining ~45 MB and ~0.2 s are the scan proper — `fontdb` parsing
every installed face's names once — and are paid once per process now.
Design exit for the item (≤ 50 MB on `vector_en_tem`): 58 MB, **missed by
8 MB and named**: the residual is `fontdb`'s own enumeration touching every
file's header pages, which a path-only enumeration of our own could avoid;
not worth a second implementation of directory scanning for 8 MB. Board
byte-identical.

## 6. A text build decodes no images

**Found** in §23 of the perf doc while settling the ratchet: `Page::text_on`
built the page graph through the same `build` a render uses, decoding every
image at full size, and on `image_bug_583804` that decode was 87% of the
text run — for a document with no text at all.

**Change:** `RequestedSize::NoSamples`, the request a text build makes; the
build's image paths (`add_image`, `inline_image`) return before the cache
or the codec, so the image object is not emitted — the outcome a codec's
refusal already had, and text extraction never reads an image object. The
facade's `text_on` sets it around its build and restores the session's
target after, the way `prepare` sets the device-sized target. Text object
indices are a text-walk identity (`ObjectIndex`), not a correlation with
an edit build, so nothing a caller holds moves. `RequestedSize` gains the
variant on `pdfrum-page`'s baseline.

| `--op text`, `Ir` (1 iteration + open) / wall | before | after |
|---|---:|---:|
| `image_bug_583804` | 3,854,572,759 / 183 ms | **1,101,652 / 0.03 ms** |
| `image_bug_898443` | 5,223,166,105 / 242 ms | **1,796,425 / 0.10 ms** |
| `text_foxittext` (no images) | 49.7 M / 2.9 ms | 49.5 M / 3.4 ms (noise) |

Board byte-identical, text tier included: 1781/2063 pages match the
oracle's text as before.
