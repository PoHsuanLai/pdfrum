# M20 — The CLI as a Unix citizen and an agent tool

**Plan:** `PLAN.md` M20, scoped 2026-09-05 from the user's first sessions
with the tool. **Started:** 2026-09-05.

## Phase 1 — composition

The tool composes: stdin in, stdout out, several files at once, and the
knobs a shell script or an agent loop needs. Everything is in
`crates/pdfrum-cli`; the facade had every method this phase needed, so no
library crate changed.

**`-` as the input.** Every reading command's FILE accepts `-`: stdin is
read whole (a PDF's cross-reference table is at its end, so there is
nothing to stream) and opened with `Document::from_bytes_with`, the
password applying as it would to a path. The record says `file  -`; files
a command derives from its input — `render`'s `{stem}-{n}.png`, `split`'s
pages, extracted images — take `stdin` as their stem. `hash` used to read
the path a second time for the file digest; it now digests
`Document::bytes()`, which is the file whole, and that is what makes
`hash -` the file's hash. `view` and `preview` refuse `-` with a one-line
reason: the pager reads its keys from stdin, and the preview draws on a
terminal.

**`-o -` as the output.** Every writing command — `pages
merge|slice|reorder|create|nup|booklet`, `forms fill|flatten`, `repair`,
`optimize`, `security decrypt|encrypt`, `inspect revision`, and `render`
as before — writes to stdout for `-`. `out::Sink` is the one place: made
first, so `-` on a terminal is refused before any work (`refusing to write
a PDF to a terminal; give -o a path or pipe it`), then handed the bytes.
The commands produce those bytes through the facade's `write_to`,
`write_form_to` and `write_pages_to` twins instead of the path-taking
saves; the saves were already those twins plus `fs::write`, so nothing
changed but who writes the file. For a file the summary line stays on
stdout; for `-` the same words go to stderr as a notice, `pdfrum: -: 3
pages`, so stdout is the PDF and nothing else. `pages split` writes many
files and refuses `-`. `forms fill --scripts` used to reopen the written
path for its script pass; it now runs the pass on the bytes in memory,
which is what lets it write to stdout too.

**Several files.** `info`, `hash`, `doctor` and `search` take one or more
FILEs. Text output is one record per file with a blank line between;
`--json` on several files is the array of the per-file documents, each
carrying its `file` key, and one file stays the one document it was, so
nothing written against the M19 shapes breaks. `search` names the file
before the page, `a.pdf:page 2:…`, when given more than one file or `-H`,
and never with `--no-filename`; its JSON for several files is `[{file,
hits}]`; it prints as each file is done, as `grep` does, and exits 1 only
when no file had a hit. `doctor --strict` exits 3 when any file had
notices. A file that cannot be opened is reported on stderr and the run
continues, exit 1 at the end, as `grep` does — `out::per_file` is the
loop and `out::error` the one place an error line is painted, which
`main` uses too.

One deviation from the scoping note: `grep`'s `-h` for `--no-filename`
is not there, because `-h` is clap's help on every command and keeping
that is worth more than the one-letter parity. `--no-filename` and `-H`
are.

**`--quiet` and `--verbose`.** `-q` drops the notices — the recovery
notice `open` prints, the written-file summaries of `render` and of `-o
-` — and leaves errors alone. `-v` replaces the one-line recovery notice
with every parser diagnostic on open, one per line as `pdfrum: <file>:
<severity> at byte N: <what>`, the list `doctor` shows, on any command.
They conflict. The level is a process-wide atomic set once by `main` and
read where a notice is printed; forty command signatures did not need to
carry it.

**`PDFRUM_PASSWORD`.** `--password` reads the variable when the flag is
absent (clap's `env`, with the value hidden from the help), so a password
need not land in the shell's history. The flag wins when both are set,
and with neither a terminal is still asked once, silently.

**`--jsonl`.** `search`, `extract links|annotations|images|fonts|attachments`,
`inspect xref|revisions|structure` and `forms dump` print one compact
JSON object per line — the same objects `--json` puts in its array — for
`jq -c`, `xargs` and `while read`. `--json` and `--jsonl` conflict.
`inspect xref --json` is the table with its trailer, an object, so its
`--jsonl` is the entries one per line; `search --jsonl` over several
files puts the `file` on each hit. `out::Json` is the mode and
`out::items` the one printer; `JsonArgs` is flattened into each of the
ten commands, so a command cannot have one flag without the other.

**Tests.** `tests/cli.rs` grew seven tests and one expected file
(`info_two_files.txt`); no new fixture. The stdin tests pipe a fixture in
and compare with the path form; the `-o -` test runs the chain from the
plan — `pages slice … -o - | pdfrum extract text -` — and then every
writing command into stdout, checking the PDF header and the stderr
notice; the `--jsonl` test checks, for every command that has it, that
the lines are objects and that together they equal what `--json` gives.
What is not tested: the refusal of `-o -` on a terminal, which needs a
pty; it was tried by hand.

**What the facade lacked:** nothing. Every method this phase wanted was
there — `from_bytes_with`, the three `write_*_to` twins, `Document::bytes`,
`Diagnostics::entries`.

**Not done here:** `extract words` (phase 2), so the three-command chain
of the milestone's exit criterion was run with `extract text - --json`
in the middle; the pipe shape is what phase 1 owed and it works.

## Phase 2 — facade: `Page::words`

`Page::words(&self) -> Vec<Word>` on `pdfrum`, with `Word { text, rect,
range, font, size }` — the shape `extract words --json` and a citation
pipeline want. It is a view over the text page the extractor already
builds, not a second layout: `Page::text()` is extracted once and
`TextPage::words` splits `chars` on whitespace in reading order (a
generated space or line break, or any Unicode whitespace). A word's
`text` is `TextPage::slice` over its `range`, so it slices back out of the
text page for context; its `rect` is the union of its glyphs' `char_box`es,
in the same page space `TextPage::rects` and `PageLink::rect` use (the
page's own y-up, unrotated coordinates — on `hello_world_2_pages.pdf` the
line set at `20 50 Td` reports `x0 ≈ 20` and a box straddling `y = 50`);
`font` and `size` come from the first character. `size` is the `Tf`
operand scaled by the text matrix's vertical scale, so a `1 Tf` under a
`12 0 0 12` matrix reads as 12 points rather than 1. The scripting API's
word list (`pdfrum_text::words`, `Doc.getPageNthWord`) is a different
reading of "word" and is untouched.

**What `pdfrum-text` had, and what it gained.** `CharBox` already carried
`char_box`, `font_size`, `matrix` and the `ObjectIndex` of the text object
that drew it, but no font name reached the text page. `TextPage` gained a
`fonts: BTreeMap<ObjectIndex, String>` filled in `extract` from each run's
`Font::base_font_name` (the subset tag stripped and standard-14 aliases
canonicalized, as the font crate already normalizes it — `Times-Roman`, not
`ABCDEF+Times-Roman`; a Type 3 font has no base name and is absent), read
through a character by `TextPage::font_name(CharIndex)`, and
`TextPage::words` with the `Word` type, which the facade re-exports. Unit
tests in `crates/pdfrum-text/src/word.rs` pin the split, the ranges, the
box union, the matrix-scaled size and the font lookup on a synthetic page;
`crates/pdfrum/tests/words.rs` pins the fixture's four words per page, the
left-to-right non-overlapping boxes, the fonts (`Times-Roman`,
`Helvetica`) and sizes (12, 16 — read off the content stream), and the
corpus guide's first page (45 words, every one non-empty with a
positive-area box).

**Untouched:** nothing a renderer or extractor already calls changed; the
`fonts` field is additive and every existing `TextPage` reader is
indifferent to it. The conformance board is byte-identical by construction.

## Phase 5 — facade fills

The library side of the phase-5 verbs — `metadata set`, `attach add`,
`stamp` — three fills on `DocEdit`, one commit each, in `crates/pdfrum-edit`
and the facade; the CLI verbs are a separate landing. Every fill has a
round-trip test (save, reopen through our own parser, assert) and an oracle
round trip through `pdfium_test` that skips without the checkout. The
`pages delete` and `pages rotate` verbs needed nothing: `DocEdit::delete_pages`
and `DocEdit::set_rotation` were already there.

**Metadata.** `DocEdit::set_metadata(&Metadata)` takes the same value
`Document::metadata()` reads, so a caller changes one field and keeps the
rest, and writes all eight keys of `/Info`: a `Some` as a PDF text string
(`PDFDocEncoding` when it fits, UTF-16BE behind a byte-order mark otherwise —
`pdfrum_object::encode_text` already did this), a `None` or an empty string
removing the key. Underneath, `pdfrum_edit::set_info_entry` sets or removes
one entry, and a document without an `/Info` gains one as a new object the
saved trailer names — the one trailer key an edit overrides, carried on
`EditDoc` and read back by the writer for both the trailer and its
reachability walk. `/ModDate` is the one key the save may overwrite: a save
with `IdSource::Random` (the default) stamps its own time, on a clone of the
session so the session never carries a date it did not set; a reproducible
save (`IdSource::Fixed`) writes `modification_date` as given, so the same
input saves to the same bytes. `pdfrum_edit::pdf_date` spells a `SystemTime`
as `D:YYYYMMDDHHmmSSZ00'00'`, always UTC, with the civil date from Hinnant's
era arithmetic rather than a calendar dependency. XMP `/Metadata` is not
touched and the method's doc says so — a document carrying both will have
the two disagree after this. Oracle: `pdfium_test --show-metadata` prints
every key we wrote.

**Attachments.** `add_attachment(name, bytes, &AttachmentOptions)` where
`AttachmentOptions { description, mime_type, modified }` is a config struct
with `Default`, every field optional and an absent one writing no key —
by reference, as every other options struct on the facade is passed. The
embedded file stream is now the shape the reader looks for: `/Type
/EmbeddedFile`, the MIME type as `/Subtype` (`text/plain` is the name
`/text#2Fplain` on the wire), `/DL`, and `/Params` with `/Size`, an MD5
`/CheckSum` and `/ModDate`; the file specification carries `/Desc`. `modified`
is a PDF date string like `Metadata`'s dates, and `pdfrum::pdf_date` is
re-exported for a caller holding a `SystemTime`. The name tree is created
when absent and rewritten flat and sorted when present, as before; the
stream is flate-compressed by the save like every other filterless stream.
`remove_attachment(name) -> bool` takes every entry of that name out;
`delete_attachment(index)` stays. Oracle: `pdfium_test --save-attachments`
writes the files back out and they compare byte for byte, for a tree
created from nothing and one grown from the fixture's — judged by the files,
because `pdfium_test` exits non-zero on its own "unsupported feature:
attachment" notice even when it wrote every one.

**Stamp.** `stamp_text(text, &StampOptions)` and `stamp_image(&image, width,
&StampOptions)`, with `StampOptions { position, margin, angle, opacity, font,
font_size, color }` and `StampPosition { Center, TopLeft, TopRight,
BottomLeft, BottomRight }`. The builders could do it: a `TextBuilder` or
`ImageBuilder` pushed onto a `PageEdit` regenerates as a *new* `/Contents`
element appended after the page's own — the writer's per-stream frame
undoes whatever transform the page's content left behind — so the existing
streams are copied through untouched and the stamp paints on top. Opacity
is the `/ca` the emitter already writes from `fill_alpha`; the image's is set
on the built object's state. Rotation is `PageEdit::transform`'s matrix
composition, shared with the stamp as `transform_object`. What the builders
lacked was measurement: a standard font's extent comes from
`pdfrum_font::load` over the `/Font` dictionary the session wrote, so the
box is centred on real widths. Placement is in the page *as displayed*: a
corner on a page with `/Rotate 90` is that corner on the screen and the
text reads upright there — the displayed box is mapped back through the
inverse of the display rotation, and the page's own turn is added to the
angle. One `/Font` object serves every page of a call. The stamp is page
content, not an annotation: it draws over the content and under any
annotation a viewer paints. Oracle: `pdfium_test --txt` extracts the stamp
beside the page's own text, and `--md5` renders a different image.

**Two things this exposed, both fixed here.** First, the text emitter
swapped `b` and `c` of `Tm` on the way out — copied from PDFium's
`GetTextMatrix`, which un-swaps that engine's *transposed storage*; our
`TextObject::matrix` already holds the true matrix (`ctm * Tm * hscale`), so
the swap turned every rotated or slanted text object the other way on
regeneration. `PageEdit::transform` by +90° came back as −90° after a save.
It is written straight through now, with a unit test on a quarter turn.
Second, `DocEdit::write_pages_to` read a page's dictionary and resources
from the base document rather than the session's overlay, so a rotation
set in the same session was lost under a content rewrite of that page, and
a second stamp swept the first's `/Font` name out of the resources. Page
edits now read through the overlay, and the stamp builds its graph from
the page *as the session has it* (`page::build_graph`, the one builder for
both), so an earlier appended stream is a clean stream of the graph and the
names it uses are kept. `apply_page` is the one place a page edit becomes
objects.

**Tests.** `crates/pdfrum-edit/src/info.rs` (unit: entries set, removed,
a broken `/Info` replaced, dates), `crates/pdfrum-edit/tests/info.rs` (full
and incremental saves), `crates/pdfrum/tests/metadata.rs`, the writer half
of `crates/pdfrum/tests/attachments.rs`, `crates/pdfrum/tests/stamp.rs`
(every page, order, centre and corner placement by word boxes, angle,
opacity and colour, a rotated page, two stamps accumulating, an image's
aspect and opacity, a refused width, a reproducible save). API baseline
updated with each commit; the enum gate counts `StampPosition`'s five.
