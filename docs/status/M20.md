# M20 — The CLI as a Unix citizen and an agent tool

**Plan:** `PLAN.md` M20, scoped 2026-09-05 from the user's first sessions
with the tool. **Started:** 2026-09-05.

## Phase 1 — composition

The tool composes: stdin in, stdout out, several files at once, and the
knobs a shell script or an agent loop needs. Everything is in
`crates/pdfrum-cli`; the facade had every method this phase needed, so no
library crate changed.

**`-` as the input.** Every reading command's FILE accepts `-`: stdin is
read whole (a PDF's cross-reference table is at its end, so there is
nothing to stream) and opened with `Document::from_bytes_with`, the
password applying as it would to a path. The record says `file  -`; files
a command derives from its input — `render`'s `{stem}-{n}.png`, `split`'s
pages, extracted images — take `stdin` as their stem. `hash` used to read
the path a second time for the file digest; it now digests
`Document::bytes()`, which is the file whole, and that is what makes
`hash -` the file's hash. `view` and `preview` refuse `-` with a one-line
reason: the pager reads its keys from stdin, and the preview draws on a
terminal.

**`-o -` as the output.** Every writing command — `pages
merge|slice|reorder|create|nup|booklet`, `forms fill|flatten`, `repair`,
`optimize`, `security decrypt|encrypt`, `inspect revision`, and `render`
as before — writes to stdout for `-`. `out::Sink` is the one place: made
first, so `-` on a terminal is refused before any work (`refusing to write
a PDF to a terminal; give -o a path or pipe it`), then handed the bytes.
The commands produce those bytes through the facade's `write_to`,
`write_form_to` and `write_pages_to` twins instead of the path-taking
saves; the saves were already those twins plus `fs::write`, so nothing
changed but who writes the file. For a file the summary line stays on
stdout; for `-` the same words go to stderr as a notice, `pdfrum: -: 3
pages`, so stdout is the PDF and nothing else. `pages split` writes many
files and refuses `-`. `forms fill --scripts` used to reopen the written
path for its script pass; it now runs the pass on the bytes in memory,
which is what lets it write to stdout too.

**Several files.** `info`, `hash`, `doctor` and `search` take one or more
FILEs. Text output is one record per file with a blank line between;
`--json` on several files is the array of the per-file documents, each
carrying its `file` key, and one file stays the one document it was, so
nothing written against the M19 shapes breaks. `search` names the file
before the page, `a.pdf:page 2:…`, when given more than one file or `-H`,
and never with `--no-filename`; its JSON for several files is `[{file,
hits}]`; it prints as each file is done, as `grep` does, and exits 1 only
when no file had a hit. `doctor --strict` exits 3 when any file had
notices. A file that cannot be opened is reported on stderr and the run
continues, exit 1 at the end, as `grep` does — `out::per_file` is the
loop and `out::error` the one place an error line is painted, which
`main` uses too.

One deviation from the scoping note: `grep`'s `-h` for `--no-filename`
is not there, because `-h` is clap's help on every command and keeping
that is worth more than the one-letter parity. `--no-filename` and `-H`
are.

**`--quiet` and `--verbose`.** `-q` drops the notices — the recovery
notice `open` prints, the written-file summaries of `render` and of `-o
-` — and leaves errors alone. `-v` replaces the one-line recovery notice
with every parser diagnostic on open, one per line as `pdfrum: <file>:
<severity> at byte N: <what>`, the list `doctor` shows, on any command.
They conflict. The level is a process-wide atomic set once by `main` and
read where a notice is printed; forty command signatures did not need to
carry it.

**`PDFRUM_PASSWORD`.** `--password` reads the variable when the flag is
absent (clap's `env`, with the value hidden from the help), so a password
need not land in the shell's history. The flag wins when both are set,
and with neither a terminal is still asked once, silently.

**`--jsonl`.** `search`, `extract links|annotations|images|fonts|attachments`,
`inspect xref|revisions|structure` and `forms dump` print one compact
JSON object per line — the same objects `--json` puts in its array — for
`jq -c`, `xargs` and `while read`. `--json` and `--jsonl` conflict.
`inspect xref --json` is the table with its trailer, an object, so its
`--jsonl` is the entries one per line; `search --jsonl` over several
files puts the `file` on each hit. `out::Json` is the mode and
`out::items` the one printer; `JsonArgs` is flattened into each of the
ten commands, so a command cannot have one flag without the other.

**Tests.** `tests/cli.rs` grew seven tests and one expected file
(`info_two_files.txt`); no new fixture. The stdin tests pipe a fixture in
and compare with the path form; the `-o -` test runs the chain from the
plan — `pages slice … -o - | pdfrum extract text -` — and then every
writing command into stdout, checking the PDF header and the stderr
notice; the `--jsonl` test checks, for every command that has it, that
the lines are objects and that together they equal what `--json` gives.
What is not tested: the refusal of `-o -` on a terminal, which needs a
pty; it was tried by hand.

**What the facade lacked:** nothing. Every method this phase wanted was
there — `from_bytes_with`, the three `write_*_to` twins, `Document::bytes`,
`Diagnostics::entries`.

**Not done here:** `extract words` (phase 2), so the three-command chain
of the milestone's exit criterion was run with `extract text - --json`
in the middle; the pipe shape is what phase 1 owed and it works.

## Phase 2 — facade: `Page::words`

`Page::words(&self) -> Vec<Word>` on `pdfrum`, with `Word { text, rect,
range, font, size }` — the shape `extract words --json` and a citation
pipeline want. It is a view over the text page the extractor already
builds, not a second layout: `Page::text()` is extracted once and
`TextPage::words` splits `chars` on whitespace in reading order (a
generated space or line break, or any Unicode whitespace). A word's
`text` is `TextPage::slice` over its `range`, so it slices back out of the
text page for context; its `rect` is the union of its glyphs' `char_box`es,
in the same page space `TextPage::rects` and `PageLink::rect` use (the
page's own y-up, unrotated coordinates — on `hello_world_2_pages.pdf` the
line set at `20 50 Td` reports `x0 ≈ 20` and a box straddling `y = 50`);
`font` and `size` come from the first character. `size` is the `Tf`
operand scaled by the text matrix's vertical scale, so a `1 Tf` under a
`12 0 0 12` matrix reads as 12 points rather than 1. The scripting API's
word list (`pdfrum_text::words`, `Doc.getPageNthWord`) is a different
reading of "word" and is untouched.

**What `pdfrum-text` had, and what it gained.** `CharBox` already carried
`char_box`, `font_size`, `matrix` and the `ObjectIndex` of the text object
that drew it, but no font name reached the text page. `TextPage` gained a
`fonts: BTreeMap<ObjectIndex, String>` filled in `extract` from each run's
`Font::base_font_name` (the subset tag stripped and standard-14 aliases
canonicalized, as the font crate already normalizes it — `Times-Roman`, not
`ABCDEF+Times-Roman`; a Type 3 font has no base name and is absent), read
through a character by `TextPage::font_name(CharIndex)`, and
`TextPage::words` with the `Word` type, which the facade re-exports. Unit
tests in `crates/pdfrum-text/src/word.rs` pin the split, the ranges, the
box union, the matrix-scaled size and the font lookup on a synthetic page;
`crates/pdfrum/tests/words.rs` pins the fixture's four words per page, the
left-to-right non-overlapping boxes, the fonts (`Times-Roman`,
`Helvetica`) and sizes (12, 16 — read off the content stream), and the
corpus guide's first page (45 words, every one non-empty with a
positive-area box).

**Untouched:** nothing a renderer or extractor already calls changed; the
`fonts` field is additive and every existing `TextPage` reader is
indifferent to it. The conformance board is byte-identical by construction.

## Phase 2 — CLI

The three commands the plan's second phase names, on the facade phase 2
gave it; everything is in `crates/pdfrum-cli`, and the facade lacked
nothing.

**`extract words`.** `pdfrum extract words FILE [--pages RANGE]
[--json|--jsonl]` over `Page::words`. For people a table — `PAGE  WORD
AREA  FONT  SIZE`, the area as `x0 y0 x1 y1` in points, the size to two
decimals, `no words` when there are none. In JSON one object per word,
`{page, text, x0, y0, x1, y1, font, size, start, end}`: the box flat
rather than nested so `jq 'select(.y0 > 700)'` needs no indexing, `font`
null when the font has no base name (a Type 3 font), and `start..end` the
word's character range in the page's text, the same count `extract text`
and `search --json` use, so a word slices back out of the page's text for
context. The test pins the table on `hello_world_2_pages.pdf` (four words
a page, `Times-Roman` at 12 and `Helvetica` at 16, read off the content
stream), the ranges, the y-up geometry, the 45 words of the corpus
guide's first page, and `--jsonl`. The milestone's exit chain now runs
with its middle command: `pdfrum pages slice benches/corpus/text_quick_start.pdf
--pages 1 -o - | pdfrum extract words - --json | jq '.[0]'` gives the
guide's first word, `Foxit` in `Segoe Print,Bold` at 10.56 points.

**`inspect object --json`.** `{object, generation, value, hints}`, with
`value` in one fixed encoding: null, booleans and numbers as themselves;
a name as `{"name": "Type"}`; a string as `{"string": "…"}` after PDF text
decoding (`PdfString::as_text`: UTF-16 with a byte-order mark, else
PDFDocEncoding) when what came out is text, else `{"hex": "…"}` with its
bytes; an array as an array; a dictionary as an object keyed by the name,
a repeated key keeping its last value (the effective view the text
printer and `hash` already take); a reference as `{"ref": [num, gen]}`; a
stream as `{"dict": {…}, "stream": {"length": N, "filters": […]}}` with
no data, `--decode` still giving that and the two flags conflicting.
`hints` is the `% …` of the text form — what each top-level reference
points at — keyed by the dictionary key, and `{}` when there is none.
The encoding lives in `syntax::json` beside the printer, documented there
and in the flag's long help.

What "text" means for a string had to be decided: PDFDocEncoding gives
every byte a character, so decoding never fails, and a rule was needed
for when the result is not a string a person meant. The rule is that the
decoded text has no control character but tab, line feed and carriage
return, and no replacement character — so a `/Title` is a string, an
`/ID` of sixteen random bytes is hex, and a UTF-16 title comes out as
its characters. The hand-built PDF in the test has one of each and a
repeated key.

**`schema`.** `pdfrum schema [COMMAND…]` prints an example of the
document a command's `--json` emits, every key with a representative
value, an optional key shown rather than left out; with no argument it
lists the commands that have one, `COMMAND  DESCRIPTION`. The plan said
"generated from the same `serde` types", and the honest way to do that
without a schema crate was weighed: serializing a sample of each report
type would have to build every report from a fixture inside the binary,
and the small fixture that is cheap to embed gives most commands an
empty array — no keys at all. So `schema.rs` is a table kept by hand
beside the structs, and two tests keep it true: a unit test walks the
clap command tree and fails when a command has `--json` and no entry, or
an entry and no command (`scripts run` follows the feature); the CLI
test runs nineteen of the commands on the fixtures and checks every key
they print is in the example. A key renamed in a struct fails the second
test; a command added without an entry fails the first.

**Tests.** `tests/cli.rs` grew three tests and one expected file
(`words_hello_world_2_pages.txt`), and `syntax.rs` and `schema.rs` one
unit test each; no new fixture — the binary-string PDF is written by the
test with a correct cross-reference table (`pdf_of`), which turned up
one thing worth knowing: a document whose page tree is empty opens with
`RootRecovered` and a rebuilt table, so the hand-built file has a page.

**What the facade lacked:** nothing. `Page::words`, `Word`,
`CharIndex::get`, `PdfString::as_text`, `Name::as_text`, `Dict::iter`
and `Document::fetch` were all there.

**Not done here:** phases 3 to 5. The exit criterion's chain works;
the other four phases are still owed before M20 is met.

## Phase 4 — serve

`pdfrum serve --stdio`: one process, each document parsed once and kept
under a small integer id, and the commands as JSON-RPC 2.0 methods over
stdin and stdout with the same JSON shapes their `--json` prints; and,
on the same process, `--mcp` for the Model Context Protocol's tool
surface, so an agent host discovers `pdfrum` as a tool set. No new
dependency: `serde_json` carries the wire. Everything is in
`crates/pdfrum-cli` — `src/rpc.rs` (the wire and the method table),
`src/cmd/serve.rs` (the loop, the session, the dispatch), one `Serve`
variant in `main.rs` — and the facade lacked nothing.

**The wire.** Newline-delimited JSON, one request per line in and one
response per line out; Content-Length framing is not used, because a
line is what `jq -c`, a shell loop and every MCP host's stdio transport
already speak. A line that is not JSON gets `-32700`; JSON that is not a
2.0 request (`jsonrpc` must be `"2.0"`, `method` must be there) gets
`-32600`; a request without an `id` is a notification and gets nothing
back. The other codes follow one rule: `-32601` for a method that does
not exist, `-32602` when the *request* is wrong — a missing or unknown
param (`deny_unknown_fields`, so a typo is caught), an id that names no
open document, a page past the end, `dpi` and `scale` together, bytes
that are not base64 — and `-32000` when the *work* failed, with the
message the CLI would have printed, `pdfrum: cannot open a.pdf: …`,
built by the same `out::error_line`. Every message starts `pdfrum: `.
Stdout carries responses and nothing else: `serve` sets the verbosity to
quiet unless `--verbose`, which logs one `pdfrum: serve: <method>: ok`
or `… <message> (<code>)` line per request on stderr. `shutdown` ends
the loop after its reply; closing stdin ends it without one; both exit 0.

**The session.** `open {file}` or `open {bytes_base64}` parses once and
answers with the `info` document plus `doc`, the id; ids start at 1 and
are never reused. A document opened from bytes is named `-` in every
report's `file`, as stdin is on the command line, and `open {file: "-"}`
is refused, since stdin is the wire. `--password` is the password for an
`open` without one, so an MCP host's fixed command can carry it through
`PDFRUM_PASSWORD`. `--max-docs N` (default 16) is the ceiling; the one
open too many is `-32000` naming the flag. One `RenderSession` serves the
whole session, so glyphs and images are cached across pages and documents.

**The methods.** Each mirrors a command, takes the command's flags as
params under the same names (`pages` is the `--pages` grammar, as a
string), and returns exactly the command's `--json` document, so a client
learns one set of shapes; `pdfrum schema serve` prints the table below
with each method's JSON Schema of params and its result example, the
example reused from `schema.rs` where the command has one.

Three things differ from the commands by design. A method never writes
a file: the writers hand the PDF back as `bytes_base64` (and with
`deterministic` the very bytes `pages slice --deterministic -o -` writes,
which the test checks), and the `-o DIR` of `attachments`, `images` and
`fonts` has no twin, so their rows never carry `written` and the schema
examples drop it. `image` is the pixels `extract images -o` would have
written, by the `index` that `images` gave the picture for the same
`pages`/`all` selection, always as PNG. `diff` compares two open
documents by id, with `visual` for the pixel counts and no picture.

**Refactoring.** The rule was one implementation per command: the
session calls the same function the command does, with printing left
to the command. Most modules already split `report()` from `print()`
(`info`, `hash`, `doctor`, `signatures`); the rest were split the same
way — `page_texts`, `word_rows`, `page_markdown`, `link_rows`,
`toc_rows`, `attachment_rows`, `annotation_rows`, `image_rows`,
`font_rows` in `extract`; `find` and `Hit` made public in `terminal`;
`render_page` and `checked_scale` in `render`; `field_rows` and
`fill_values` in `forms`; `object_report`, `xref_report`,
`revision_rows`, `structure_rows` in `inspect`; `Compare` and `report`
in `diff`; `slice_bytes` and `merge_bytes` in `pages`. `image_rows` now
returns the row with its picture, so the command's file-writing loop
and the session's `image` read the same list. Nothing a command prints
changed; the CLI tests pin that.

**MCP.** `pdfrum serve --stdio --mcp` answers `initialize` with
`protocolVersion` `2024-11-05`, `capabilities: {tools: {}}` and
`serverInfo: {name: "pdfrum", version}`; ignores
`notifications/initialized` and `notifications/cancelled`; answers
`ping` with `{}`; lists one tool per method in `tools/list`, each with a
one-line `description` and an `inputSchema` — a JSON Schema object built
by hand from the method's params in `rpc.rs`, `additionalProperties:
false`; and dispatches `tools/call {name, arguments}` to the same
functions. A result is `{content: [{type: "text", text: <the JSON
serialized>}]}`; when the result carries `png_base64` (`render`,
`image`) the picture goes into a second `{type: "image", data,
mimeType: "image/png"}` block and the key is taken out of the text, so
a host does not hand a model the same base64 twice. A method that fails
comes back as `{content: [{type: "text", text: "pdfrum: …"}], isError:
true}`, as the protocol has it, so the model sees the reason; an unknown
tool name is the JSON-RPC error `-32602`. The plain methods are not on
the MCP surface (`info` there is `-32601`), and `shutdown` is not a
tool. Since a host spawns the server with a fixed command, `open` takes
a path, and documents persist until `close` or exit. Two points were
decided from memory of the specification and should be checked against
a real host: tool names use underscores (`forms_dump`, `pages_slice`)
because the hosts' tool-name grammar is `[A-Za-z0-9_-]`, so the plain
name and the tool name of the four dotted methods differ; and
`initialize` answers `2024-11-05` whatever version the client offers,
where a newer client is expected to accept an older server.

**Tests.** `tests/serve.rs` drives the binary over pipes: every line of
stdout is parsed, so a stray print fails every test. The seven tests
cover the open/info/text/words/render/search/close round trip on the
fixtures; each error code with its message; `--max-docs 1` refusing the
second open until the first is closed; `shutdown` ending the session
mid-stream, EOF exiting 0, and `--verbose`'s one line; bytes in
(`bytes_base64`) and files out, with `pages.slice --deterministic`
byte-identical to the command line, `pages.merge`, `diff`, `forms.fill`,
`images` and `image`; every method run once against `schema serve`, its
result's keys at every depth a subset of the example's (and every method
in the table run, so a method added without a run fails); and the MCP
sequence `initialize` → `tools/list` → `tools/call` with the exact keys,
the image block, `isError`, `ping` and the notification's silence. Unit
tests in `rpc.rs` and `serve.rs` pin the parser's two codes, that every
method in the table is dispatched and nothing else is, the tool-name
grammar, and the image-block split; `term.rs` gained `unbase64` beside
`base64`, with the RFC vectors and a 256-byte round trip.

**Skipped, and why.** `preview` and `view` draw on a terminal.
`pages split` writes many files. The other writers — `pages
reorder|create|nup|booklet`, `repair`, `optimize`, `security
decrypt|encrypt`, `inspect revision`, `forms flatten` — were not in the
phase's list; each is a `{bytes_base64}` twin on the pattern
`pages.slice` sets and a small addition when wanted. `scripts run` and
`forms fill --scripts` are the feature, and the session has no script
pass. `schema`, `completions` and `manpage` are about the tool, not a
document. An `attachment {doc, name} -> {bytes_base64}` for an embedded
file's data is the obvious next method; `attachments` lists them without
it. `open` takes no `name` for bytes, so a document sent as bytes is `-`
in `diff`'s `left`/`right` too; the ids tell them apart.

**What the facade lacked:** nothing. `Document::from_bytes_with`,
`Pixmap::encode_png`, `PageImage::pixmap`, `RenderSession` across
documents, and the `write_*_to` twins were all there.

## Phase 5 — facade fills

The library side of the phase-5 verbs — `metadata set`, `attach add`,
`stamp` — three fills on `DocEdit`, one commit each, in `crates/pdfrum-edit`
and the facade; the CLI verbs are a separate landing. Every fill has a
round-trip test (save, reopen through our own parser, assert) and an oracle
round trip through `pdfium_test` that skips without the checkout. The
`pages delete` and `pages rotate` verbs needed nothing: `DocEdit::delete_pages`
and `DocEdit::set_rotation` were already there.

**Metadata.** `DocEdit::set_metadata(&Metadata)` takes the same value
`Document::metadata()` reads, so a caller changes one field and keeps the
rest, and writes all eight keys of `/Info`: a `Some` as a PDF text string
(`PDFDocEncoding` when it fits, UTF-16BE behind a byte-order mark otherwise —
`pdfrum_object::encode_text` already did this), a `None` or an empty string
removing the key. Underneath, `pdfrum_edit::set_info_entry` sets or removes
one entry, and a document without an `/Info` gains one as a new object the
saved trailer names — the one trailer key an edit overrides, carried on
`EditDoc` and read back by the writer for both the trailer and its
reachability walk. `/ModDate` is the one key the save may overwrite: a save
with `IdSource::Random` (the default) stamps its own time, on a clone of the
session so the session never carries a date it did not set; a reproducible
save (`IdSource::Fixed`) writes `modification_date` as given, so the same
input saves to the same bytes. `pdfrum_edit::pdf_date` spells a `SystemTime`
as `D:YYYYMMDDHHmmSSZ00'00'`, always UTC, with the civil date from Hinnant's
era arithmetic rather than a calendar dependency. XMP `/Metadata` is not
touched and the method's doc says so — a document carrying both will have
the two disagree after this. Oracle: `pdfium_test --show-metadata` prints
every key we wrote.

**Attachments.** `add_attachment(name, bytes, &AttachmentOptions)` where
`AttachmentOptions { description, mime_type, modified }` is a config struct
with `Default`, every field optional and an absent one writing no key —
by reference, as every other options struct on the facade is passed. The
embedded file stream is now the shape the reader looks for: `/Type
/EmbeddedFile`, the MIME type as `/Subtype` (`text/plain` is the name
`/text#2Fplain` on the wire), `/DL`, and `/Params` with `/Size`, an MD5
`/CheckSum` and `/ModDate`; the file specification carries `/Desc`. `modified`
is a PDF date string like `Metadata`'s dates, and `pdfrum::pdf_date` is
re-exported for a caller holding a `SystemTime`. The name tree is created
when absent and rewritten flat and sorted when present, as before; the
stream is flate-compressed by the save like every other filterless stream.
`remove_attachment(name) -> bool` takes every entry of that name out;
`delete_attachment(index)` stays. Oracle: `pdfium_test --save-attachments`
writes the files back out and they compare byte for byte, for a tree
created from nothing and one grown from the fixture's — judged by the files,
because `pdfium_test` exits non-zero on its own "unsupported feature:
attachment" notice even when it wrote every one.

**Stamp.** `stamp_text(text, &StampOptions)` and `stamp_image(&image, width,
&StampOptions)`, with `StampOptions { position, margin, angle, opacity, font,
font_size, color }` and `StampPosition { Center, TopLeft, TopRight,
BottomLeft, BottomRight }`. The builders could do it: a `TextBuilder` or
`ImageBuilder` pushed onto a `PageEdit` regenerates as a *new* `/Contents`
element appended after the page's own — the writer's per-stream frame
undoes whatever transform the page's content left behind — so the existing
streams are copied through untouched and the stamp paints on top. Opacity
is the `/ca` the emitter already writes from `fill_alpha`; the image's is set
on the built object's state. Rotation is `PageEdit::transform`'s matrix
composition, shared with the stamp as `transform_object`. What the builders
lacked was measurement: a standard font's extent comes from
`pdfrum_font::load` over the `/Font` dictionary the session wrote, so the
box is centred on real widths. Placement is in the page *as displayed*: a
corner on a page with `/Rotate 90` is that corner on the screen and the
text reads upright there — the displayed box is mapped back through the
inverse of the display rotation, and the page's own turn is added to the
angle. One `/Font` object serves every page of a call. The stamp is page
content, not an annotation: it draws over the content and under any
annotation a viewer paints. Oracle: `pdfium_test --txt` extracts the stamp
beside the page's own text, and `--md5` renders a different image.

**Two things this exposed, both fixed here.** First, the text emitter
swapped `b` and `c` of `Tm` on the way out — copied from PDFium's
`GetTextMatrix`, which un-swaps that engine's *transposed storage*; our
`TextObject::matrix` already holds the true matrix (`ctm * Tm * hscale`), so
the swap turned every rotated or slanted text object the other way on
regeneration. `PageEdit::transform` by +90° came back as −90° after a save.
It is written straight through now, with a unit test on a quarter turn.
Second, `DocEdit::write_pages_to` read a page's dictionary and resources
from the base document rather than the session's overlay, so a rotation
set in the same session was lost under a content rewrite of that page, and
a second stamp swept the first's `/Font` name out of the resources. Page
edits now read through the overlay, and the stamp builds its graph from
the page *as the session has it* (`page::build_graph`, the one builder for
both), so an earlier appended stream is a clean stream of the graph and the
names it uses are kept. `apply_page` is the one place a page edit becomes
objects.

**Tests.** `crates/pdfrum-edit/src/info.rs` (unit: entries set, removed,
a broken `/Info` replaced, dates), `crates/pdfrum-edit/tests/info.rs` (full
and incremental saves), `crates/pdfrum/tests/metadata.rs`, the writer half
of `crates/pdfrum/tests/attachments.rs`, `crates/pdfrum/tests/stamp.rs`
(every page, order, centre and corner placement by word boxes, angle,
opacity and colour, a rotated page, two stamps accumulating, an image's
aspect and opacity, a refused width, a reproducible save). API baseline
updated with each commit; the enum gate counts `StampPosition`'s five.

## Phase 5 — CLI

The verbs on the phase-5 fills, all in `crates/pdfrum-cli`, one commit
each, and nothing new below the facade. Every verb is a writer the way
`pages slice` is: `-o PATH` or `-o -`, `--deterministic`, a one-line
summary on stdout, and a method twin in the session that hands the file
back as `bytes_base64`. The facade lacked one thing, noted at the end.

**The verbs.**

| command | on | summary |
|---|---|---|
| `metadata set FILE [--title T] [--author A] [--subject S] [--keywords K] [--creator C] [--clear KEYS] -o OUT` | `Document::metadata` changed, `DocEdit::set_metadata` | `out.pdf: metadata set, 3 keys` (`, 2 cleared` when asked) |
| `pages delete FILE --pages RANGE -o OUT` | `DocEdit::delete_pages` | `out.pdf: 2 pages deleted, 9 left` |
| `pages rotate FILE [--pages RANGE] --by DEGREES -o OUT` | `Page::rotation`, `DocEdit::set_rotation` | `out.pdf: 3 pages rotated by 90` |
| `attach add FILE PATH… [--description D] [--mime TYPE] -o OUT` | `DocEdit::add_attachment` with `AttachmentOptions` | `out.pdf: 2 attachments added` |
| `attach remove FILE NAME… -o OUT` | `DocEdit::remove_attachment` | `out.pdf: 1 attachment removed` |
| `stamp text FILE TEXT [--position P] [--opacity O] [--angle A] [--size PT] [--rgb RRGGBB] [--font NAME] -o OUT` | `DocEdit::stamp_text` with `StampOptions` | `out.pdf: stamped 11 pages` |
| `stamp image FILE IMAGE [--width PT] [--position P] [--opacity O] [--angle A] -o OUT` | `DocEdit::embed_jpeg`/`embed_image`, `DocEdit::stamp_image` | `out.pdf: stamped 11 pages` |

**What was decided on the way.** `metadata set` reads the whole `/Info`
through `Document::metadata`, changes the keys named and writes the
value back, so a key not named is kept; `--clear` takes the names `info`
prints (`title`, `author`, `subject`, `keywords`, `creator`, `producer`,
`created`, `modified`), and an empty `--title ""` removes the key the
way the facade defines it. There is no `metadata show`: `info` prints
them. `pages rotate --by` is added to each page's own `/Rotate` (a page
at 90 turned by 90 stands at 180), takes 90, 180, 270 or -90 and refuses
0 — a turn of nothing is a mistake, not a no-op — and `slice` keeps its
absolute `--rotate` and `--crop`. `pages delete` refuses to delete every
page. `attach add` names each attachment after its file, guesses the
MIME type from the extension for pdf, png, jpg, txt, json, csv, xml and
zip and writes `application/octet-stream` for anything else, takes
`--mime` for a single file only, puts `--description` on every file
given, records the file's modification time as `/ModDate` unless the
save is reproducible (the time is not part of the bytes), and refuses a
name already attached rather than writing a name tree with two entries
of one key. `attach remove` refuses a name that is not there before
removing anything. The stamps take `--position` as clap's five words
(`center`, `top-left`, …), `--opacity` 0..1, `--angle` in degrees
counter-clockwise; the text stamp's colour is `--rgb RRGGBB` because
`--color WHEN` is the terminal's flag on every command, and `--font` is
one of the standard 14 by the name the specification gives it
(`Times-Roman`, `Helvetica-BoldOblique`, `ZapfDingbats`). `stamp image`
defaults `--width` to the picture's pixel width, one point a pixel, as
`pages create` does at 72 dpi. `pages create`'s image decoding became
`cmd::pages::decode_bytes` and `embed`, shared with the stamp. `slice`
and `nup` now parse `--crop`, `--grid` and `--sheet` themselves, so
`main`'s page dispatch stays under the line limit.

**Checks before work.** Every refusal happens before a file is opened or
any edit is made, with nothing written: the checks live apart from the
`*_bytes` functions — `metadata::apply`, `pages::deletion`,
`pages::parse_turn`, `stamp::options`, `stamp::checked_text`,
`stamp::checked_width` — so the session can run the same check and
answer `-32602` for a wrong request and `-32000` only when the work
failed. The one that stays `-32000` is `attach.remove` of a name the
document lacks, and `attach.add` of a name it already has: those are
facts about the document, not the request.

**The session.** Seven methods in `rpc::methods` — `metadata.set`,
`pages.delete`, `pages.rotate`, `attach.add` (`{name, bytes_base64,
description?, mime?}`, one file per call), `attach.remove` (`{names}`),
`stamp.text`, `stamp.image` (`{image_base64, width?}`) — each with the
command's flags as params and `{…, bytes_base64}` back, in the phase-4
table above and in `schema serve` and `tools/list` (`metadata_set`,
`pages_delete`, …). With `deterministic` the bytes are the very bytes
the command writes with `--deterministic -o -`, which the tests check
for `pages.rotate`, `metadata.set` and `pages.delete`.

**Tests.** `crates/pdfrum-cli/tests/verbs.rs`: every verb writes into a
scratch directory and is read back with our own commands — `info --json`
for the metadata and the rotations, `extract attachments --json -o DIR`
for the names, types, sizes and bytes, `extract text --json` and
`extract words --json` for the text stamp's presence, face, size and
placement, `extract images --json --all` for one picture drawn per page
— with the refusals and their messages, reproducible saves, and every
verb on `-o -`; and one oracle check per verb, skipped with a message
without `PDFRUM_ORACLE_CHECKOUT`: `pdfium_test --show-metadata` prints
every key we set, `--show-pageinfo` counts the pages left, `--png`
draws the turned page on its side (792 by 612 for a quarter-turned
letter page), `--save-attachments` writes the added file byte for byte
and not the removed one, `--txt` extracts the text stamp beside the
page's own text, and `--md5` renders the image-stamped page differently
from the plain one. `tests/serve.rs`: the seven methods run against
their schemas, the bytes compared with the command line, the refusals
with their codes, and the tool names. Unit tests in `cmd::metadata`,
`cmd::pages`, `cmd::attach` and `cmd::stamp` for the parsers.

**Gap.** `DocEdit::stamp_text` and `stamp_image` stamp every page and
take no page selection, so the stamps have no `--pages`; a facade fill
(a `pages` field on `StampOptions`, or a page-range parameter) would give
it to both the command and the method without a change here.

## Phase 3 — limits (library)

The two ceilings a host puts on untrusted input, both on `Limits`, both
off by default, both reached through `OpenOptions::limits` and nothing
else: `max_render_pixels: Option<u64>` and `deadline: Option<Deadline>`.
There is no per-render copy — `RenderOptions` says how a page is drawn,
the document's `Limits` says how much it may cost — so a server sets both
once at open and every later call on that document honours them. A
default `Limits` changes nothing: the board is byte-identical (below).

**The error.** `Error::Limit(LimitExceeded)`, a new facade variant whose
payload lives in `pdfrum-common` beside `Limits` with a hand-written
`Display`, so the crates that hit a ceiling answer with the same value:
`LimitExceeded::RenderPixels { width, height, allowed }`, `Time { budget,
during, page }` and `Stopped { during, page }`, with `Operation` naming
what was under way (`Open`, `PageLoad`, `Interpret`, `Render`, `Extract`,
`Script`). The messages say what would satisfy the cap: `render of 20000 x
20000 px (400 megapixels) is above the cap of 100 megapixels; render at a
smaller scale or raise `Limits::max_render_pixels``, `time limit of 5 s
exceeded while rendering page 3; allow more time or do less`, `stopped by
the caller while loading page 7`. The member crates' errors — `LoadError`,
the parser's `Error`, the render `Error` — each gained a `Limit` variant
for the same value, and the facade's `From` impls route all of them to
`Error::Limit`, so a caller matches one place. `Limits` is `Clone` and no
longer `Copy` (a `Deadline` shares a flag); every reader already took
`&Limits`, and the two owners clone once.

**The pixel cap** is the facade's alone, checked before anything is
allocated or decoded: in `Page::render_on` *before* `prepare`, because the
build decodes every image at the device size and that is the first
allocation a too-large request would make, and again in
`PreparedPage::render_on`, because `prepare` is infallible and a page
prepared above the cap is refused at the draw. The size is truncated
exactly as the engine's `target_size` truncates it, so the pixels counted
are the pixels the pixmap would have; a non-finite or empty axis is the
engine's `TargetEmpty` to report, not the cap's. PDFium has no equivalent
(`pdfium_test --scale` sizes the bitmap and only `CFX_DIBitmap`'s pitch
overflow refuses it).

**The deadline** is a cooperative stop, checked at the boundaries the
engine already has. `Deadline` is a flag any thread raises
(`Deadline::manual()`, `stop()`, clones share it) and, on targets with a
monotonic clock, a budget that raises it for you (`Deadline::after(d)`,
`Deadline::at(instant)`). **The flag is the mechanism and the clock the
convenience**, because `Instant::now()` aborts at runtime on
`wasm32-unknown-unknown` and the facade builds for that target: the two
clock constructors and the clock field do not exist there, so no `wasm32`
code path can read one, and a host there stops the work from its own
timer with `stop()`. `cargo check -p pdfrum --target wasm32-unknown-unknown
--no-default-features --features vello-cpu,codecs-all,forms,edit` passes
and is in the gate. Where each check sits:

- **Open** (`pdfrum-parser`): once on entry to `load`, then every 4096
  tokens of the cross-reference rebuild scan — the one long loop an open
  has. Fails with `LoadError::Limit` → `Error::Limit`.
- **Page load** (facade `Page::load`): once per page, before the
  dictionary is read — the per-page boundary a walk over a document
  crosses, and the fallible boundary text extraction has (see below).
  `Document::pages` ends there; `Document::page` says why.
- **Interpret** (`pdfrum-page` `interpret_streams`): every 256 operators,
  the first read before the first one. The interpreter cannot fail, so it
  stops where it is, returns the objects built so far and records the new
  `DiagKind::TimeLimitReached`.
- **Render** (`pdfrum-render`): the deadline rides the per-call
  `RenderSession` as a borrow and `RenderCtx` as a pointer — *not*
  `RenderOptions`, which every nested context clones (a first cut put it
  there and cost 0.66% in `memcpy` alone). Read once before the target is
  allocated, once per object in `render_object_list` (nested lists
  included, each returning at its next object so the walk unwinds without
  a flag), and once after the walk, which is what turns a half-drawn
  device into `Error::Limit` rather than a returned pixmap. The facade
  adds the page index to the message.
- **Extract** (`pdfrum-text`): once on entry to `extract` — a page is its
  unit of work — answering an empty page and `TimeLimitReached`, since
  `Page::text` cannot fail. The `limits` parameter, previously unread,
  now has a reader.
- **Script** (`pdfrum-form`): before each run, beside `boa`'s loop budget:
  a script that starts past the deadline is refused as one that ran out
  (`ScriptStop::LimitReached`, `DiagKind::ScriptLimitReached`). `boa` has
  no wall-clock hook, so the budget bounds *inside* a run and the deadline
  *between* runs.

**Cost, measured.** `profile --op render --file
benches/corpus/vector_en_tem.pdf --iterations 5 --backend agg` under
`valgrind --tool=callgrind`, the default path (no deadline, no cap):
before 1,132,732,314 Ir (a repeat: 1,133,049,910, so run noise is 0.03%);
after 1,138,188,884 Ir, +0.48%. That is above the 0.1% asked for, and it
is not the checks: per function, the interpreter loop's own delta is
+24k Ir (0.002%) and every other engine function is unchanged; the whole
difference is `__memcpy` called from `_int_realloc`, which runs exactly
30,951 times in both builds, and all of it in `pdfrum-filters`' 170
decoded-stream buffer growths (12.8M → 18.0M Ir), a crate this phase does
not touch. `ObjectStore` lives in an `Arc` and carries `Limits` inline,
so a larger `Limits` shifts the heap and more of those large buffers move
instead of growing in place. The control: the untouched baseline with
only a 56-byte pad on `Limits` — the bytes the two fields add — measures
1,139,785,885 Ir, +0.62%, more than the real change. The number is heap
layout, and any field on `Limits` would pay it.

**Tests.** `crates/pdfrum-common` (the `Deadline` states, equality as
sharing a flag, the messages, `check_deadline` on a default `Limits`),
`crates/pdfrum-parser/src/xref/rebuild.rs` (a spent deadline stops the
scan at its stride; no deadline scans through), `crates/pdfrum-page/src/
build.rs` (a spent deadline builds nothing and says so; a generous one
builds everything), `crates/pdfrum-render/tests/engine.rs` (a spent
session deadline fails before the target exists; a generous one draws the
same bytes), `crates/pdfrum-form/src/script/tests.rs` (a spent deadline
refuses a script as a limit), and `crates/pdfrum/tests/limits.rs` — the
pixel cap (400 megapixels against 100 refused in no time with size, cap
and message; the prepared path refused at the draw; at the cap passes,
one below fails; the default caps nothing) and the deadline on the corpus
guide (a spent one refuses the open; an hour changes nothing, pixel for
pixel; one that passes after the open fails the render naming page 0,
empties the text with the diagnostic on `all_diagnostics`, refuses the
next page and ends `pages()`; a manual stop does the same by hand and
from another thread). API baseline updated with each commit; the enum
gate counts 317.

**Board.** 1759 files, 1537 pass, 222 fail, 0 rows changed against the
reference run (`board-m20e.json`); the two `util_printd`/`util_scand`
rows the runner flags against the committed scoreboard fail in the
reference run too and predate this phase.

**The CLI owner's next step:** `--max-pixels` on `render` and

`Limits { max_render_pixels: Some(n), ..}` and `Limits { deadline:
Some(Deadline::after(d)), ..}` through `OpenOptions::limits`, the
`Error::Limit` message as the reason.
