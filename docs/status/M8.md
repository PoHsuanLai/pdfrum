# M8 — API & release polish

**Updated:** 2026-08-29 · **State:** benchmarks landed, publishability audited.

Covers the M8 exit criteria that are about *shipping* rather than about
behaviour: cache reuse on the public API, a document-wide diagnostics view,
criterion benchmarks against the oracle's own timings, and what stands between
this workspace and a crates.io release.

The other M8 items — facade API review, rustdoc and examples — landed with the
facade itself; see `docs/status/pdfrum-facade.md`.

---

## 1. Cache reuse across pages: `RenderSession`

`pdfrum-render`'s `render_page` allocated a fresh `RenderCaches` per call, so
*glyph outlines were re-flattened for every page* even when a caller was
already threading a `BuildContext` through the fonts and images. There was no
public way to avoid it: no `render_page_with_caches`, and `target_size` was
private, so reusing the cache meant reimplementing the entry point on top of
`render_object_list`.

Three additive changes, no behaviour change to the existing entry point:

- **`pdfrum_render::render_page_with_caches`** — `render_page` plus a
  `&mut RenderCaches`. `render_page` now delegates to it with a fresh set, so
  every existing caller renders exactly the pixels it did before.
- **`pdfrum_render::target_size`** made public, so a caller can size a buffer
  or reject an oversized page without paying for a render to find out.
- **`pdfrum::RenderSession`** — the facade-level handle, a plain record of the
  two caches that belong to different crates and do not know about each other:
  `BuildContext` (fonts, colour spaces, functions, images) and `RenderCaches`
  (flattened glyph outlines). Reached through `Page::render_session` and
  `Page::text_session`.

No globals and no shared mutable state (STYLE.md §1): the session is owned by
the caller and reached through `&mut`, exactly as `BuildContext` already was,
so the rayon story is unchanged — `map_init(RenderSession::new, …)` gives each
worker its own.

**The caveat is documented rather than papered over.** Type-3 glyph snapping is
order-dependent by design, so a page drawn with a warm cache can differ by a
snapped pixel from the same page drawn cold. `render_page` — fresh caches per
page — remains the byte-identical baseline, and the conformance harness keeps
using it. This is stated on both `render_page_with_caches` and `RenderSession`.

### What it buys

Measured, not asserted (full table in §3):

| Fixture | Pages | Per-page caches | One session | Speed-up |
|---|---:|---:|---:|---:|
| `cropped_text` | 4 | 5.57 ms | 1.81 ms | **3.08x** |
| `bookmarks` | 2 | 8.90 ms | 4.14 ms | **2.15x** |
| `many_rectangles` | 1 | 2.59 ms | 2.42 ms | 1.07x |
| `bug_650` | 1 | 74.30 ms | 70.79 ms | 1.05x |
| `latin_extended` | 1 | 8.07 ms | 8.36 ms | 0.97x |
| `embedded_images` | 1 | 5.22 ms | 5.91 ms | 0.88x |

The shape is the honest one: **the win is per-document, and single-page
documents have nothing to reuse.** The four one-page fixtures sit between 0.88x
and 1.07x — that is, no effect, with two of them landing on the *slow* side of
1.0. Nothing is being reused there (a session's caches are populated by the
first page and there is no second page to spend them on), so the spread is
measurement noise on a shared machine and is reported rather than rounded to
"no change". Two pages sharing a font is where this pays; four pages more so.

## 2. Document-wide diagnostics: `Document::all_diagnostics`

`Document::diagnostics()` answered "what did opening this file repair" and was
documented as if it answered "what did this document need repaired". It could
not: PDF is read lazily by design, so a stream with a bad `/Length` on page 400
is repaired hundreds of calls after `open` returned, and that repair went into
whatever short-lived sink the call had created to satisfy the signatures below
it — then dropped on return.

There turned out to be **three** sinks, not one:

1. **Load-time** — `pdfrum_parser::Document::diags`, a snapshot fixed at open.
2. **The object store** — `ObjectStore` already carried
   `diags: Mutex<Diagnostics>` and already recorded every lazy object fetch
   into it. It was drained *exactly once*, inside `load`, before the
   `Document` was constructed. Everything after that accumulated there and was
   unreachable.
3. **This crate's own reads** — page building, text extraction, appearance
   generation, attachment decoding: twelve call sites each constructing a
   `Diagnostics` and discarding it.

The design, without breaking the no-global-state rule:

- **`pdfrum_parser::Document::lazy_diagnostics()`** — a *snapshot* of the
  store's running total, backed by a new `ObjectStore::peek_diags`. It
  deliberately does not drain: a caller must be able to ask twice between two
  fetches and get the same answer, which `drain_diags` would break.
- **`pdfrum::Document`** grows a `session: Mutex<Diagnostics>` and a
  `pub(crate) note()`, and every one of the twelve discarding call sites now
  folds its sink into it. A `Mutex` and not a `RefCell` because `Document` is
  what a rayon `par_iter` shares; it is locked only to append a few entries,
  never held across a parse, and a poisoned lock drops the entries rather than
  panicking (STYLE.md §3).
- **`pdfrum::Document::all_diagnostics()`** returns an owned snapshot of all
  three, as a running total.

`diagnostics()` is unchanged and still returns the load-time `&Diagnostics`.
Keeping them separate is deliberate: an existing caller's answer must not start
moving under it, and "what was wrong with the file as it arrived" is a
different question from "what has this document needed so far".

**No member-crate signature changed**, so no `[spec]` protocol was required.
The two additions (`lazy_diagnostics`, `peek_diags`) are new methods, and the
one new `pdfrum-common` method — `Diagnostics::extend`, folding one sink into
another — replaces a loop that was open-coded at all three existing merge
sites.

### It reports things that were previously invisible

Pinned by tests rather than claimed:

| Fixture | `diagnostics()` after open | `all_diagnostics()` after a render |
|---|---|---|
| `hello_world.pdf` | *empty* | `KeywordResync` @ 533 — the content stream that omits its `/Length`, found when the stream is first read |
| `text_form.pdf` | *empty* | `AppearanceGenerated` — the widget appearance this crate's own render path asks for |

Both were being recorded and then dropped before this change.

## 3. Benchmarks

A new `benches/` crate (`pdfrum-bench`, `publish = false`, criterion — already
sanctioned by DEPS.md as bench-only and in no library crate's tree). Four
groups over six fixtures: `open`, `render`, `render-session`, `text`.
`scripts/bench-oracle.sh` times `pdfium_test` over the same files.

Fixtures are copied unmodified from the oracle checkout with provenance in
`benches/fixtures/PROVENANCE.md`, chosen to *separate* costs rather than
average them: text-dominated, path-dominated, image-dominated, one whose
cross-reference table is deliberately invalid, and two multi-page.

**criterion is pinned to 0.5.1, not the current 0.8.2, and the reason is the
pure-Rust guarantee.** From 0.6 onward criterion depends unconditionally on
`alloca`, which carries a `cc` build-dependency and compiles C. DEPS.md's
guarantee is enforced rather than promised — `cargo-deny` bans `cc` outright
and `scripts/ci.sh` walks the whole workspace — so 0.8 makes the gate fail on
its first run. There is no feature flag that avoids it: `alloca` is not
optional. 0.5.1 predates that dependency, is pure Rust, and nothing here uses a
newer API. Worth knowing before anyone "updates the benchmark dependency".

**Environment.** AMD Ryzen 9 7950X (16C/32T), Linux 6.8, rustc 1.97.1, release
profile (opt-level 3, no LTO), single-threaded. Oracle: `pdfium_test` from the
checkout at `6f2272e`, `is_debug = false`, AGG rasterizer. Both render at one
pixel per PDF point with no scaling.

### How the oracle side is measured, and why it is not a criterion run

`pdfium_test` has no criterion. It has `--render-repeats=<n>`, which renders
the document n times inside one process. The script times each file at n=40 and
at n=1 and reports `(t40 - t1) / 39` — the marginal cost of one more render
pass over the whole document, which is the same quantity criterion's
per-iteration time reports, with the process start, the font-database build and
the file read differenced away rather than counted. Each measurement is the
**minimum** of five runs: a wall-clock sample is bounded below by the real cost
and unbounded above by whatever else the machine was doing.

### The table

Whole-document times. Lower is better; the ratio is pdfrum ÷ oracle, so **>1 is
pdfrum being slower**.

| Fixture | Pages | Oracle render | pdfrum `render` | pdfrum `render-session` | Ratio (session) |
|---|---:|---:|---:|---:|---:|
| `many_rectangles` | 1 | 22.01 ms | 2.59 ms | 2.42 ms | **0.11x** — we are 9.1x *faster* |
| `bookmarks` | 2 | 1.29 ms | 8.90 ms | 4.14 ms | 3.2x slower |
| `bug_650` | 1 | 19.26 ms | 74.30 ms | 70.79 ms | 3.7x slower |
| `embedded_images` | 1 | 1.38 ms | 5.22 ms | 5.91 ms | 4.3x slower |
| `latin_extended` | 1 | 1.68 ms | 8.07 ms | 8.36 ms | 5.0x slower |
| `cropped_text` | 4 | 0.06 ms | 5.57 ms | 1.81 ms | *not reportable — see below* |

pdfrum-only columns, for which the oracle offers no comparable number:

| Fixture | `open` | `text` |
|---|---:|---:|
| `bookmarks` | 3.6 µs | 0.83 ms |
| `bug_650` | 6.6 µs | 6.29 ms |
| `cropped_text` | 2.7 µs | 5.01 ms |
| `embedded_images` | 46.4 µs | 1.58 ms |
| `latin_extended` | 3.2 µs | 0.81 ms |

alone. `embedded_images` costing 13x the other files to open is the

### Where we are slower, and why we think so

**We are slower at drawing text, by roughly 3–5x, and faster at filling paths,
by about 9x.** That is the whole result; the rest is which fixture leans which
way.

This is measured rather than guessed. Splitting a render into content
interpretation and rasterization:

| Fixture | Build (parse + interpret) | Raster | Raster share |
|---|---:|---:|---:|
| `latin_extended` | 0.36 ms | 13.61 ms | 97% |
| `bug_650` | 11.09 ms | 60.44 ms | 84% |
| `many_rectangles` | 0.39 ms | 2.05 ms | 84% |

So the gap is not in the parser, the object store or the content interpreter —
`open` is microseconds against the oracle's milliseconds, and interpretation is
3% of a text page's cost. It is in **glyph rasterization**, and two further
measurements narrow it:

- Both backends land in the same place on `bug_650` (`vello_cpu` 71.5 ms,
  `tiny-skia` 62.6 ms) while differing 2.8x on `latin_extended` (14.0 ms vs
  38.5 ms). A cost that survives swapping the rasterizer is upstream of it.
- Pre-warming the glyph cache and re-rendering the *same* page recovers only
  ~8%, so it is not outline lookup or flattening. The outlines are already
  cached; what costs is submitting each glyph as an independent filled path,
  every time it occurs.

The working hypothesis, stated as a hypothesis: PDFium rasterizes text through
a dedicated glyph path — FreeType-rendered glyph *bitmaps* cached per
(face, size, subpixel offset) and then blitted — whereas pdfrum hands every
glyph to the general path rasterizer as an outline to fill, per occurrence.
That trades a blit for a fill per glyph, which is the right order of magnitude
for a 3–5x gap on text-heavy pages and predicts both observations above.
`many_rectangles` is the control: no text at all, and there the general path
rasterizer — `vello_cpu`'s sparse-strip design doing what it is good at — beats
AGG by 9.1x. The engine above the rasterizer is not the problem; text is.

A glyph-bitmap cache in `pdfrum-render` is therefore the obvious next
optimization, and it is deliberately **not** attempted here: it interacts with
the type-3 snapping determinism noted in §1 and with the conformance SSIM
ratchet, so it wants its own design pass rather than being smuggled into a
polish commit.

### 2026-08-29 — burn-down wave 7b built it, and the hypothesis was two-thirds right

`docs/status/pdfrum-render.md`'s wave 7b section has the pipeline; this is what
it did to these numbers, and where the hypothesis above needed correcting.

**Right:** the oracle does cache FreeType glyph bitmaps and blit them, the cost
here really was per-occurrence rasterization, and caching the bitmap is worth
**1.5–3.5x on a real text page** — measured whole-document through
`Page::render_session`, best of five runs of twenty iterations:

| page | glyphs / distinct | `tiny-skia` | `exact` | `vello_cpu` |
|---|---|---:|---:|---:|
| `corpus/fx/other/foxittext.pdf` | 2891 / 82 | **2.08x** | **1.85x** | 1.34x |
| `corpus/fx/text/ch_9_android.pdf` | — | **3.51x** | **1.84x** | 1.40x |
| `corpus/third_party/tcpdf/example_063.pdf` | 24942 / 569 | **1.73x** | **1.47x** | 1.06x |
| `benches/fixtures/latin_extended.pdf` | 256 / 256 | 1.06x | — | 0.99x |

The last row is the control and belongs in the table: a page with **no glyph
reuse at all** neither gains nor loses, which is what says the gain above is
the cache and not the raster being cheaper.

**Wrong in two ways, and both were only visible once it was built.**

- **A blit is not automatically cheaper than a fill.** The bitmap reaches the
  device through `draw_image`, and `pdfrum-raster-exact`'s general image path —
  an inverse transform and two floors per pixel, plus an antialiased
  rasterization of the footprint — cost *more* per glyph (2.56 µs) than filling
  the outline it replaced (2.20 µs). The gain only appears once `draw_image`
  recognises a whole-pixel translation and takes a real blit, which it now does
  for every image, not only for glyphs.
- **`vello_cpu` cannot benefit, structurally.** It is a *retained-scene*
  rasterizer: the device accumulates commands and rasterizes at `finish`, so
  there is no pixel buffer to blit into and every glyph is a scene command
  either way. The facade's default therefore gains about 1.1x where the two
  immediate-mode backends gain 1.4–3.7x, and that is a property of the
  rasterizer rather than something left undone.

**And the fixture set could not see any of it.** Five of the six fixtures draw
a few hundred glyphs; `latin_extended`, the one the table above calls "the text
fixture", draws **256 glyphs of which 256 are distinct** — a 0% cache hit rate,
the worst case a glyph cache has. Measuring a cache on it measures the miss
path. `foxittext.pdf` is added for that reason and the numbers above are why;
`latin_extended` is kept, now labelled as the worst case it is.

### What these numbers are not

- **The fixtures are small.** PDFium's `testing/resources` are unit-test
  inputs: the largest is 85 KB, and only two files exceed two pages. Nothing
  here resembles a 300-page report and these numbers should not be
  extrapolated to one. The larger `testing/corpus` is not part of the checkout.
- **`cropped_text`'s ratio is not reportable.** The oracle renders it in ~0.06
  ms — below the resolution of a differenced wall-clock measurement, and the
  runs behind that figure ranged from 0.055 ms to 0.53 ms, one of them
  negative. The pdfrum column for it is sound; the ratio is not, and is left
  out rather than printed as a headline "33x". Its four pages are almost
  entirely clipped away, so there is very little for either engine to draw.
- **The machine was shared.** An earlier run of the identical benchmark, taken
  while another build was running on the same box, produced pdfrum numbers
  roughly 2x higher across the board while leaving every *ratio* between
  fixtures intact. The numbers above are the quiet run. Absolute milliseconds
  here are worth less than the shape they make.
- **Single-threaded throughout.** pdfrum's rayon path and `vello_cpu`'s
  internal multithreading are both off. A parallel comparison is a different
  measurement and is not made here.
- **No tuning was done for these numbers.** Nothing was reordered, no
  fast-paths added, no fixture chosen after seeing its result. `many_rectangles`
  is in the set because it isolates path filling, and it happens to be the one
  we win.

### Reproducing

```
cargo bench -p pdfrum-bench                 # criterion, from benches/
scripts/bench-oracle.sh [pdfium_test] [n] [rounds]
```

## 4. Publishability audit

### Fixed

- **Every publishable crate now has a standalone `README.md`** (17 of them),
  each leading with what the crate is on its own terms rather than as a piece
  of pdfrum — the independence story, since `pdfrum-type1`, `pdfrum-filters`,
  `pdfrum-crypt` and `pdfrum-cmap` are all useful without the rest. `readme =
  "README.md"` declared in each manifest; previously the packaged manifests
  said `readme = false` and the crates.io pages would have been blank below the
  metadata box.
- **`keywords` and `categories` on every publishable crate** — there were none
  anywhere. Category slugs validated against the crates.io API, including the
  `multimedia::images` subcategory.
- **Licence files now ship.** `LICENSE-MIT` and `LICENSE-APACHE` existed only
  at the workspace root, and `cargo publish` does not reach parent directories
  — so no crate's tarball contained a licence despite `license = "MIT OR
  Apache-2.0"`, and `pdfrum-cmap`/`pdfrum-font` even listed `LICENSE*` in
  `include` matching nothing. Both files are symlinked into each crate; cargo
  follows the symlinks and packages the contents (verified in the tarball).
- **`pdfrum-text` gained an `include`**, matching its siblings. It ships a
  `tables/unicode.bin` that `include_bytes!` needs, but was also shipping
  `tests/` and the 24 KB ICU property dump the blob is *generated from* — build
  script input, not library input.
- **`crates/pdfrum-tool/input.pdf.0.txt`** — a tracked stray dump artifact that
  would have shipped in the tarball — removed and the pattern gitignored.

### Verified

`cargo publish --dry-run -p pdfrum-common` **passes** end to end: packaged 10
files, 45.6 KiB, and the tarball contains `README.md`, both licence files, and
a manifest carrying description, keywords, categories, licence and repository.
It is the only crate that *can* fully dry-run today, because it is the only one
whose dependencies are all already on crates.io.

Metadata completeness across the workspace, from `cargo metadata` — all 17
publishable crates: description ✓, keywords ✓ (3–5 each), categories ✓ (2–4
each), licence ✓, repository ✓, README present on disk ✓. `conformance` and
`pdfrum-bench` correctly carry `publish = false`; the fuzz ring is a separate
workspace.

### What remains before a real publish

**The version-locked family release process.** The remaining four leaf crates
(`pdfrum-object`, `pdfrum-filters`, `pdfrum-crypt`, `pdfrum-cmap`,
`pdfrum-type1`) fail `--dry-run` today for exactly one reason, confirmed
individually: `no matching package named 'pdfrum-common' found` — the
dependency is not on crates.io yet. This is not a defect to fix. It is the
normal bootstrap of a family of crates that has never been published, and it
resolves only by publishing bottom-up.

The internal dependency declarations are already in the correct form for this:
every one is `{ path = "…", version = "=0.1.0" }`, so cargo rewrites them to
registry dependencies on publish. Verified negatively too — stripping the
version and packaging fails with *"all dependencies must have a version
requirement specified when packaging"*, which is the error the current form
exists to avoid.

What a release therefore needs:

1. **Publish in dependency order**, which is already the `members` order in the
   root `Cargo.toml`: `pdfrum-common`, `pdfrum-object`, `pdfrum-crypt`,
   `pdfrum-filters`, `pdfrum-cmap`, `pdfrum-type1`, `pdfrum-font`,
   `pdfrum-parser`, `pdfrum-page`, `pdfrum-render`, `pdfrum-raster-vello`,
   `pdfrum-raster-tinyskia`, `pdfrum-text`, `pdfrum-doc`, `pdfrum-edit`,
   `pdfrum`, `pdfrum-tool`. Each publish waits for the index to carry the
   previous one.
2. **`--no-verify` on the first round only, or accept the dev-dependency
   back-edges.** Five crates have a dev-dependency on a crate that depends on
   *them* — `pdfrum-object ⇢ pdfrum-parser` is the tightest, and
   `pdfrum-render ⇢ pdfrum-raster-{vello,tinyskia}` the same shape. These are
   not real cycles (cargo drops dev-dependencies from a published tarball's
   resolution) but the *verification* build of the first publish cannot find
   them. Either skip verification for the bootstrap round or drop the back-edges.
3. **`=0.1.0` pins make every release a whole-family release.** An exact pin
   means publishing a patch of `pdfrum-common` alone leaves every other crate
   unbuildable against it. That is a deliberate trade — it guarantees the
   family is version-consistent and that a user cannot assemble a mismatched
   set — but it means the release unit is the workspace, and the process above
   runs in full every time. Relaxing to caret requirements before 1.0 is a
   decision worth taking explicitly rather than by drift.
4. **MSRV is still undeclared.** No crate carries `rust-version`. The workspace
   is on edition 2024 and builds on 1.97.1; the floor has not been established
   and no CI job tests it.
5. **`repository` points at `https://github.com/pdfrum/pdfrum`**, which is a
   placeholder — it must exist and be public before the first publish, since
   crates.io links it and docs.rs builds from the tarball.

### Noted and deliberately not changed

- `pdfrum-tool` publishes a binary named `pdfrum-tool`. A user typing
  `cargo install pdfrum-tool` might expect a `pdfrum` binary; adding a
  `[[bin]] name = "pdfrum"` is a naming decision, not a packaging fix, and is
  left to the user.
- `crates/pdfrum-page/src/build.rs` was flagged during the audit as a build
  script in the wrong directory. It is not — it is the page-builder module,
  declared `mod build;` in `lib.rs`. No change needed.

## Gate

`fmt`, `clippy --workspace --all-targets -D warnings`, `cargo nextest run`
(**2640** tests, up from 2632), `cargo test --doc` (**149**, up from 143),
`cargo deny check` (advisories, bans, licences, sources all ok), pure-Rust tree
check — `scripts/ci.sh` **green**.

The benchmark crate is a workspace member, so clippy and the formatter cover
it. `cargo bench` is deliberately *not* in the gate: it is minutes where the
gate is seconds, and a benchmark that fails a threshold is a conversation
rather than a build break.

**One correction to a previous claim.** `docs/status/pdfrum-facade.md` recorded
`cargo doc --no-deps` as warning-free. It is not: the workspace emits 34
rustdoc warnings — redundant explicit link targets, and public docs linking to
private items — spread across `pdfrum-type1`, `pdfrum-cmap`, `pdfrum-filters`,
`pdfrum-font` and others. The count is **identical before and after this work**
(verified by stashing), so none of them are new here, and none are in the
facade. They went unnoticed because `cargo doc` is not in `scripts/ci.sh`.
Fixing them and adding the check to the gate is unclaimed work; the facade
status doc has been corrected rather than left overstating.
