PLAN.md §M12 sets the shape: baseline first, then measured hotspots one at a
time, conformance as the regression gate. DEPS.md's **Performance ring** sets
the admission rule for any dependency: it lands only beside a committed A/B
against a *tuned no-dep baseline*, and stays only if it clears 10% on a bench

The short version of what follows: **no perf dependency has earned its way in
yet**, one of the two pre-approved ones was implemented dependency-free and
measured at zero, and the largest single cost in the corpus turned out to be
something no loop tuning can reach — a cache, which §9.1 built for **-90% on
five image documents** with a byte-identical conformance scoreboard. Peak RSS
comes out at a geometric mean of **1.20x** the oracle against a ≤1.5x target,
with the five exceptions named and explained rather than averaged away.

## 0. Environment, and what these numbers are worth

AMD Ryzen 9 7950X (16 cores / 32 threads), Linux 6.8.0-138, rustc 1.97.1,
release profile (`opt-level = 3`, no LTO, `debug = 1` — see §6). Oracle:
`pdfium_test` from the checkout at `6f2272e`, `is_debug = false`, AGG
rasterizer. Both render at one pixel per PDF point with no scaling.

**The machine is shared.** Run-to-run spread on an identical binary was measured
at up to 5% on the heavier documents (§2's noise band), and every conclusion
below is drawn against that number rather than around it. Where a change came
in under the band it is reported as *no effect*, not rounded up.

## 1. P0 — the baseline

### 1.1 The corpus: 44 files, six classes

`benches/corpus/`, with `benches/corpus/PROVENANCE.md` recording where each
file came from, unmodified, and why it is in the set. It replaces the seven
files in `benches/fixtures/` as the measurement set — those are kept because
`docs/status/M8.md`'s tables measured them and deleting them would strand those
numbers.

The M8 set's stated weakness was that it was made of unit-test inputs: *"the
largest is 85 KB, and only two files exceed two pages."* The new set is chosen
against that, by measurement rather than by name. Every PDF in both of the
oracle's directories — 1375 files — was scanned for **decompressed operator
counts** (`Tj`/`TJ`, path operators, `sh`, `Do`) and then actually rasterized;
selection is on what a file costs and which operator dominates it.

Two findings from that scan are worth recording because they contradict the
obvious heuristic, and because acting on the heuristic would have produced a
worse corpus:

- **File size is nearly uncorrelated with render cost.**
  `FRC_8.5_Screen_Rendition.pdf` is 25 MB and renders in 90 ms — the bulk is an
  embedded video attachment. `bug_718762.pdf` is **1 KB and renders in 1.2
  seconds**: a small JPEG header declaring a 5000x5000 image. "Pick the big
  files" would have produced a corpus slow to clone and fast to render.
- **Nothing in the checkout has more than sixteen pages.** The rayon scaling
  curve in §4 is bounded by that and says so rather than extrapolating to the
  300-page report nobody has.

| Class | Files | What it isolates |
|---|---:|---|
| `text` | 9 | Glyph-dominated pages, including three CJK |
| `vector` | 6 | Path-dominated; `vector_paths_1751` is the only genuinely pure one in 1375 files |
| `image` | 9 | Decode and resample, spread across JPEG / JPX / JBIG2 / CCITT |
| `shading` | 8 | Every shading type with a distinct evaluator, mesh types included |
| `forms` | 7 | The widget-appearance path, a different code path from page content |
| `mixed` | 5 | No dominant cost; the two sixteen-page documents live here |

Nine documents have eight pages or more, which is what `corpus::multipage()`
selects for the scaling measurement.

### 1.2 The benches

`benches/benches/engine.rs`, six criterion groups over all 44 documents, every
id spelt `<class>/<stem>` so the ratchet can aggregate by class without a second
table mapping one to the other:

`open`, `render-exact`, `render-tinyskia`, `render-vello`, `text`, `save`.

The three render backends are **separate groups, not one parameterised group**,
because they are not three implementations of one number: `vello_cpu` is a
retained-scene rasterizer that does its work in `finish` where the two
immediate-mode backends do theirs per primitive. Averaging them would let an
improvement in one hide a regression in another.

### 1.3 The ratchet

`benches/baseline.json` plus `benches/src/bin/ratchet.rs` — the performance
half of what `conformance/scoreboard.json` is for correctness.

```
cargo bench -p pdfrum-bench
cargo run --release -p pdfrum-bench --bin ratchet -- check    # fails on a regression
cargo run --release -p pdfrum-bench --bin ratchet -- update   # records improvements
```

The rule: slower than the committed median by more than the group's noise band
is a regression and exits non-zero; faster by more than the band is an
improvement and `update` writes it in; **inside the band nothing happens and the
baseline keeps its old number** — a baseline that absorbed every in-band sample
would ratchet itself downward one noise-width at a time and eventually fail on a
machine behaving perfectly.

A benchmark in the baseline but absent from the run is reported as *not run*
rather than passing, so a filtered `cargo bench` cannot look like a clean sweep.

The statistic is criterion's **median**, not the mean and not its `slope`. A
wall-clock sample is bounded below by the real cost and unbounded above by
whatever else the machine was doing, so a contended run inflates the mean
permanently and leaves the median alone; `slope` is better still for benchmarks
whose iteration count varies but is absent for the ones criterion measures in
flat mode, and a ratchet that changes statistic per benchmark cannot be compared
across a corpus.

`estimates.json` and `baseline.json` are both hand-parsed rather than read
through a JSON crate, for the reason `conformance/src/json.rs` gives about the
scoreboard: this file is the project's performance fitness function and its
numbers must not shift under a dependency update.

### 1.4 The profiling harness

`scripts/profile.sh <op> <file> [iterations] [backend]`, over
`benches/src/bin/profile.rs` — one operation in a loop with nothing else in the
process. Not `cargo bench`: criterion interleaves its own statistics between
iterations, so a profile taken over it attributes cost to criterion's
bookkeeping as well as to the engine.

**`perf` was not available on this machine and the harness says so rather than
failing.** `perf` is installed but `kernel.perf_event_paranoid = 4`, and the
session had no way to lower it; `perf record` refuses outright. The script
checks both the binary and the sysctl, prints the exact remedy
(`sudo sysctl kernel.perf_event_paranoid=1`), and falls back.

The fallback is **instrumentation, not sampling**, and that choice is the
interesting part. A backtrace sampler needs either `unsafe` (forbidden
workspace-wide) or an unwinder crate (DEPS.md is closed), and a sampler that can
only report elapsed time tells you nothing. So `--sample` wraps the chosen
`RasterBackend` in a decorator that clocks every `RenderDevice` call, which
splits a render exactly at the seam the P1 questions are about:

- **raster** — the sum of the device calls: scanline integration, span blitting,
  compositing, image sampling;
- **engine** — everything else: content interpretation, the page-graph walk,
  glyph outline lookup and flattening, colour conversion.

It is exact rather than statistical. Its limitations are two and both are real:
an `Instant::now()` pair around a call costing a microsecond is a few percent of
that call, and the decorator's own cost lands in the engine half. Neither moves
a conclusion that a 20% difference rests on. One further caveat found the hard
way: the decorated path renders `Page::objects()`, which is page content
*without* annotation overlays — so the `forms` class is not measurable this way
and its numbers below come from whole-document timings instead.

### 1.5 The oracle side-by-side

`scripts/bench-oracle.sh [pdfium_test] [repeats] [rounds] [dir]`, unchanged in
method from M8 and now defaulting to `benches/corpus`. It times each file at
`n=40` and at `n=1` and reports `(t40 - t1) / 39` — the marginal cost of one
more render pass, with process start, font-database build and file read
differenced away rather than counted. Each measurement is the minimum of five
runs.

### Read the `image` row against §9.1 before drawing a conclusion from it

**The `image` class's 9.38x is our cold path against the oracle's warm one, and
it is a benchmark defect rather than an engine result.** §9.1 measured the
rendered-image cache at -90% on exactly these documents. This table does not
show that, and the reason is structural:

- The cache lives in `RenderCaches`, which is **per page** — deliberately, and
  matching `CPDF_PageImageCache`'s own lifetime.
- Every heavy image document in the corpus is **one page**.
- Each criterion iteration builds a **fresh `RenderSession`**.

So the cache is cold on every iteration and never sees the second render that
would hit it. Measured both ways on the same binary and backend:

| Document | criterion (fresh session per iteration) | one shared `RenderCaches` |
|---|---:|---:|
| `image_bug_718762` | 1205.9 ms | **84.6 ms** |

Fourteen times. Meanwhile `pdfium_test --render-repeats` — the other column of
every ratio here — renders the same document repeatedly *in one process*, so the
oracle's caches are warm for every timed pass by construction.

That makes the `image` ratios, and to a lesser degree `forms`, a comparison
between two different questions. It is not that the oracle is being flattered;
it is that we are measuring our worst case against their best one and calling
the quotient a speed ratio.

**What the honest summary is, then.** The geomean of **3.58x** stands as the
answer to *"what does a caller who renders one page of a document, once, pay
relative to the oracle?"* — a real question, and the answer is: 3.58x, with
`shading` at 1.09x and `vector_paths_1751` at 0.46x on the winning end. It is
**not** the answer to *"how fast is the engine"*, and the next revision of this
suite should measure both: keep the cold group, and add a warm one that holds a
session across iterations the way the oracle holds its own. Until that exists,
no conclusion about the image class should be drawn from this table that §9.1
does not already support better.

### What the table does say, cleanly

- **`shading` is 0.60x by total and 1.09x by geomean — we are faster over the
  class**, and `shading_tensor` is 0.27x. Neither is cache-sensitive: these are
  rasterizer numbers, and they are where the analytic backend and `vello_cpu`'s
  sparse-strip design earn their place against AGG.
- **`vector_paths_1751` is 0.46x** — the one genuinely path-pure file in 1375
  — which is M8's "9x faster at paths" finding surviving a bigger corpus at a
  more modest and more believable size.
- **`text` at 2.42x geomean** is cache-insensitive in the same way (the glyph
  caches *are* warm within a page) and is a real result: M8 measured 3–5x on
  its own fixtures, and §3.2's -33% is part of the difference.
- **`vector` improved from 4.50x to 3.37x** between the pre-P2 baseline and this
  one, which is the `object_bbox` allocation fix in `8c51d4d` showing up where
  it should.

**§1.7 is superseded as the M12 verdict by §1.10.** It is kept because it is the
measurement that produced the question, and because the cold column in §1.10 is
its direct successor — the same quantity, re-taken after the split and the two
fixes. What changed is not the number but which number the target is judged on;
§1.8 is that ruling.


### 1.8 The convention: cold and warm, and which one the target is on

§1.7's own closing paragraph asked for this, and the orchestrator's ruling
settles it. Restated as plainly as it can be:

**The committed baseline measured cold renders against a warm oracle.** Each
criterion iteration built a fresh `RenderSession` — so the glyph cache was cold,
and the rendered-image cache §9.1 built was empty — while `pdfium_test
--render-repeats` renders the same document repeatedly *in one process*, with
`CPDF_PageImageCache` enabled by default (§9.3). Every ratio in §1.7 is
therefore our worst case over their best one. That is a defensible quantity to
publish, and an indefensible one to judge "geomean >= oracle" with.

The suite now measures **both**, as two named conventions:

| Convention | What the closure holds | The question it answers | Oracle target |
|---|---|---|---|
| **`render-cold`** | a fresh `RenderSession` *inside* `b.iter()` | First-render latency: open a document, draw one page, exit. | none — ratcheted only |
| **`render-warm`** | one `RenderSession` hoisted *outside*, primed by one untimed render | Steady-state: a viewer scrolling, a thumbnailer, a server rendering the same page twice. | **this is the M12 exit target** |

Three things about that table are deliberate and worth defending.

*The target moves to warm, not because warm is flattering, but because warm is
what the oracle column already was.* Nothing about the oracle's measurement
changed; what changed is that ours now asks the same question. A comparison in
which only one side pays for a cold cache is not a comparison, and §9.1 had
already measured the size of that asymmetry — fourteen times on
`image_bug_718762` — a milestone before anyone acted on it.

*Cold is kept, with its own ratchet entries and no target.* It is a real
quantity that a real caller pays, it is the one a command-line tool rendering a
page and exiting sees, and it is where a regression in one-time setup work would
show. Deleting it to make a table look better would be the wrong direction. It
simply has no oracle to be compared with, because `pdfium_test` offers no cold
mode, and a target against a number that cannot be measured on both sides is
theatre.

*The warm group is primed with one untimed render before the loop.* Criterion's
warm-up would fill the cache eventually, but only eventually, and on
`image_bug_718762` the first render is fourteen times the rest — so without
priming the reported median depends on how many warm-up iterations criterion
happened to fit in its window. Priming makes the first *measured* iteration warm
by construction rather than by luck.

**What warm does not mean.** It is not "the cache does the work". Both groups
run the whole engine — the page graph is rebuilt, the content stream is
re-walked and re-interpreted, every path is re-flattened and re-rasterized, on
every iteration of both. What a warm session skips is exactly what §9.1's cache
covers (a decoded and reduced image that has not changed) and what M8's glyph
cache covers (a flattened outline). On a document with no images and no repeated
glyphs the two conventions measure within noise of each other, and on the corpus
they mostly do: the gap is concentrated in the `image` class, which is precisely
where §1.7 said the defect was.


### 1.9 The per-crate split

The suite was one bench target in one crate, `benches/engine.rs`, holding all
six groups over all 44 documents. It is now five, one per crate, and the shared
corpus and the ratchet stay in `benches/` as the certificate suite.

| Crate | Bench file | Groups |
|---|---|---|
| `pdfrum-parser` | `benches/open.rs` | `open` |
| `pdfrum-page` | `benches/build.rs` | `build` **(new)** |
| `pdfrum-render` | `benches/render.rs` | `render-cold-{exact,tinyskia,vello}`, `render-warm-{exact,tinyskia,vello}` |
| `pdfrum-text` | `benches/text.rs` | `text` |
| `pdfrum-edit` | `benches/save.rs` | `save` |
| `pdfrum-bench` | *(none)* | `corpus/`, `baseline.json`, `ratchet`, `profile`, `scaling` |

**Why it is worth the churn.** `cargo bench -p pdfrum-render` is now a command
with a meaning. Before, measuring a rasterizer change meant building the whole
workspace and running eleven groups over 44 documents, so in practice nobody ran
it between edits and the ratchet was a thing you remembered at commit time.
Ownership also puts the benchmark next to the code it measures, where a person
changing that code will see it.

**The `build` group is new, and it is the one the split was most worth doing
for.** §3.1 measured that the engine half — the content-stream walk and its
interpretation, which is `pdfrum-page` — is 54-85% of a render, and §3's entire
P1 pass then optimized the rasterizer half, because that is where the profile
could name a function on a machine without `perf`. The larger half had no
benchmark of its own: a regression in it could only be seen through a render
number that also contained a rasterizer. `build` runs the walk, the interpreter,
the graphics-state machine and the resource resolution, and stops before a pixel
is drawn. §7's outstanding `bumpalo` question is a question about this number,
and it now has one.

**The dependency problem, and the leaf crate that solves it.** All five benches
need the same document list, and they all enter through the *facade* rather than
at their own crate's seam — deliberately: `pdfium_test` renders a document, not
one layer of one, so a bench entering at `pdfrum_render::render_page_with_caches`
would measure a rasterizer against a whole engine and the oracle column would
stop meaning anything. That makes `pdfrum` a dev-dependency of crates it depends
on. Cargo permits that cycle for dev-dependencies and it reaches no published
normal tree, but had the *corpus list* stayed in `pdfrum-bench` — which also
depends on the facade — `cargo bench -p pdfrum-parser` would have built the
vello rasterizer to read a list of filenames, which is the opposite of what the
split is for. So the list moved to `benches/corpus-list`, the `pdfrum-corpus`
crate, whose entire dependency set is `std` and whose one rule is that nothing
in it may know what a PDF is.

**Ratchet compatibility.** `open`, `text` and `save` keep their ids exactly.
The three render groups are renamed `render-{exact,tinyskia,vello}` →
`render-cold-{...}`, and `build` plus the three `render-warm-{...}` groups are
new. The baseline was **re-initialized rather than renamed**, and the reason is
not laziness about the mapping: the same commit changed what the render path
costs (§10's two fixes), so a carried-over number would have shown a large
improvement in a file whose entire purpose is to make improvements visible one
at a time. Re-initializing records the new floor honestly, and §10 carries the
before/after the ratchet would otherwise have printed. The ratchet binary itself
needed no change to find the new groups — it reads `target/criterion/**`, which
criterion keys by group name, not by which crate's binary produced it.

**One sharp edge the split introduces.** `cargo bench -p pdfrum-render` leaves
the other four crates' results on disk from whenever they last ran, and a
subsequent `ratchet check` will compare against them as though they were fresh —
the "not run" report cannot see the difference, because the files are there. The
rule is `cargo bench --workspace` before any check that decides something;
`benches/README.md` and the ratchet's own module docs both say so.

**The dev loop.** `scripts/bench-quick.sh` runs three representative documents
per class — eighteen files, chosen for spread *inside* each class rather than
for weight, so a change that helps large inputs and hurts small ones shows as
two rows moving oppositely instead of one average that moved a little — at
criterion's floor, in about three minutes. It takes an optional group name.
It deliberately does **not** run the ratchet: at ten samples the interval is
several times the noise band, and a result from it is a reason to run the full
suite, never a substitute for having run one.

## 2. The noise band, measured

The ratchet's bands are empirical. They come from running the suite repeatedly
on an unchanged binary and taking the spread, not from picking a round number.

| Group | Band | Why it is where it is |
|---|---:|---|
| `open` | 8% | Microseconds per iteration; the widest spread in the suite, and the reason it is not judged at the render band |
| `render-exact` | 3% | Immediate-mode, no internal threading |
| `render-tinyskia` | 3% | Same |
| `render-vello` | 4% | Retained-scene; the `finish` rasterization is one large burst and jitters more |
| `text` | 4% | |
| `save` | 5% | Allocation-dominated |

Criterion is configured at **50 samples over a 5-second window with a 2-second
warm-up**. The tension behind those numbers is worth stating: the defaults leave
the confidence interval wider than the regressions the ratchet must catch, but
44 documents x 6 groups is 264 benchmarks, and every second added to the window
costs four and a half minutes of wall clock. A suite nobody runs catches
nothing. `sample_size(50)` rather than the default 100 because criterion's floor
is `sample_size` iterations *regardless* of the window, and at 100 the two
second-long image documents alone would add ten minutes for no reduction in
spread.

### What the suite actually costs to run, and the one thing to fix next

The estimate above ("about forty minutes") was made from median document cost
and is **wrong for this corpus**, which is worth recording because the next
person will make the same estimate. Criterion's floor is `sample_size`
iterations regardless of the window, so a benchmark's cost is
`max(window, 50 x iteration)` — and the `image` class's three pathological
documents cost 0.6–1.2 seconds *per iteration*. Each of those is therefore a
**48–60 second benchmark**, times three render backends, and the nine image
documents alone dominate the wall clock.

The measured shape: the first 60 benchmarks (all of `open`, which is
microseconds, plus the first render group's cheap classes) complete in minutes;
the render groups over `image` then take longer than everything else combined.

**The fix, taken:** `sample_size` is chosen **per document** rather than per
suite, in `samples_for`. The five second-scale documents get 10 or 20 samples;
the other 39 keep 50. That is not a shortcut but the correct allocation of a
fixed time budget: the standard error of a median falls as `1/sqrt(n)`, so the
last thirty samples of a one-second benchmark tighten an interval that is
*already* far inside the 5% the machine itself contributes — and cost half an
hour to collect. Spending that time on the microsecond benchmarks, where fifty
samples is genuinely few, is strictly better.

The counts are a named list rather than a measured threshold because criterion
needs the number before it has timed anything; a "measure then decide" rule
would need a warm-up pass of its own. The list is stable as long as the corpus
is, and the symptom of a missing entry is a suite ten minutes longer per
backend.

**The bands in the table above were re-measured at these counts**, not carried
over from the flat-50 configuration — changing `sample_size` changes the
distribution the band describes, and the band is what the ratchet's correctness
rests on.

Still not taken, and still worth doing: a `--quick` profile running one
representative document per class for the iterate-on-a-change loop, with the
full 44 reserved for the ratchet.

**Independently measured, the whole-document spread on an unchanged binary
reached 5% on the heaviest documents.** That is larger than several of the
per-group bands above, and the difference is real rather than contradictory:
criterion's median over 50 samples is a much tighter statistic than a single
whole-document wall-clock timing, which is what §3's A/B numbers are. Every
conclusion in §3 is drawn against the 5% figure, which is the conservative one.

### 3.1 Where the time actually goes

Three things this says that the M8 hypothesis did not:

- **Shading is a `fill_path` workload, not a shading-evaluator workload.** The
  mesh and axial rasterizers decompose a shading into *thousands of small
  fills* — 28368 of them on one page — so the span blitter and the compositor
  are what a shading page costs. That is why §3.2's change moved this class
  most.
- **Text really is `draw_image`**, confirming wave 7b: the glyph-bitmap cache
  turned per-glyph outline fills into per-glyph blits, and the blit is now the
  line item.
- **The engine half is not small.** On `mixed_tcpdf_045` it is 85%. Content
  interpretation and the page-graph walk are not the free part of a render,
  which is a correction to M8's "interpretation is 3% of a text page's cost" —
  true of that fixture, not of this corpus.

### 3.2 Landed: the opaque-destination composite fast path

`crates/pdfrum-render/src/blend.rs`. `composite_premultiplied` un-premultiplied
both pixels, blended straight, and premultiplied back — four divides and two
multiplies per channel — for *every* pixel of *every* fill, stroke, glyph blit
and image draw.

For `BlendMode::Normal` over an **opaque** destination the whole of that
collapses, algebraically and exactly, to one `alpha_merge` per channel:
`blend_rgb(Normal, ..)` is the identity on the source, so `out_a = 255`, the
premultiply-back is the identity, `ratio = sa`, and the channel is
`alpha_merge(d, s, sa)`.

This is not a corner case: a PDF page renders onto an opaque white backdrop by
default, so every ordinary draw on a page with no transparency group takes it.

**Proved identical rather than argued identical**, three independent ways,
because this is a performance change inside a parity engine:

1. `the_opaque_normal_fast_path_is_exhaustively_identical` walks all relevant
   inputs against the general route reconstructed in the test module.
2. An out-of-tree brute force over the full `(sa, sr, dr, coverage)` product —
   including non-canonical premultiplied inputs where a channel exceeds its
   alpha — found zero mismatches.
3. The rendered PNG of an affected corpus file is **byte-identical** with and
   without the fast path.

Three further tests pin the guards: a non-opaque destination must not take it,
the other fourteen blend modes must not take it, and unequal channels with
partial coverage must still agree.

**Measured** (instrumented, `exact`, best of repeated runs):

| Document | Before | After | Delta |
|---|---:|---:|---|
| `text_foxittext` — `draw_image` | 2.914 ms | 1.233 ms | **-58%** |
| `text_foxittext` — whole page | 4.665 ms | 3.107 ms | **-33%** |
| `shading_axial_radial` — whole page | 42.12 ms | 35.08 ms | **-17%** |

### 3.3 Landed: the span blitter's loop-invariant hoist

`crates/pdfrum-raster-exact/src/target.rs`. `blend_span` and `blend_span_with`
called `clip_at(col, row)` per pixel, which re-decided whether a clip existed at
all and recomputed `row * width + col` from scratch, and then `blend_pixel`
recomputed the destination index a second time to write the result. All of it is
loop-invariant or contiguous; none of it was visible to the optimizer through
the `Option<AlphaMask>` behind a reference.

Now the clip's bytes for the span are taken **once**, as a slice, and the
destination row is walked as `chunks_exact_mut(4)`.

This surfaced a **latent bug**, which is recorded because it is the one way the
change could have moved a pixel. `clip_at` computes `y * mask.width() + x` and
reads it out of a flat buffer; at `x >= mask.width()` that index is still inside
the buffer and lands on the **next row of the mask**. A span running past a
narrow clip's right edge would have been painted through whatever the row below
held. `clip_span` refuses the slice and answers all-zero — outside the clip is
not painted. No corpus pixel moves, because the engine sizes every clip mask to
the device; the invariant is now load-bearing for the fast path, so
`a_clip_narrower_than_the_target_reads_zero_past_its_edge` pins it and
`clip_span_reproduces_clip_at_exactly` requires the fast form to agree with the
old one at every position of a deliberately awkward mask. `clip_at` is retained
under `#[cfg(test)]` purely as that specification.

Measured together with §3.2 (the two are in the same call chain and were
measured as a pair): the numbers in §3.2's table are the combined effect.

### 3.4 Landed, no effect: the image resample inner loop

`crates/pdfrum-render/src/stretch.rs`. `reduce_to`'s two box-filter passes went
through `pixel()`/`set_pixel()` per texel — four bounds-checked `get`s to read,
an index recomputed to write. Rewritten to walk row slices, with the vertical
pass resolving its tap rows once per destination row instead of once per pixel,
and each row **paired with its weight** so that a row the bounds check rejects
drops its weight with it (a `filter_map` into a bare `Vec` zipped against
`weights` afterwards would silently shift every later weight onto the wrong row
— the one way this rewrite could have changed a pixel).

| Document | Before | After | Delta |
|---|---:|---:|---|
| `image_bug_718762` | 1253.8 ms | 1202.5 ms | -4.1% |
| `image_bug_583804` | 727.2 ms | 745.0 ms | +2.4% |
| `image_bug_898443` | 1021.5 ms | 942.5 ms | -7.7% |
| `image_en_fqa` | 651.1 ms | 612.7 ms | -5.9% |

**All four are inside the 5% whole-document noise band, in both directions.**
The change is kept — it is strictly less work and the code is no worse — but it
is recorded as *no measured effect*, not as a 5% win. §3.6 is why.

### 3.5 Landed, no effect: hoisting the stencil branch out of `to_pixmap`

`crates/pdfrum-render/src/image.rs`. The per-pixel loop re-tested
`if let Pixels::Stencil` — a property of the *image* — on every sample, and wrote
through `set_pixel`. Hoisted and slice-written. Same outcome as §3.4: every
document moved less than the noise band. Kept for the same reason.

### 3.6 The image class's real cost, which is not a loop

The instrumented profile of `image_bug_718762` — 1 KB of PDF, 1.2 seconds of
render:

```
page-graph build (once, not in the loop): 337.663 ms
RASTER (sum)          0.029     0.0%
ENGINE (rest)       872.829   100.0%
```

**872 ms per render, and 0.03 ms of it reaches the rasterizer.** The file
declares a 5000x5000 image — 25 million pixels — and every render converts the
decoded samples to a pixmap (`to_pixmap`) and box-reduces them (`prescale`)
again from scratch. That is ~35 ns per source pixel across the two, which is
about what those loops should cost; there is no constant factor left to win.

The cost is not the loop, it is that **the loop runs again for every render of
the same unchanged image.** `BuildContext` already carries an `ImageCache` for
*decoded* images; what is not cached is the conversion and the reduction
downstream of it, both of which are pure functions of (image, device footprint).

This is the largest single finding in M12 and it is deliberately **not fixed
here**. It is a cache with an eviction policy and a key that has to include the
device footprint, it interacts with `RenderCaches`' existing budget, and PLAN.md
puts decoded-image cache eviction in **P2** alongside the peak-RSS work. Fixing
it inside a P1 loop-tuning commit would be smuggling a design decision through
the wrong gate.

### 3.7 Landed, measured at zero: `FxBuildHasher` (and why `rustc-hash` stays out)

DEPS.md pre-approves `rustc-hash` for the object store and the glyph-cache maps.
The protocol still requires the tuned no-dep baseline first, so that is what was
built: `pdfrum_common::FxHasher`, which *is* `rustc-hash`'s algorithm — a rotate,
an xor and a multiply per word, about twenty lines — applied to
`ObjectStore::{cells, containers}` (keyed by object number, a `u32` this
workspace assigns) and `BitmapCache::entries` (keyed by a glyph id and four
`i32` matrix coefficients).

Both keys are integers *we* generate, so SipHash's collision resistance is
resistance to nothing; the module documents which keys may and may not use it,
because a name string out of a file must keep the seeded hasher.

**A/B, whole-document, best of repeated runs:**

| Document | SipHash | FxHash | Delta |
|---|---:|---:|---|
| `text_foxittext` render | 5.618 ms | 5.557 ms | -1.1% |
| `text_tcpdf_055` render | 125.97 ms | 126.74 ms | +0.6% |
| `vector_font_feature` render | 136.18 ms | 138.47 ms | +1.7% |
| `mixed_tcpdf_045` render | 51.76 ms | 53.80 ms | +3.9% |
| `text_tcpdf_055` open | 0.039 ms | 0.032 ms | -18% |
| `mixed_tcpdf_045` open | 0.017 ms | 0.016 ms | -6% |

Every render number is inside the noise band, in both directions. The `open`
numbers look large and are not: `open` is tens of microseconds, sits at the 8%
band for exactly this reason, and the absolute difference is 7 microseconds.

**Verdict: `rustc-hash` is not admitted.** Not because the no-dep version beat
it — they are the same three instructions and would measure the same — but
because *neither* clears DEPS.md's bar over doing nothing. The maps are not hot
enough for the hash function to be visible. The no-dep hasher is kept: it costs
one file, it is strictly less work, and it makes hash iteration order
deterministic across runs, which is a property this workspace wants anyway.

If a future profile shows object resolution dominating something, this is the
place the dependency question reopens — with the A/B already built.

### 3.8 Not attempted, with a reason: the lexer's byte-scan loops

The corpus does not justify it yet. `open` is **tens of microseconds** on every
document in the set, against renders of milliseconds to a second — three to five
orders of magnitude apart. The tuned scalar scan is the right first move when
there is a file that makes it matter, and §7 records where `memchr` would be
evaluated when there is.

### 3.9 Measured and declined: `fearless_simd` in the span compositor

§7's first-ranked candidate, taken to a working implementation and A/B'd under
DEPS.md's performance ring. **The dependency is not admitted**, and the reason
is not that the kernel was slow — it is that the loop it vectorises does not
have the shape §7 assumed.

**What was built.** `crates/pdfrum-raster-exact/src/simd.rs`, behind a
`simd` cargo feature (default off), vectorising `blend_span`'s unclipped inner
loop for the solid-colour / opaque-destination / `Normal` case — the case §3.2
showed is most of a page. Four pixels per 16-byte vector via `widen_u8x16` into
sixteen `u16` lanes, `alpha_merge` as multiply-add, and the truncating divide by
255 as the exact shift-add identity

```text
x / 255 == (x + (x >> 8) + 1) >> 8      for all x in 0 ..= 65534
```

which is *exact*, not approximate, over the range that arises: `alpha_merge`'s
numerator is bounded by 255 * 255 = 65025, and the single value where the
identity fails (65535) is unreachable. The one divide by a *varying* quantity —
un-premultiplying the source — is hoisted out of the loop by the caller, because
a solid span's source pixel is loop-invariant. That hoist is what makes the
kernel expressible at all.

**`fearless_simd` 0.4.1's API was sufficient**, so `wide` was never reached for
on API grounds: `widen_u8x16`/`narrow_u16x16`, `mul_u16x16`, `add`, `shr`, `and`,
`or` and `dispatch!` express the whole kernel. One API trap is worth recording
because it produced silently wrong pixels and the identity test caught it:
`cvt_from_bytes_u16x8` is a **bit-level reinterpretation**, not a widening
zero-extend — it pairs two bytes into one lane. `widen_u8x16` is the widening
operation.

**Parity was proved, not argued**, the way §3.2's fast path was:

1. `the_simd_kernel_is_byte_identical_to_the_scalar_loop` — exhaustive over
   every alpha, a spread of source and destination values, and every span length
   that exercises the vector body, its tail, and the boundary between them.
2. `div255_is_exact_where_it_is_used` — the shift-add identity over its whole
   range, plus the bound that makes the failing value unreachable.
3. `the_kernel_agrees_with_the_engines_own_compositor` — against
   `composite_premultiplied` itself, so the kernel cannot drift into being a
   second, divergent compositor.
4. **All 209 rendered pages of all 44 corpus documents are byte-identical**
   with and without the feature (`pdfrum-tool --png --md5`).

So the kernel is correct. It is also not worth having.

Per class, as geometric means of the per-document ratios:

| Class | Geomean | Verdict |
|---|---:|---|

| `vector` | **+1.6%** | slower |
| `shading` | **+2.2%** | slower |

The bar is >= 10% on a class or >= 5% on the geomean. The measurement is
**+1.4% in the wrong direction**, the best single document is -1.0% (inside the
noise band), and the worst is +6.2%. It fails, and it fails the way §7 warned it
might — the sparse-span cases regress.

**Why, and why no kernel could have won.** §7's premise was that the compositor
is a walk over long spans. It is not, and this is the finding worth keeping.
Instrumenting `blend_span`'s span lengths over the corpus:

| Document | Solid spans | Pixels | Mean length |
|---|---:|---:|---:|
| `shading_axial_radial` | 342 308 | 343 088 | **1.00** |
| `shading_tcpdf_030` | 737 770 | 782 310 | **1.06** |
| `vector_paths_1751` | 16 896 | 17 085 | **1.01** |
| `vector_en_system` | 102 478 | 103 227 | **1.01** |
| `text_tcpdf_055` | 987 322 | 2 120 426 | 2.15 |
| `vector_tcpdf_009` | 6 479 | 165 699 | 25.57 |

On `shading_axial_radial`, **99.8% of spans are exactly one pixel long**. That
is structural rather than incidental: `sweep_row` emits a boundary pixel as its
own `emit(x, 1, y, alpha)` and then the interior run separately, and a shading
decomposed into 28 368 tiny fills is nearly all boundary. The fraction of
composited pixels that a vector body of width W can even *reach*:

| Document | W=4 | W=8 | W=16 |
|---|---:|---:|---:|
| `shading_axial_radial` | **0.0%** | 0.0% | 0.0% |
| `vector_paths_1751` | **0.6%** | 0.0% | 0.0% |
| `shading_tcpdf_030` | 2.8% | 0.4% | 0.3% |
| `text_tcpdf_055` | 45.6% | 45.6% | 32.3% |
| `vector_tcpdf_009` | 97.8% | 97.8% | 97.8% |

**This is what decides `wide` as well as `fearless_simd`, without implementing
it.** `wide`'s advantage is a compile-time width and a smaller surface; neither
changes a span's length. On the two documents that nominated this work in the
first place, *no* SIMD kernel at *any* width reaches a single pixel, and a wider
vector is strictly worse. The remaining cost on those documents is the guard
itself — the destination-opacity scan and the dispatch — which is the +2 to +3%
the table shows.

**And the ceiling is low even where SIMD does reach.** Replacing the solid-span
blend with nothing at all — an infinitely fast compositor, the strict upper
bound on any optimization of this loop — measures:

| Document | Real | Blend deleted | Solid-composite share |
|---|---:|---:|---:|
| `shading_axial_radial` | 53.53 ms | 44.17 ms | **17.5%** |
| `text_tcpdf_055` | 180.90 ms | 158.54 ms | **12.4%** |
| `vector_paths_1751` | 11.91 ms | 11.26 ms | **5.4%** |

So on `vector_paths_1751` the entire budget available to this work is 5.4%, and
DEPS.md asks for 10%. The 63.4% the §3.1 profile charges to `fill_path` on
`shading_axial_radial` is **not** 63.4% of compositing — it is path setup,
rasterizer reset, cell sorting and sweep dispatch across 28 368 separate fills,
of which the actual blend arithmetic is 17.5%.

**Verdict: `fearless_simd` is not admitted, and `wide` is declined on the same
evidence.** The gated code is **deleted** rather than left in tree. That is a
judgement about maintenance cost against option value: the negative result is
structural and will not change while the rasterizer emits per-pixel boundary
spans, so the code would be a permanent second compositor — a dependency edge, a
cargo feature, a `#[cfg]` in the hot path, and an arithmetic path that must be
kept byte-identical to the oracle forever — held against a re-measurement nobody
should want to make. What is worth keeping is the *measurement*, which is this
section, and the reusable finding is the span-length distribution above.

**Where this reopens.** If the shading rasterizer ever stops decomposing into
thousands of small fills — evaluating a shading directly into long spans, which
is a real optimization and a much larger one than this — then the compositor
becomes a long-span walk, `text_tcpdf_055`-shaped or better, and the SIMD
question is worth asking again. The order matters: span length first, vector
width second. Reaching for SIMD before the spans are long is optimizing the
17.5% inside the 5.4%.

## 4. The rayon multi-page scaling curve

`scripts/bench-scaling.sh`, over `benches/src/bin/scaling.rs`: the nine corpus
documents with eight pages or more, rendered through
`par_iter().map_init(RenderSession::new, …)` — a session per *worker*, reused
across every page that worker handles, which is the shape
`crates/pdfrum/examples/parallel-render.rs` documents.

One process per thread count, because rayon's global pool is built once and
cannot be resized: a single process sweeping thread counts would measure the
first configuration several times and print a flat curve that looks like a
result.

| Threads | Total (ms) | Speed-up | Efficiency |
|---:|---:|---:|---:|
| 1 | 1270.2 | 1.00x | 100% |
| 2 | 714.5 | 1.78x | 89% |
| 4 | 411.5 | 3.09x | 77% |
| 8 | 264.5 | 4.80x | 60% |
| 16 | 208.7 | 6.09x | 38% |
| 32 | 211.9 | 6.00x | 19% |

Per document, one thread against sixteen:

| Document | Pages | 1 thread | 16 threads | Speed-up |
|---|---:|---:|---:|---:|
| `text_tcpdf_055` | 14 | 159.8 ms | 20.5 ms | **7.78x** |
| `mixed_tcpdf_059` | 16 | 85.0 ms | 13.7 ms | 6.22x |
| `vector_font_size14` | 9 | 93.5 ms | 15.2 ms | 6.16x |
| `text_quick_start` | 11 | 440.2 ms | 69.1 ms | 6.37x |
| `text_foxit_products` | 11 | 67.5 ms | 11.1 ms | 6.09x |
| `text_tcpdf_063` | 10 | 160.2 ms | 27.2 ms | 5.88x |
| `mixed_en_uicase` | 12 | 69.6 ms | 12.4 ms | 5.61x |
| `vector_font_feature` | 10 | 111.3 ms | 23.1 ms | 4.83x |
| `mixed_tcpdf_045` | 16 | 104.4 ms | 27.3 ms | 3.83x |

**Reading the curve honestly.** It is near-linear to four threads (77%
efficiency), pays for itself to sixteen, and **stops at sixteen** — 32 threads is
slower than 16. That is the machine, not the engine: the 7950X has 16 physical
cores and 32 SMT threads, and a render is a dense arithmetic workload with
little memory stall for a sibling thread to fill, so the second thread on a core
buys nothing and costs scheduling.

The ceiling is also **the corpus, not the code**: the longest document available
is sixteen pages, so past sixteen threads there is at most one page per worker
and the curve is measuring how evenly nine documents' page counts divide. PLAN.md
§M12's target — *">= 3x oracle throughput on multi-page docs with rayon"* — is
met at four threads and exceeded by 6x at sixteen. A 300-page document would
almost certainly scale further and there is not one in the checkout to prove it
on, which is stated rather than extrapolated.

`vello_cpu`'s own internal multithreading is **off** throughout; this is the
facade's page-level parallelism alone. Configuring the two together is a
separate measurement and is not made here.

## 5. Conformance: the gate, and a pre-existing drift traced to its commit

`conformance run --check-regressions` was run after every change.

**Result: 1675 files, 1624 pass, 51 fail, no regressions** — identical to the
committed scoreboard in every total and every tag:
`page-count 2, pixel-fail 42, tierA-mismatch 9`, text 2052/2061 pages (99.6%).

M12's stricter self-imposed rule was that pixel numbers must not move *at all*.
Four files' SSIM moved in the fourth or fifth decimal place:

| File | Committed | Measured |
|---|---|---|
| `corpus/fx/other/3bigpreview.pdf` | ssim 0.962150 | 0.962106 |
| `resources/annotation_highlight_square_with_ap.pdf` | max_channel_diff 65 | 64 |
| `resources/pixel/bug_1015233.pdf` | ssim 0.994581 | 0.994579 |
| `resources/pixel/bug_1015233.in` | ssim 0.994581 | 0.994579 |

**This drift is not M12's**, and P2 found out whose it is. The P1 evidence that
it predated the milestone was:

- It appeared in the **first conformance run of this session, before any code
  change was made.**
- A **completely pristine tree** — every M12 change stashed, `git status` clean
  on tracked files — reproduces the same four deltas against the committed
  scoreboard.
- Every M12 variant produces **byte-identical scoreboards to each other**: the
  full change set, blend-only, blend-plus-target, and pristine all agree.
- The rendered PNG of the affected file is **byte-identical** with and without
  the composite fast path.

P1 guessed from that that the cause was "most likely a toolchain or dependency
rebuild." **That guess was wrong**, and the way it was disproved is the useful
part of this section.

### 5.1 The cause: `31cba80`, bisected rather than argued

The suspect is `31cba80`, *"Read a real the way PDFium reads one, to the last
ulp"* — a one-file change to `crates/pdfrum-page/src/tokenize.rs` that replaced
the content tokenizer's digit-by-digit `f32` accumulator with a correctly
rounded `str::parse`, matching PDFium's `StringToFloat`. Its own message
explains the mechanism exactly — *"a rectangle's edge runs through floor and
ceil on its way to a device rect, so a 1e-7 relative error becomes a whole row
of pixels"* — and then ends by asserting that the conformance scoreboard does
not move. **That last sentence is the one wrong thing in it.**

The scoreboard was rebuilt at three revisions plus HEAD, each in a detached
worktree with its own `CARGO_TARGET_DIR` so no in-flight edit could contaminate
a number:

| Revision | `3bigpreview` ssim | `annot_hl_sq` mcd | `bug_1015233` ssim |
|---|---|---|---|
| `be7a3db` — the scoreboard's own commit | **0.962150** | **65** | **0.994581** |
| `d486801` — the culprit's parent | 0.962150 | 65 | 0.994581 |
| `31cba80` — the culprit | **0.962106** | **64** | **0.994579** |
| `4504fdb` — HEAD at the time | 0.962106 | 64 | 0.994579 |

**The `be7a3db` row is what makes this a bisect and not a story.** It
reproduces the committed numbers bit for bit today, on today's toolchain and
today's lock file — which is precisely what a toolchain or dependency rebuild
could not do. A rebuild would have moved `be7a3db` too. The timeline agrees:
the scoreboard's `generated_at` is two minutes before `be7a3db` was committed,
and `31cba80` landed 45 minutes later.

Three renders sit behind the four rows: `bug_1015233.pdf` and `.in` are two
corpus entries sharing one golden.

### 5.2 The other half: we are deterministic, measured

The question §5 raised was not only *what moved* but *whether we move at all*,
because a ratchet on a nondeterministic engine is worthless. Measured:

- **44 renders of `3bigpreview.pdf` are byte-identical**, md5
  `2ecc7999ac200a35ae2937d675aaa521` — 24 runs sweeping `RAYON_NUM_THREADS`
  over 1, 2, 8 and 32, then 20 more at randomized counts in 1..32.
- `annotation_highlight_square_with_ap.pdf` and `bug_1015233.pdf` are likewise
  byte-stable over nine runs each at three thread counts.

Thread count cannot reach a file's metric **by construction**, which is the
stronger statement: `pdfrum-tool` links no rayon at all (rayon appears in this
workspace only as a *caller-side* option in `pdfrum`'s docs),
`conformance/src/pool.rs` parallelises one subprocess per file so cross-file
scheduling cannot touch one file's pixels, and `conformance/src/ssim.rs` is a
sequential `f64` reduction with no parallel accumulation order to vary.

The oracle side cannot have moved either: the goldens are frozen PNGs on disk
and `git log be7a3db..HEAD -- conformance/goldens` is empty. Only our side
could move, and it did.

One trap worth recording because it costs an hour: **`manifest.json`'s `md5`
digests do not match `md5sum` of the golden PNGs, for any of the 1712
artifacts.** That is correct, not corruption — it is `pdfium_test --md5`'s
digest over the raw *bitmap buffer*, not over the encoded file, and
`conformance/src/run.rs` uses it only as a presence flag.

### 5.3 What was done about it

The scoreboard is re-baselined in a commit of its own that touches nothing
else, because rewriting a parity baseline inside a performance change is the
move that makes a scoreboard stop meaning anything. Nothing is *fixed*, because
nothing is broken: `31cba80` is the correct behaviour, validated against
PDFium's own `ByteStringToFloat` vectors with exact equality, and it fixed a
real bug — the old accumulator truncated exponents and read `1.2e34` as `1.2`.

The direction of the four is **mixed**, which is what a last-ulp correction
should look like rather than a regression: `annotation_highlight_square_with_ap`
*improves* (max channel difference 65 → 64, one level closer to the oracle),
while the other two lose 4.4e-5 and 2e-6 of SSIM where the old error happened
to cancel. No file changes pass/fail status.

Two process findings outlive this investigation:

- **A commit that knowingly moves pixels should re-baseline in the same
  breath.** `31cba80` reasoned correctly about why its change was visible and
  then asserted the opposite about the scoreboard, unverified.
- **`--check-regressions` is monotone by design and cannot catch this.** It
  fires on pass → fail; all four of these moved *within* their status. M12's
  stricter "pixel numbers must not move at all" rule is a genuinely different
  check, and wanting it means building it — a scoreboard diff, which is what
  every P2 change below was gated on instead.

`scripts/ci.sh` is green: fmt, clippy `-D warnings`, 3003 tests, doctests,
rustdoc, `cargo-deny`, and the pure-Rust dependency-tree check.

## 7. The gated-dependency candidates, prioritized by evidence

DEPS.md gates `fearless_simd`, `wide`, `bumpalo` and `memchr` behind the same
admission-by-measurement rule. None is admitted. This is the ranked list of
where each would be *evaluated next*, with the loop named and the profile line
that nominates it — evidence, not guesses.

### 1. ~~`fearless_simd` or `wide` — the span compositor~~ — **RESOLVED, declined**

**§3.9 has the measurement.** This item is closed: the kernel was written
against `fearless_simd` 0.4.1, proved byte-identical three ways plus 209
byte-identical rendered pages, and measured at **+1.4% geomean — slower** —
against a bar of 10% on a class or 5% on the geomean. `wide` is declined on the
same evidence rather than implemented separately.

The premise stated here was wrong, and the correction is the useful part:
**the compositor is not a long-span walk.** 99.8% of the solid spans on
`shading_axial_radial` are exactly one pixel long, so a vector body of any width
reaches 0.0% of its composited pixels. The 63.4% the profile charges to
`fill_path` is per-fill overhead across 28 368 fills, not blend arithmetic —
deleting the blend entirely buys 17.5% there and 5.4% on `vector_paths_1751`.

The risk this section flagged was real but secondary: the sparse cases did
regress (+2 to +3%), though on the guard's cost rather than on the
`cov == 0` early-out. The reopening condition is in §3.9 — **span length first,
vector width second.**

### 2. `bumpalo` — the page-graph walk's per-object temporaries

**Where:** `pdfrum_render::walk`, and the `Vec` churn under it.

**Why it is second:** the profile's biggest surprise is that the **engine half is
not small** — 85.4% on `mixed_tcpdf_045`, 59.8% on `vector_paths_1751`, 53.8% on
`text_foxittext`. That is the walk, not the rasterizer, and it is the half M12
has not touched at all.

**What has to happen first:** this one is *not* ready for an A/B, and saying so
is the useful part. The profile attributes to the seam, not to symbols, so
"85% is engine" does not yet distinguish allocation churn from colour conversion
from interpretation. **A real `perf` profile is the prerequisite** — which means
either a machine where `perf_event_paranoid <= 1`, or the P2 work adding
finer-grained instrumentation inside the walk. Reaching for an arena allocator
before knowing whether allocation is the cost would be exactly the guess this
protocol exists to prevent.

### 3. `memchr` — the lexer's byte scans

**Where:** the token scanner and the keyword resynchronisation path in
`pdfrum-parser`.

**Why it is third and not higher:** §3.8's number. `open` is tens of microseconds
on every one of the 44 documents; there is no file in the corpus where lexing is
visible against rendering. `memchr` would be a real win on a *large* file — a
100 MB linearized document, a cross-reference rebuild scanning the whole file —
and the corpus has nothing like one because the oracle's checkout has nothing
like one.

**What it needs first:** a benchmark input that makes the lexer matter, which
means either synthesising one or sourcing a large real-world PDF. Then the tuned
scalar scan (a `chunks_exact(8)` word-at-a-time scan for the delimiter set),
*then* the A/B. Recorded now so the order is not lost.

### 4. Nothing for the image class — and that is the finding

The obvious candidate would have been SIMD for `to_pixmap` and `reduce_to`. §3.6
says why it is not on this list: those loops already run at ~35 ns per source
pixel and the cost is that **they run again on every render of an unchanged
image**. A 4x SIMD win on 872 ms of redundant work is 654 ms of redundant work.
The fix is a cache (P2), and until it exists, vectorizing those loops would buy
a fraction of something that should be zero.

**P2 built the cache (§9.1), and this entry survives it unchanged.** The
redundant work is gone; what remains on a *cold* image is one pass of those two
loops, which is now a once-per-image cost rather than a per-render one. That
makes vectorizing them worth even less than before, not more: the loop that used
to run on every render now runs once, so a 4x win on it is 4x of a cost already
paid a single time. Nothing for the image class, still.

## 9. P2 — the cache the profile demanded, and the memory it costs

### 9.1 The rendered-image cache: the largest single win in M12

§3.6 named the largest cost in the corpus and deliberately left it: `to_pixmap`
and `prescale` re-running over 25 million samples on **every render of an image
that had not changed**, 872 ms of it on `image_bug_718762`, 0.03 ms of which
reaches the rasterizer. Both are pure functions of `(image, fill, transfer,
size)`. They are now memoized in `RenderCaches` beside the glyph outlines and
bitmaps, keyed the way SPEC.md §7 keys the *decoded* cache: by the `XObject` the
image came from and the shape of the request.

Measured with the instrumented harness, `exact` backend, best of repeated runs,
milliseconds per render — the same method and the same machine as §3:

| Document | Before | After | Delta |
|---|---:|---:|---|
| `image_bug_718762` | 837.2 ms | 84.4 ms | **-90%** |
| `image_jbig2_1478366` | 326.8 ms | 33.6 ms | **-90%** |
| `image_bug_898443` | 714.7 ms | 74.4 ms | **-90%** |
| `image_jbig2_880920` | 184.2 ms | 22.9 ms | **-88%** |
| `image_jpx_123` | 59.1 ms | 19.5 ms | **-67%** |
| `image_ccitt_transfer` | 9.4 ms | 3.2 ms | **-66%** |
| `image_bug_583804` | 546.1 ms | 191.2 ms | **-65%** |
| `image_ccitt_3bigpreview` | 38.1 ms | 28.6 ms | -25% |
| `image_en_fqa` | 88.7 ms | 90.5 ms | +2% (in band) |

The A/B was taken in two detached worktrees with separate `CARGO_TARGET_DIR`s,
because a concurrent agent had `pdfrum-raster-exact` mid-edit in the main
checkout; a measurement taken against a tree somebody else is writing is not a
measurement.

**Four key decisions, each of which the obvious alternative gets wrong.**

*The key is the `ObjRef`, not the `Arc<ImageData>`'s address.* A pointer is
stable only while its `Arc` lives; the allocator reuses the address afterwards,
and a cache keyed on one would hand a freed image's pixels to whatever landed on
its bytes. `ImageObject::source` already carries the reference the interpreter
resolved (SPEC.md §7, M11). An image without one — an inline `BI…EI`, or one
reached through an annotation's `/AP` — is simply not cached, which is the right
answer for an inline image anyway: its samples live in the content stream and it
is drawn once.

*The reduction is keyed by its output dimensions, not by the device footprint
that produced them.* `prescale` maps a fractional footprint through a `ceil` and
a clamp onto an integer pixel count, and only that integer changes the pixels.
Keying on the `f64` would miss on two draws of one image whose placements differ
in the seventh decimal and whose reduced pixels are byte-identical — which is
exactly what a page stepping one image across a row produces. `reduction_for`
now names that decision and `prescale` is rewritten to call it, so the key and
the pixels cannot drift apart.

*The colour inputs are in the key only where they are inputs to the pixels.* A
stencil takes its ink from the fill colour, so one 1-bit image painted red and
painted blue is two pixmaps; a photograph never reads the fill colour, and the
key normalizes it away so the same photograph under two fill colours is one
entry. The transfer function is keyed by a **digest** of its samples — the key
must own its data, and 768 bytes in every key of a map mostly without a `/TR` is
not a key.

*The budget refuses rather than evicts*, for a sharper version of the reason
`BitmapCache` does. A rendered image is large — the 5000x5000 one is 100 MB
premultiplied — so an LRU evicting to make room for the image about to be drawn
would, on a page holding two that each fill the budget, evict each for the other
and never register a hit. Refusing degrades to *no cache*, never to *no image*.
The one exception is an empty cache, which admits an image larger than the whole
budget: that is the case §3.6 exists to fix, it is drawn once per render, and it
competes with nothing.

Conformance after the change: **the scoreboard is byte-identical** to the
committed one — not merely free of regressions but free of any movement in any
metric of any of the 1675 files, which is the stricter rule §5 says the
regression gate cannot enforce.

### 9.2 Peak RSS against the oracle, and the target

`scripts/bench-rss.sh`: both engines open and render each corpus document once,
compared on the kernel's own `ru_maxrss` high-water mark.

Three method choices differ from `bench-oracle.sh`, each because peak RSS is a
different *kind* of quantity than elapsed time, and getting this wrong is how a
memory harness produces confident nonsense:

- **The maximum over rounds, not the minimum.** A wall-clock sample is bounded
  below by the real cost and inflated by contention, so the minimum is the least
  contaminated estimate. A high-water mark is the opposite: contention does not
  make a process allocate. The worst case is the honest summary, and the spread
  is printed so a reader can see it is tight (it is: 1.01–1.10 across the set).
- **One render pass, not forty.** `--render-repeats` is how the time harness
  amortizes process start; here it would *hide* the thing being measured, since
  an unbounded cache only shows itself on the second pass and later.
- **`ru_maxrss`, not `/proc` sampling.** A poller races the peak and usually
  misses it entirely on a document that allocates for forty milliseconds.

The process floor is measured first — both binaries are 3.3 MB having done
nothing — because on a small document that floor is most of what a ratio
compares.

**Result: geometric mean 1.20x over 44 documents.** PLAN.md §M12's target is
≤ 1.5x, and it is met on the mean and on 39 of the 44 files. A geometric mean
because the arithmetic mean of a set of ratios is dominated by whichever is
furthest above 1 and is not the reciprocal of the reverse comparison.

The five that exceed it are all image documents:

| Document | Oracle | pdfrum | Ratio |
|---|---:|---:|---:|
| `image_bug_718762` | 6.9 MB | 202 MB | 29.3x |
| `image_bug_898443` | 25.9 MB | 258 MB | 10.0x |
| `image_jbig2_1478366` | 10.7 MB | 86.9 MB | 8.2x |
| `image_jbig2_880920` | 11.4 MB | 59.4 MB | 5.2x |
| `image_bug_583804` | 143 MB | 357 MB | 2.5x |
| `shading_tcpdf_058` | 10.2 MB | 18.1 MB | 1.8x |

The 29x is mostly its denominator. `image_bug_718762` renders onto a 64x64 page
from a 5000x5000 source: the oracle streams that through a scaled buffer and
peaks at 6.9 MB, where we materialize the decoded image and its pixmap. That is
a real architectural difference — a scaled decode, not a cache policy — and it
is now measured rather than suspected. It is the honest limit of the ≤1.5x
target on this corpus, and it is recorded here rather than argued away.

**How much of this is §9.1's cache?** Almost none, which is worth stating
because the assumption runs the other way. Measured pre-cache against
post-cache, same tool, same files:

| Document | Pre-cache | With cache | Delta |
|---|---:|---:|---:|
| `image_bug_718762` | 201 MB | 201 MB | -0.2 MB |
| `image_bug_898443` | 257 MB | 257 MB | +0.0 MB |
| `image_jbig2_1478366` | 87.4 MB | 86.6 MB | -0.9 MB |
| `image_bug_583804` | 278 MB | 357 MB | **+78 MB** |

Four of the five peaks were already there: the pixmap exists at the moment of
the draw whether or not it is kept afterwards, so retaining it does not raise a
peak it was already part of. `image_bug_583804` is the exception and the number
is exactly explicable — its image is 4473x4473 onto a 4473-point page, so no
reduction applies and the retained pixmap is the full 76 MiB, against a measured
+78 MB.

### 9.3 The eviction policy: what PDFium actually does

PLAN.md asks for "the C++-equivalent budget if PDFium has one, else a documented
cap with LRU." **It has one, and it is not what it looks like.**

`CPDF_PageImageCache::CacheOptimization` is a textbook two-stage policy: sort by
a recency tick, drop unconditionally to the 15 most recent, then keep dropping
until under a 100 MiB budget. Our `pdfrum_page::ImageCache` already reproduces
that mechanism exactly, including the surprising order — the entry cap fires
*before* the byte budget, so a cache of twenty small images sheds five of them.

What the mechanism does not tell you is **when it runs**, and that is the
finding:

```cpp
if (status.GetRenderOptions().GetOptions().bLimitedImageCache) {
  page_cache_->CacheOptimization(...);
}
```

`bLimitedImageCache` **defaults to `false`** and is opt-in through the public
`FPDF_RENDER_LIMITEDIMAGECACHE`; and even when set it runs once per rendered
*layer*, not per insert. So PDFium's default is an **unbounded** per-page image
cache. What bounds it is the page: `CPDF_PageImageCache` is constructed from a
`CPDF_Page` and dies with it.

Ours has the same lifetime — every caller in this workspace builds
`RenderCaches` per page — with a 64 MiB budget on top, which makes it strictly
the *more* conservative of the two. 64 MiB rather than the decoded cache's 100
MiB deliberately: this cache holds the same images again at four bytes per
pixel, and giving both the same budget would double a session's floor for
nothing.

### 9.4 The bound was tested for the obvious tightening, which did not pay

An opt-in "hold at most one rendered image" mode mirroring `bLimitedImageCache`
was implemented, measured, and **removed**.

| Document | Unbounded | One entry | Saved |
|---|---:|---:|---:|
| `image_bug_583804` | 455 MB | 455 MB | -0.3 MB |
| `image_bug_718762` | 201 MB | 201 MB | +0.3 MB |
| `image_bug_898443` | 257 MB | 256 MB | +0.5 MB |
| `image_jbig2_1478366` | 86.4 MB | 86.9 MB | -0.5 MB |

Nothing, in both directions. The corpus explains why, and the explanation is the
part worth keeping: the documents with a memory problem draw **exactly one image
each**, so "at most one entry" is already what the unbounded cache holds; the
documents that draw many images — `mixed_en_uicase` at 5208 draws,
`image_ccitt_3bigpreview` at 1129 — have small ones and no memory problem at
all. The two conditions never coincide in 44 files, so no available document
could demonstrate the knob working.

It is removed rather than shipped-and-documented because an option whose effect
cannot be demonstrated is how a configuration surface fills with things nobody
can later delete. The finding is kept where the code is, so the next person with
a many-large-images document knows the experiment was run and what it needs to
be re-run against.

### 9.5 The Arc/clone pass: one real find, measured at no effect

`object_bbox` built a whole transformed copy of every path — `matrix *
path.clone()` — to decide a cull that discarded it immediately, on **every
object of every page**. On `vector_paths_1751` that is 4970 path allocations per
render, none outliving the comparison two lines later.

It now unions the segments' bounding boxes through the matrix and allocates
nothing. `path_bbox` is pinned by a test requiring it to equal the expression it
replaced across curves, quadratics, rectangles, degenerate paths and five
matrices — including the segment-less case, where kurbo answers
`Rect::default()` (the origin) rather than nothing, so a bare `MoveTo` still
culls exactly as it did.

Best of five, whole document:

| Document | Before | After | Delta |
|---|---:|---:|---|
| `vector_paths_1751` | 4.042 ms | 4.161 ms | +2.9% |
| `vector_tcpdf_009` | 15.150 ms | 15.181 ms | +0.2% |
| `mixed_tcpdf_045` | 5.352 ms | 5.335 ms | -0.3% |
| `text_tcpdf_055` | 52.076 ms | 52.990 ms | +1.7% |

**Inside the noise band, in both directions** — the same outcome as §3.4 and
§3.5, and reported the same way. The allocator handles a short-lived `BezPath`
cheaply enough that removing five thousand of them is invisible against the
render around it. Kept because it is strictly less work and no harder to read;
recorded as *no measured effect*, not rounded into a win.

The wider lesson for the `bumpalo` question §7's second entry defers: this was the most
obviously wasteful allocation in the walk, and removing it bought nothing
measurable. That is weak evidence *against* allocation being the engine half's
cost, and it does not substitute for the `perf` profile §7's second entry says is the
prerequisite — but it is the first actual data point on that question.


## 10. The two outliers, diagnosed — and not fixed

§1.7's table had two rows worse than the class around them by enough that "the
engine is slower" could not be the explanation: `mixed_formfield` at 24.16x and
`image_ccitt_transfer` at 21.66x, against class geomeans of 3.98x and 9.38x.

**Both are now diagnosed to a specific cause. Neither is fixed, and the section
title says so.** In each case the first hypothesis was wrong, the replacement
hypothesis was *also* wrong, and the thing that finally explained the number
turned out to be a cost M12 has no answer for. Two changes did land — one
memoization and one correctness fix — and both are kept, but the A/B says
plainly that neither moves the row it was written for. The measured numbers are
in each entry, including the two claims an earlier draft of this document made
and this one withdraws.

This is the least satisfying section in the file and the one most worth reading.
The pattern in it — a plausible story about where time goes, instrumented at the
wrong seam, producing a confident number that an A/B then refutes — is the exact
failure this document's method exists to catch. It caught it twice. What kept
both from shipping as wins was insisting on the A/B *after* the fix, on the same
binary, against the unfixed tree.

The conformance scoreboard after both changes is **byte-identical** to the
committed one — not merely free of regressions but free of any movement in any
metric of any of the 1675 files, the stricter rule §5 says the gate cannot
enforce.


### 10.1 `mixed_formfield`: three image decodes behind three widgets

**Hypothesis:** widget appearance regeneration runs per render instead of once.

**Wrong, and so was the first replacement for it.** This entry records both
wrong turns, because the way each was refuted is the useful part.

The page has **zero content objects** — rendering it with `annotations: false`
takes 0.035 ms — so all 86 ms is the annotation overlay, and the hypothesis was
at least pointing at the right half of the engine. But appearance *generation*
is not the cost: instrumented, `ap::generate_appearances_with_text` is
**0.19 ms** and `ap::FormFonts::load` is **1.5 ms**, together under 2% of the
render. The overlay is expensive for a reason that has nothing to do with
appearances being regenerated.

**The first replacement hypothesis, and why it was also wrong.** The file's
AcroForm `/DR /Font` holds sixteen non-embedded fonts, fourteen of them
byte-identical SimSun descriptors under names differing by one appended digit.
Each falls to the bottom of the substitution ladder into `builtin_generic`,
which re-parsed a 67 KB `include_bytes!` PFB on every call. That is a genuine
defect and it is fixed here — the blob is a compile-time constant, so the parse
is a pure function of a `bool` and a `OnceLock` per variant is unconditionally
sound; the base-14 faces reached through `standard_font_data` get the same
treatment as a dense fourteen-entry array. **But it is not this document's
cost.** Measured directly, the first `builtin_generic` call is **0.382 ms** and
every later one is 0.000 ms, so fifteen parses were ~5.7 ms of an 86 ms render,
not the bulk of it. An earlier draft of this section claimed 55 ms on the
strength of an instrumented reading that had compared a cold `FormFonts::load`
against a later, already-warm one — a measurement error, and exactly the kind
this document exists to catch rather than publish.

**The actual cost.** Three of the twenty widgets carry an appearance stream
whose 31 operators include `/IMG Do`, and each takes **10.3 ms to interpret**
— 330 µs per operator. The image is drawn under `0.0678 0 0 0.0678 … cm`, so a
large source is being reduced to a thumbnail: instrumented at the rendered-image
cache's own seam, each of the three produces a **70x53 pixmap in 15 ms**. That
is 45 ms of the document's 84, at roughly **4 µs per output pixel**.

The rendered-image cache is working correctly here and is not the problem: the
three are three *different* `XObject`s (`183`, `187`, `189`), so three misses is
the right answer, and they carry their `ObjRef` properly — the annotation-`/AP`
path does not lose it, because `do_xobject` resolves the reference through the
form's own resource holder before `add_image` ever sees it. Caching cannot help
a document that draws three distinct images once each.

**So this outlier is diagnosed but not fixed, and it is counted as not fixed.**
The cost is `to_pixmap` + `prescale` on the decode path — the same pair §3.6
named as the image class's real cost and §9.1 addressed *by memoizing rather
than by making faster*. Where a document repeats an image, the cache is a
complete answer; where it draws each once, nothing in M12 has made the kernel
itself cheaper, and this document is the corpus's clearest statement of that
gap. §11 counts it as named residue. The honest next step is a reduction path
that decimates before it converts rather than after — reading only the source
pixels the output needs — which is a real piece of work and not a loop tweak.

**What did land here**, and is kept on its own merits: `builtin_generic` and the
base-14 faces are memoized. It is strictly less work on every render of every
document with a non-embedded font, it is measured at ~5 ms on this one, and it
costs nothing — but it does not move this row out of the outlier column, and
§1.10's table shows it not moving.

### 10.2 `image_ccitt_transfer`: a correctness bug found, and a performance claim withdrawn

**Hypothesis:** the P2 rendered-image cache misses here — a keying gap — or
`hayro-ccitt` has per-call overhead.

**Both wrong.** Every image in this file carries an `ObjRef`, none is inline,
and the cache is hit exactly as designed. CCITT is not the cost either: the
44x46 `/ImageMask` the file is named for decodes in **0.0056 ms**, 0.02% of the
document.

The cost is one JBIG2 image, and the mismatch behind it is real and confirmed at
runtime: the dictionary declares `/Width 400 /Height 400`, the codestream's page
is **3562x851**, and the sink's cursor ends at row 851 having been driven over
roughly 3.03 million pixels to fill an image of 160,000. The decode is
**15.4 ms** of the document's 25.7.

**But the fix that seemed to follow does not pay, and the claim is withdrawn.**
An earlier draft of this section asserted 16.3 ms recovered by skipping the
out-of-range callbacks. Measured as an A/B on the same binary, best of eight
cold runs and forty warm:

| | Without the fix | With it | Delta |
|---|---:|---:|---|
| cold | 26.42 ms | 25.75 ms | -2.5% |
| warm | 3.40 ms | 3.37 ms | -1% |

Both are inside the noise band, reported as such rather than rounded up — the
same treatment §3.4, §3.5 and §9.5 give their own non-results. The reason is
visible once the decode is timed on its own: the 15.4 ms is spent inside
`hayro-jbig2`'s arithmetic decoder, which walks the full 3562x851 page whatever
the sink does with the pixels it emits. **The callbacks were never the cost**,
so making them cheap recovers nothing. The decoder exposes no way to bound the
region it decodes, and that — not the sink — is where the 15 ms would have to be
attacked. §11 counts this row as named residue.

**The correctness fix stands, and it is the reason this entry is worth reading.**
Chasing the timing turned up a real bug that has nothing to do with speed:
`BitSink::set` bounds-checked the flat index `y * row_bytes + x / 8` against the
buffer's *length*, which a write one pixel past the declared width passes — it
simply lands on the next row's leading byte. **A codestream wider than the
dictionary was bleeding set pixels into the row below, silently, on every row.**
The sink now carries the width alongside `row_bytes` and refuses a write past
either edge, pinned by
`a_codestream_wider_than_the_dictionary_does_not_bleed_into_the_next_row`, with
`a_chunk_straddling_the_right_edge_keeps_its_valid_prefix` guarding the fast
path against dropping pixels that *are* in range.

It changed no rendered pixel in the corpus or in the 1675-file conformance set —
the bled bits happened never to fall where a visible pixel was decided — which is
exactly the shape of bug that survives a regression gate indefinitely. It is kept
on its own merits, and it is the only thing in this entry that is not a
non-result.

### 10.3 What both entries have in common

Neither outlier was what its hypothesis said, **and neither is fixed.**
`mixed_formfield` is three genuine image decodes producing three thumbnails at
4 µs per output pixel; `image_ccitt_transfer` is one JBIG2 decode of a page
twenty times the size of the image it fills. Both are the *same* gap in
different clothes: **M12 made repeated image work free and left single image
work exactly where it was.** §9.1's cache is a complete answer to a document
that draws an image twice and no answer at all to one that draws three images
once each.

That is the milestone's most useful negative result, and it should set the next
one's agenda ahead of the `bumpalo` and `memchr` questions in §7 — both of which
are about the *engine* half, on evidence that is thinner than this. What landed
from these two investigations is one memoization worth ~5 ms on any document
with a non-embedded font, one correctness fix, and three regression tests.


## 11. The verdict

Every M12 target, with the number it is judged on and where that number comes
from. The render target is judged on **warm** (§1.8's ruling); cold is reported
beside it as a tracked metric with no target.

| Target | Result | Number |
|---|---|---|
| Single-thread geometric mean **>= oracle** on the bench corpus | **MET** | **0.97x** warm geomean over 44 files (§1.10). Sum ratio 1.00x — 1644.2 ms against the oracle's 1639.2 ms. Cold, the same corpus is 3.46x, tracked without a target. |
| **>= 3x** oracle throughput on multi-page docs with rayon | **MET** | **3.09x at 4 threads, 6.09x at 16** (§4), flat past the 16 physical cores. |
| Peak RSS **<= 1.5x** oracle | **MET** | **1.20x** geometric mean over 44 files (§9.2), and on 39 of them individually. The five that miss are image documents where the oracle scales its decode and we materialize; named in §9.2 rather than averaged away. |
| Conformance unmoved by every perf change | **MET** | The scoreboard is **byte-identical** to the committed one after P3's two changes — no movement in any metric of any of the 1675 files, which is stricter than the regression gate §5 can enforce. |
| The ratchet only tightens | **MET** | `baseline.json` re-initialized on the split suite (§1.9's id mapping); `ratchet check` green. |

### The named residue

The geomean is met and three classes beat the oracle. What it does not mean is
that nothing is slow, and the exceptions are worth more than the average.

**`forms` at 3.35x warm is the largest remaining gap**, and it is the one class
where neither convention nor cache helps: form documents are annotation-overlay
work, and §10.1 established that the overlay's cost on `mixed_formfield` is
image decoding inside appearance streams. Six of the seven forms documents are
above 3x. This is the clearest single target for M13.

**Single-image documents are where the engine is genuinely behind**, and
`image_en_fqa` at 11.24x warm is the proof — 598 ms warm against 598 ms cold,
because its images are each drawn once and a cache that memoizes repeats has
nothing to hit. §10.3 states the general form: **M12 made repeated image work
free and left single image work exactly where it was.** `to_pixmap` + `prescale`
have never been made faster, only skipped. A reduction path that decimates
before it converts — reading only the source pixels the output needs — is the
work M12 did not do.

**Two decoder-kernel gaps are outside our code**: `image_ccitt_transfer`'s
15.4 ms sits inside `hayro-jbig2`'s arithmetic decoder walking a 3562x851 page
behind a 400x400 dictionary (§10.2), and no change to our sink reaches it.

**`text` at 1.45x** is the honest middle: cache-insensitive, already optimized
by §3.2's composite fast path, and the class where further work means the
engine half §3.1 measured at 54-85% and §7 still has no `perf` profile of.

### What P3 actually changed, separated from what it revealed

Worth stating plainly, because the headline number moved by a factor of 3.5 and
almost none of that is a code change:

- **The convention change moved the number.** 3.58x → 0.97x is a measurement
  correction, not an optimization. The engine is the same engine; §9.1's cache
  had already done this work a milestone earlier and the suite could not see it.
- **One code change moved a class**: memoizing the built-in Multiple-Master and
  base-14 faces took `forms` cold from 6.56x to 5.18x (§10.1).
- **One code change moved nothing and is kept anyway**: the JBIG2 sink's
  out-of-range fast path, measured at -2.5% cold and -1% warm, both inside the
  band (§10.2).
- **One code change was never about speed**: the JBIG2 row-bleed, a silent
  correctness bug that moved no pixel in 1675 files and was found only because
  the timing investigation went looking somewhere else (§10.2).
- **Two performance claims were withdrawn** after the A/B refuted them (§10.1,
  §10.2). Both are recorded rather than deleted.

The methodological lesson is §10's, and it is the one worth carrying to M13: the
A/B *after* the fix, on the same binary against the unfixed tree, is what
separates a result from a story. It refuted two of this milestone's four
candidate wins.
